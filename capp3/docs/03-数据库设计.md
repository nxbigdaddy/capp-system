## 1. 数据库设计原则与规范

### 1.1 设计原则

| 原则 | 说明 |
|------|------|
| **第三范式(3NF)** | 消除传递依赖，确保数据一致性 |
| **数据完整性** | 通过主键、外键、唯一约束、检查约束保证数据质量 |
| **安全性** | 敏感字段加密存储，操作日志完整记录 |
| **可扩展性** | 预留扩展字段，支持未来业务增长 |
| **性能前置** | 核心查询路径预先设计索引，避免后期大规模重构 |

### 1.2 字符集与存储引擎

- **字符集**: `utf8mb4`（支持完整Unicode，包括emoji和特殊符号）
- **排序规则**: `utf8mb4_unicode_ci`
- **存储引擎**: `InnoDB`（支持事务、行级锁、外键、崩溃恢复）
- **时区**: 统一使用 `Asia/Shanghai`，应用层处理时区转换

### 1.3 字段设计规范

- 主键统一使用 `BIGINT UNSIGNED AUTO_INCREMENT`
- 状态字段使用 `TINYINT`，0=禁用/删除，1=启用/正常
- 金额字段使用 `DECIMAL(18,4)`
- 时间字段使用 `DATETIME` 或 `TIMESTAMP`
- 布尔字段使用 `TINYINT(1)`，0=false，1=true
- 所有表必须包含 `created_at`、`updated_at`、`created_by`、`updated_by` 审计字段
- 软删除使用 `deleted_at DATETIME NULL` 或 `is_deleted TINYINT(1) DEFAULT 0`

## 2. 命名规范

### 2.1 数据库对象命名

| 对象类型 | 命名规则 | 示例 |
|---------|---------|------|
| 数据库 | `capp_` + 环境标识 | `capp_prod`, `capp_dev` |
| 表 | 小写，下划线分隔，复数形式 | `users`, `process_routes` |
| 字段 | 小写，下划线分隔 | `user_name`, `created_at` |
| 索引 | `idx_` + 表名缩写 + 字段名 | `idx_pr_product_id` |
| 唯一索引 | `uk_` + 表名缩写 + 字段名 | `uk_u_phone` |
| 主键 | `pk_` + 表名 | `pk_users` |
| 外键 | `fk_` + 从表 + _ + 主表 | `fk_bom_products` |
| 视图 | `v_` + 描述 | `v_process_card_full` |
| 存储过程 | `sp_` + 操作 + _ + 对象 | `sp_sync_wechat_users` |

```

   │                              │

   ├──1:N── [departments]

                            │
                            ├──1:N── [parts]
                            │         │
                            │         └──1:N── [boms] ──1:N── [bom_details]
                            │
                            └──1:N── [process_routes] ──1:N── [process_steps]
                                                          │
                                                          ├──1:N── [process_cards]
                                                          │         │
                                                          │         └──1:N── [process_files]
                                                          │
                                                          ├──1:N── [process_params]
                                                          │
                                                          └──N:M── [step_equipments] ──N:1── [equipments]
                                                                    │
                                                                    └──N:M── [step_tools] ──N:1── [tools]

[materials] ──1:N── [material_quotas]

[standard_work_hours] ──1:N── [work_hour_quotas]

[change_requests] ──1:N── [change_approvals] ──1:N── [change_histories]

[maxkb_configs] ──1:N── [maxkb_sync_logs]

```

## 5. 数据库性能优化策略

### 5.1 索引优化

| 优化策略 | 具体措施 |
|---------|---------|
| **主键索引** | 所有表使用自增BIGINT主键，避免UUID导致的页分裂 |
| **唯一索引** | 业务编码字段（product_code, part_code等）建立唯一索引 |
| **联合索引** | 高频查询组合字段建立联合索引，遵循最左前缀原则 |
| **覆盖索引** | 常用查询字段组合建立覆盖索引，减少回表 |
| **前缀索引** | 长文本字段（如content）使用前缀索引 |

### 5.2 查询优化

- 核心查询预先编写并经过EXPLAIN验证
- 复杂统计查询使用物化视图或汇总表
- 分页查询使用游标/键集分页，避免深分页OFFSET
- 大数据量报表查询走只读从库

### 5.3 写入优化

- 批量插入使用`INSERT ... VALUES (),(),()`语法
- 大批量导入使用`LOAD DATA INFILE`
- 事务控制：单条操作不开启事务，批量操作合理控制事务大小（500-1000条/事务）

### 5.4 架构层优化

- **读写分离**：主库写，从库读，一主两从架构
- **连接池**：PHP使用持久连接（p:mysql:...），最大连接数200
- **缓存策略**：热点数据Redis缓存，TTL 300-3600秒
- **分表策略**：operation_logs按月份分表，sync_records按系统分表

## 6. 数据备份与恢复策略

### 6.1 备份策略

| 备份类型 | 频率 | 保留周期 | 存储位置 |
|---------|------|---------|---------|
| 全量备份 | 每日02:00 | 30天 | 本地NAS + 异地OSS |
| 增量备份 | 每6小时 | 7天 | 本地NAS |
| Binlog归档 | 实时 | 15天 | 本地NAS + 异地OSS |
| 配置备份 | 每次变更后 | 永久 | Git版本库 |

### 6.2 恢复策略

| 场景 | RTO目标 | RPO目标 | 恢复方式 |
|------|---------|---------|---------|
| 单表误删 | < 30分钟 | < 1小时 | Binlog闪回 |
| 数据库损坏 | < 2小时 | < 6小时 | 全量+增量恢复 |
| 服务器故障 | < 4小时 | < 6小时 | 从库提升为主库 |
| 灾难恢复 | < 24小时 | < 24小时 | 异地备份恢复 |

### 6.3 备份脚本示例

```bash
#!/bin/bash
# 每日全量备份
BACKUP_DIR="/backup/mysql/$(date +%Y%m%d)"
mkdir -p $BACKUP_DIR
mysqldump -h localhost -u backup -p'xxx' --single-transaction   --routines --triggers --databases capp_prod > $BACKUP_DIR/capp_full.sql
# 压缩
gzip $BACKUP_DIR/capp_full.sql
# 上传异地
ossutil cp $BACKUP_DIR/capp_full.sql.gz oss://capp-backup/mysql/
```

## 7. 分表分库策略

### 7.1 当前阶段策略

当前系统采用**单库多表**架构，通过以下方式预留扩展性：

- 所有主键使用BIGINT，支持百亿级数据
- 核心表预留扩展字段（ext_json JSON类型）
- 日志类表按时间分表（operation_logs_202401, operation_logs_202402）

### 7.2 未来分表策略

| 数据表 | 分表策略 | 分表键 | 预估触发条件 |
|--------|---------|--------|------------|
| operation_logs | 按月分表 | created_at | 单表>1000万 |
| sync_records | 按系统分表 | system_code | 单表>500万 |
| ai_messages | 按会话ID取模 | conversation_id % 16 | 单表>1000万 |
| process_cards | 按产品类型分表 | product_type | 单表>500万 |

### 7.3 未来分库策略

当单库性能达到瓶颈时，考虑按业务域垂直分库：

- **capp_user**：用户、权限、部门、企业微信
- **capp_product**：产品、零件、BOM
- **capp_process**：工艺路线、工序、工艺卡片、参数
- **capp_log**：操作日志、同步记录、AI对话

### 7.4 分表分库实施原则

1. **透明路由**：应用层通过DAO层统一路由，业务代码无感知
2. **分布式ID**：采用雪花算法生成全局唯一ID
3. **分页适配**：跨分片查询使用ES或汇总表，避免深分页
4. **渐进实施**：先分表后分库，先日志表后业务表

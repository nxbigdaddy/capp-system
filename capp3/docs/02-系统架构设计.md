## 1. 总体架构概述

### 1.1 架构设计原则

本CAPP系统在架构设计过程中遵循以下核心原则，确保系统在企业级生产环境中长期稳定、高效、安全地运行：

**（1）分层解耦原则**
系统严格采用分层架构设计，将表现层、业务逻辑层、数据访问层、数据存储层进行清晰分离。每一层只与相邻层交互，通过标准接口进行通信，降低层与层之间的耦合度。当某一层的技术实现需要变更时（如更换前端框架、升级数据库版本），不会对其他层产生连锁影响，从而提升系统的可维护性和可扩展性。

**（2）模块化设计原则**
系统按业务功能划分为若干高内聚、低耦合的模块。每个模块独立开发、独立测试、独立部署，模块之间通过定义良好的API进行交互。模块化设计使得系统可以分阶段实施，也便于后续针对单个模块进行功能增强或技术重构，而不会影响整体系统稳定性。

**（3）开闭原则**
系统架构对扩展开放、对修改封闭。新增功能时，尽量通过增加新的模块或组件来实现，而不是修改现有核心代码。这一原则通过抽象接口、依赖注入、事件驱动等机制加以保障，确保系统核心框架的稳定性。

**（4）安全性优先原则**
安全设计贯穿架构的各个层面，从网络边界防护、应用层身份认证、数据传输加密、数据存储加密，到操作审计、备份恢复，形成纵深防御体系。安全不是事后补丁，而是架构设计的首要考虑因素。

**（5）性能与可扩展性并重原则**
架构设计充分考虑企业未来3-5年的业务发展需求，在硬件资源、并发处理能力、数据存储容量等方面预留充足的扩展空间。通过负载均衡、读写分离、缓存机制、异步处理等技术手段，确保系统在高负载下仍能保持良好的响应性能。

**（6）标准化与规范化原则**
系统遵循业界通用的技术标准和编码规范，包括HTTP/HTTPS协议、RESTful API设计规范、JSON数据交换格式、SQL编码规范、PHP PSR编码标准等。标准化设计降低了系统的学习和维护成本，也便于与第三方系统进行集成。

### 1.2 总体架构图（文字描述）

本CAPP系统总体架构采用经典的B/S（浏览器/服务器）多层架构，自上而下可分为六个层次，同时横向贯穿安全体系、监控体系和集成体系。以下通过文字详细描述总体架构的组成与交互关系：

**第一层：客户端接入层（Client Layer）**
位于架构最顶端，是用户与系统交互的入口。包括三类客户端：
- **PC浏览器端**：工艺工程师、管理人员主要通过Chrome、Edge等现代浏览器访问系统Web应用，进行工艺文件编制、审批、查询等复杂操作。
- **移动端轻应用**：车间班组长、现场工艺员通过企业微信内置浏览器访问移动端适配页面，进行任务查看、现场报工、问题反馈等轻量级操作。
- **外部系统客户端**：PDM/PLM系统、ERP系统、MES系统、质量管理系统等外部系统通过标准API接口与CAPP系统进行数据交换，属于机器客户端。

客户端通过企业内网或VPN接入，所有请求首先经过网络边界的安全防护设备（防火墙、WAF），然后到达负载均衡层。

**第二层：负载均衡与网关层（Load Balancing & Gateway Layer）**
该层是系统流量的统一入口和调度中心，主要包括：
- **负载均衡器（Nginx）**：采用反向代理模式，将来自客户端的HTTP/HTTPS请求按照轮询或权重策略分发到多台应用服务器。同时承担静态资源（图片、CSS、JS文件）的直接 serving 职责，减轻应用服务器压力。
- **API网关**：对外部系统调用进行统一接入管理，负责请求鉴权、流量限制、协议转换、日志记录、异常熔断等。API网关将外部请求路由到对应的后端服务模块。
- **SSL/TLS终止**：HTTPS加密通信在负载均衡层进行解密（SSL Offloading），后续内网通信可根据安全策略选择明文或加密传输，优化应用服务器的计算资源。

**第三层：应用服务层（Application Service Layer）**
该层是系统的核心业务处理层，由多台运行PHP原生应用的应用服务器组成Web服务器集群。每台服务器部署完全相同的PHP应用代码，通过Nginx+PHP-FPM（FastCGI Process Manager）运行环境处理动态请求。

应用服务层内部按功能划分为多个业务模块，每个模块由独立的PHP代码包实现，共享公共基础框架和数据库连接池。主要业务模块包括：工艺文件管理模块、工艺路线设计模块、工艺BOM管理模块、工艺定额管理模块、工艺资源管理模块、工艺变更管理模块、质量工艺控制模块、生产任务管理模块、报表统计模块、系统管理模块等。

应用服务层通过数据访问层与数据库交互，通过服务集成层与外部系统交互，通过缓存层加速数据读取。

**第四层：数据访问与缓存层（Data Access & Cache Layer）**
该层是应用服务层与数据存储层之间的桥梁，负责数据的高效访问和临时存储：
- **数据访问组件**：封装所有数据库操作，提供统一的CRUD接口、事务管理、连接池管理、SQL注入防护。业务逻辑层不直接编写SQL语句，而是通过数据访问组件调用存储过程或参数化查询。
- **缓存服务（Redis）**：部署独立的Redis缓存服务器集群，存储会话信息（Session）、热点数据（如工艺资源字典、用户权限缓存）、频繁查询结果（如工艺文件列表缓存）。通过缓存机制将数据库读压力降低60%以上。
- **消息队列（Redis List/Stream）**：利用Redis实现轻量级消息队列，用于处理异步任务（如报表生成、批量数据导入、邮件/企业微信通知发送），避免阻塞主业务请求。

**第五层：数据存储层（Data Storage Layer）**
该层负责系统全部数据的持久化存储，包括：
- **主数据库（MySQL Master）**：采用MySQL 8.0作为主数据库，存储工艺路线、工艺文件、BOM、定额、资源、用户权限、审批流程等全部业务数据。数据库采用InnoDB存储引擎，支持事务、行级锁、外键约束。
- **从数据库（MySQL Slave）**：通过主从复制机制实时同步主库数据，承担只读查询请求（如报表统计、历史数据查询），实现读写分离，分担主库压力。
- **文件存储服务器**：采用独立的文件服务器（或NAS网络存储）存储工艺文件附件、CAD图纸、工艺图片、质量记录扫描件等非结构化数据。文件元数据（文件名、路径、大小、上传人、上传时间）存储在MySQL中，实际文件存储在文件系统中，支持按日期和类型分目录存储。
- **备份存储**：通过定时任务将数据库备份和文件备份写入独立的备份服务器或磁带库，确保灾难恢复能力。

**第六层：外部系统集成层（External System Integration Layer）**
该层位于架构底部，代表CAPP系统需要对接的企业已有信息系统：
- **PDM/PLM系统**：提供设计BOM、图纸、技术规范的导入接口。
- **ERP系统**：接收工艺BOM、工艺定额、工艺路线数据，反馈生产订单、库存信息。
- **MES系统**：下发工艺指令和作业计划，接收生产执行数据。
- **质量管理系统**：传递检验工艺、质量记录，接收不合格品信息。
- **企业微信/钉钉**：推送审批通知、任务提醒，支持移动端单点登录。
- **LDAP/AD域控**：提供统一身份认证服务。

**贯穿全架构的支撑体系：**
- **安全体系**：包括网络防火墙、Web应用防火墙（WAF）、入侵检测系统（IDS）、数据加密、访问控制、操作审计、漏洞扫描等，形成从网络层到应用层再到数据层的纵深防御。
- **监控运维体系**：包括服务器性能监控（CPU、内存、磁盘、网络）、应用性能监控（APM，追踪接口响应时间、SQL执行时间、错误率）、日志集中收集与分析（ELK Stack：Elasticsearch + Logstash + Kibana）、告警通知（邮件、短信、企业微信）。
- **持续集成/持续部署（CI/CD）体系**：包括代码版本管理（Git）、自动化构建、自动化测试、自动化部署流水线，确保代码变更可以快速、安全地发布到生产环境。

### 1.3 架构层次关系

各架构层次之间的调用关系遵循严格的单向依赖原则：

- **客户端接入层** → 调用 → **负载均衡与网关层**（通过HTTP/HTTPS协议）
- **负载均衡与网关层** → 分发 → **应用服务层**（通过HTTP/FastCGI协议）
- **应用服务层** → 调用 → **数据访问与缓存层**（通过PHP函数调用、Redis协议）
- **数据访问与缓存层** → 调用 → **数据存储层**（通过MySQL协议、文件系统IO）
- **应用服务层** ↔ 交互 ↔ **外部系统集成层**（通过REST API、WebService、消息队列）

禁止跨层调用，例如表现层不允许直接访问数据库，必须通过业务逻辑层和数据访问层进行中转。这种严格的层次隔离确保了架构的清晰性和可维护性。

### 2.2 表现层（Presentation Layer）

表现层负责用户界面的呈现和用户交互的处理，是系统与用户直接对话的窗口。本系统表现层采用前后端分离与服务器端渲染相结合的混合模式：

**（1）后台管理界面（PC端）**
- 采用服务器端渲染（SSR）模式，PHP原生输出HTML页面。每个页面由PHP控制器加载对应的视图模板文件（.php或.html模板），将后端数据嵌入页面后返回给浏览器。
- 前端UI组件库选用Layui或自研组件库，提供表格、表单、树形控件、下拉选择、日期选择、文件上传、富文本编辑等常用组件，风格统一、操作便捷。
- 页面布局采用经典的左侧导航菜单 + 右侧内容区域模式，顶部显示用户信息、消息通知、系统设置入口。支持标签页多开，方便工艺人员同时处理多个工艺文件。
- 工艺文件在线编辑页面集成富文本编辑器（如UEditor或自研表格编辑器），支持工艺卡片表格的在线编辑、单元格合并、公式计算、图片插入、CAD图纸预览等功能。
- 报表统计页面集成ECharts图表库，支持折线图、柱状图、饼图、雷达图、甘特图、漏斗图等多种图表类型，数据可下钻、可联动。

**（2）移动端轻应用**
- 针对车间现场使用场景，开发适配手机浏览器的H5轻应用页面。
- 采用响应式布局设计，确保在手机屏幕上的良好显示效果和触控操作体验。
- 核心功能包括：任务看板、扫码报工、现场拍照上传、语音录入、审批待办处理、消息通知查看。
- 移动端通过企业微信内置浏览器访问，利用企业微信JS-SDK实现扫码、拍照、定位、分享等原生能力。

**（3）前端技术规范**
- HTML页面采用语义化标签，确保结构清晰，便于SEO和维护。
- CSS采用模块化命名规范（如BEM命名法），避免样式冲突。使用CSS预处理器（Sass/Less）提高样式开发效率。
- JavaScript采用原生ES6+语法编写，避免过度依赖大型前端框架（如React/Vue），降低系统复杂度和学习成本。关键交互逻辑封装为独立的JS模块，通过原生模块化（ES Modules）或立即执行函数（IIFE）组织代码。
- 前端与后端通过AJAX（XMLHttpRequest/Fetch API）进行异步数据交互，数据格式统一采用JSON。所有AJAX请求统一封装，自动处理加载状态、错误提示、Token携带、超时重试等通用逻辑。

### 2.3 业务逻辑层（Business Logic Layer）

业务逻辑层是系统的核心，负责处理全部业务规则、业务流程和业务计算。本系统采用PHP原生开发，不依赖任何第三方Web框架（如Laravel、ThinkPHP、Symfony等），而是基于企业自身业务特点，构建轻量级、高度定制化的基础框架。

**（1）基础框架设计**
- **入口文件统一控制**：所有请求通过单一入口文件（index.php）进入应用，由入口文件完成环境初始化、配置加载、自动加载注册、请求路由分发。
- **自动加载机制**：遵循PSR-4自动加载规范，通过spl_autoload_register实现类和接口的按需加载。项目代码按命名空间组织，如App\Controller、App\Service、App\Model、App\Dao等。
- **配置管理**：系统配置（数据库连接、缓存连接、邮件服务器、企业微信参数等）采用PHP数组文件存储，按环境（开发dev、测试test、生产prod）分离。配置加载后存入内存，避免重复读取文件。
- **错误与异常处理**：注册全局错误处理函数和异常捕获机制，将运行时错误、未捕获异常统一转换为友好的错误页面或JSON错误响应。生产环境隐藏详细错误信息，记录到日志系统。
- **请求生命周期管理**：每个HTTP请求的生命周期包括：请求接收 → 路由解析 → 中间件过滤（身份认证、权限检查、请求日志） → 控制器执行 → 服务层业务处理 → 数据访问层交互 → 响应封装 → 输出返回。生命周期中的每个阶段都可扩展和拦截。

**（2）路由与控制器**
- **路由机制**：采用简单高效的路由表模式，将URL路径映射到对应的控制器类和方法。支持RESTful风格路由和自定义路由规则。路由配置集中管理，便于权限控制和接口文档生成。
- **控制器层（Controller）**：控制器负责接收请求参数、调用服务层、返回响应数据。控制器本身不包含业务逻辑，只负责参数校验、请求转发、视图选择。每个控制器对应一个功能模块的页面或API接口集合。
- **中间件（Middleware）**：在请求到达控制器之前，通过中间件链进行预处理。系统内置中间件包括：会话启动中间件、身份认证中间件、权限检查中间件、请求日志中间件、CSRF防护中间件、输入过滤中间件等。中间件支持全局启用和按路由单独配置。

**（3）服务层（Service）**
- 服务层封装具体的业务逻辑，是系统的"大脑"。每个业务模块对应一个或多个服务类，如ProcessRouteService（工艺路线服务）、ProcessDocService（工艺文件服务）、BomService（BOM服务）等。
- 服务层遵循单一职责原则，每个服务类只负责一类业务逻辑。服务类之间通过依赖注入获取所需的其他服务或数据访问对象，避免直接实例化导致的耦合。
- 复杂业务流程（如工艺变更审批流程）通过流程引擎服务统一调度，流程引擎负责解析流程定义、驱动流程状态流转、触发节点事件、记录流程历史。
- 业务规则校验集中在服务层完成，如工艺路线中工序顺序的合法性检查、工艺定额数值范围的校验、工艺文件必填字段的检查等。

**（4）事件驱动机制**
- 系统内置轻量级事件总线（Event Bus），支持业务事件的发布与订阅。当关键业务操作发生时（如工艺文件发布、工艺变更审批通过、生产任务下达），触发相应事件，由事件监听器执行后续动作（如发送通知、更新缓存、记录日志、同步外部系统）。
- 事件机制实现了业务主流程与附属操作的解耦，主流程无需等待通知发送完成即可返回响应，提升系统响应速度。附属操作通过异步事件或消息队列延后执行。

### 2.4 数据访问层（Data Access Layer）

数据访问层负责所有与数据库的交互操作，为业务逻辑层提供统一、安全、高效的数据访问接口。该层的核心目标是隔离业务逻辑与数据库实现细节，防止SQL注入，优化数据库性能。

**（1）数据库连接管理**
- 采用PDO（PHP Data Objects）扩展连接MySQL数据库，PDO提供统一的数据库访问接口，支持预处理语句，从根本上杜绝SQL注入风险。
- 实现数据库连接池管理（通过持久连接或自定义连接池），避免每次请求都创建和销毁数据库连接带来的性能开销。连接池配置最大连接数、连接超时时间、空闲回收策略。
- 支持读写分离：写操作（INSERT、UPDATE、DELETE）自动路由到主库，读操作（SELECT）根据负载情况路由到从库。读写分离对业务层透明，由数据访问层自动处理。

**（2）数据访问对象（DAO）**
- 每个数据库表对应一个DAO类（如ProcessRouteDao、ProcessDocDao、BomDao），DAO类封装对该表的所有CRUD操作。
- DAO类只包含纯粹的数据库操作逻辑，不包含任何业务规则。业务逻辑层通过调用DAO方法完成数据持久化。
- DAO方法采用参数化查询（Prepared Statements），所有用户输入都作为绑定参数传入，禁止字符串拼接SQL语句。
- 提供通用基础DAO类（BaseDao），封装常用的分页查询、批量插入、批量更新、软删除、乐观锁等方法，各业务DAO继承基础DAO复用通用能力。

**（3）事务管理**
- 数据访问层提供统一的事务管理接口，支持编程式事务和声明式事务（通过注解或配置）。
- 事务边界由业务逻辑层控制，一个业务操作（如工艺变更审批通过并更新多个相关表）作为一个原子事务，确保数据一致性。
- 支持事务嵌套（Savepoint），在复杂业务流程中可部分回滚。
- 事务超时和死锁检测机制，避免长时间占用数据库连接。

**（4）查询构建器（Query Builder）**
- 提供轻量级查询构建器，以链式调用的方式构建复杂SQL查询，同时保持参数化查询的安全性。
- 查询构建器支持SELECT字段选择、WHERE条件组合（AND/OR）、JOIN关联、GROUP BY分组、HAVING过滤、ORDER BY排序、LIMIT分页等完整SQL语法。
- 查询构建器自动处理表前缀、字段转义、SQL方言差异，便于未来数据库迁移。

### 2.5 数据存储层（Data Storage Layer）

数据存储层负责系统全部数据的持久化保存，包括结构化业务数据、非结构化文件数据、缓存数据和日志数据。

**（1）MySQL数据库设计**
- 采用MySQL 8.0 Community Edition作为核心数据库，利用其高性能、高可靠、丰富功能特性支撑企业级应用。
- 数据库采用UTF-8mb4字符集，支持中文、特殊符号和Emoji字符存储。
- 表设计遵循第三范式（3NF），减少数据冗余，同时针对高频查询场景适当反范式设计，增加冗余字段或汇总表，以空间换时间。
- 所有表必须包含主键（优先使用自增整数ID或雪花算法生成的分布式ID），包含创建时间、更新时间、创建人、更新人等审计字段。
- 外键约束在数据库层面定义，确保参照完整性。同时应用层也进行关联校验，形成双重保障。
- 索引设计遵循最左前缀原则，针对WHERE条件、JOIN关联、ORDER BY排序字段建立合适的单列索引或组合索引。定期分析慢查询日志，优化索引策略。

**（2）文件存储设计**
- 工艺文件附件、CAD图纸（DWG/DXF/PDF）、工艺图片、质量记录扫描件（PDF/JPG）等非结构化数据存储在独立文件服务器或NAS网络存储中。
- 文件存储采用分级目录结构：/storage/yyyy/mm/dd/，按上传日期分目录，避免单目录文件数量过多导致文件系统性能下降。
- 文件命名采用UUID（通用唯一识别码）+原始扩展名，避免文件名冲突和特殊字符问题。原始文件名作为元数据存储在数据库中。
- 文件上传限制类型（白名单机制）、限制大小（单文件最大50MB），上传后进行病毒扫描（集成ClamAV或调用杀毒软件接口）。
- 文件访问通过PHP代理控制，验证用户权限后才允许下载，防止未授权访问。静态图片、CSS、JS等公共资源可直接通过Nginx访问。

**（3）缓存存储设计**
- Redis部署为独立服务，与应用服务器分离，避免资源争抢。
- 缓存数据分类：
  - **会话缓存（Session）**：用户登录会话信息存储在Redis中，支持多应用服务器共享会话，实现无状态应用服务器部署。
  - **数据字典缓存**：工艺资源类型、材料牌号、设备型号等变化频率低的数据，全量缓存到Redis，减少数据库查询。
  - **热点数据缓存**：高频访问的工艺文件列表、待办任务数量等，设置合理的过期时间（TTL）。
  - **计算结果缓存**：复杂报表统计结果、工艺定额计算结果等，缓存一定时间避免重复计算。
- 缓存更新策略：数据变更时主动更新或删除对应缓存（Cache Aside模式），确保缓存与数据库最终一致性。
- 缓存穿透、缓存击穿、缓存雪崩防护：对不存在的数据缓存空值、热点数据设置随机过期时间、采用互斥锁防止并发重建缓存。

### 2.6 服务集成层（Service Integration Layer）

服务集成层负责CAPP系统与外部系统的数据交换和业务协同，是系统开放性和生态能力的体现。

**（1）内部服务调用**
- 系统内部模块间通过PHP函数调用或服务容器（Service Container）进行通信，确保高效、类型安全。
- 对于跨模块的复杂业务协作，通过事件总线或消息队列实现异步解耦。

**（2）外部系统接入**
- **RESTful API**：为外部系统提供基于HTTP/JSON的RESTful API接口，遵循统一的接口规范（见第7章）。API接口按模块组织，版本化管理（如/api/v1/process/doc）。
- **WebService**：针对部分遗留系统（如老旧的ERP系统），提供SOAP/XML格式的WebService接口，确保兼容性。
- **数据库直连（受限）**：在严格控制和安全审计的前提下，允许特定外部系统通过只读数据库视图（View）直接查询部分工艺数据，减少接口开发工作量。数据库账号严格限制IP和权限。
- **文件交换**：对于大批量数据交换（如BOM导入），支持通过SFTP服务器交换标准格式文件（Excel、XML），由定时任务自动解析和导入。

**（3）企业微信集成**
- 通过企业微信开放平台API，实现组织架构同步、单点登录、消息推送、移动端审批等功能。
- 企业微信集成采用独立的适配器模块封装，便于未来替换为钉钉或飞书等其他企业IM平台。

### 2.7 公共组件层（Common Components Layer）

公共组件层提供贯穿全系统的通用能力，被表现层、业务逻辑层、数据访问层共同使用。

**（1）日志组件**
- 基于PSR-3日志接口规范，实现多通道日志记录：文件日志（按日期分文件）、数据库日志（关键操作记录）、远程日志（发送到ELK系统）。
- 日志级别：DEBUG（调试）、INFO（信息）、NOTICE（注意）、WARNING（警告）、ERROR（错误）、CRITICAL（严重）、ALERT（警报）、EMERGENCY（紧急）。
- 业务操作日志自动记录：操作人、操作时间、操作类型、操作对象、操作前数据、操作后数据、操作结果、客户端IP、浏览器信息。

**（2）安全组件**
- 输入过滤：对所有用户输入进行XSS过滤、SQL注入防护、HTML标签白名单过滤。
- 密码加密：用户密码采用bcrypt算法哈希存储，成本因子设为10以上，确保密码安全性。
- Token管理：API接口采用JWT（JSON Web Token）或自研Token机制进行身份认证，Token包含用户ID、过期时间、签名，防止篡改。
- 限流防刷：基于Redis实现接口访问频率限制，防止暴力破解、爬虫抓取、DDoS攻击。

**（3）文件组件**
- 封装文件上传、下载、压缩、解压、图片处理（缩略图生成、水印添加）、Office文档转换（Word/Excel转PDF）等常用文件操作。
- 文件上传支持分片上传、断点续传，提升大文件上传可靠性。

**（4）消息组件**
- 统一消息发送接口，支持邮件发送（SMTP协议）、企业微信消息（文本/图文/卡片）、短信发送（集成短信平台API）、系统站内信。
- 消息发送支持同步发送和异步队列发送，非紧急消息通过队列延后处理。

**（5）缓存组件**
- 封装Redis操作，提供字符串、哈希、列表、集合、有序集合等数据结构的便捷操作方法。
- 支持缓存标签（Cache Tag），便于批量清除某一类缓存。

**（6）工具类库**
- 提供字符串处理、数组操作、日期时间计算、数字格式化、编码转换、UUID生成、雪花算法ID生成、Excel读写、PDF生成、二维码生成等常用工具类。

## 3. 部署架构

### 3.1 服务器规划

根据企业当前业务规模和未来3-5年的增长预期，系统部署采用"主备分离、读写分离、应用集群"的部署模式。初期部署规划如下表所示：

| 服务器角色 | 数量 | 硬件配置（单台） | 操作系统 | 部署组件 | 备注 |
|-----------|------|----------------|---------|---------|------|
| 负载均衡服务器 | 2台 | 4核8GB内存，100GB SSD | CentOS 7.9 | Nginx（主备模式，Keepalived实现VIP漂移） | 一台主用，一台备用，确保入口高可用 |
| 应用服务器 | 3台 | 8核16GB内存，200GB SSD | CentOS 7.9 | Nginx + PHP 8.1-FPM + 应用代码 | 三台组成集群，可横向扩展 |
| 数据库主服务器 | 1台 | 16核32GB内存，500GB SSD（RAID 10） | CentOS 7.9 | MySQL 8.0（Master） | 承担写操作和部分读操作 |
| 数据库从服务器 | 2台 | 16核32GB内存，500GB SSD（RAID 10） | CentOS 7.9 | MySQL 8.0（Slave） | 承担读操作，可扩展更多从库 |
| 缓存服务器 | 2台 | 4核16GB内存，100GB SSD | CentOS 7.9 | Redis 6.2（主从+哨兵模式） | 一主一从，哨兵监控自动故障转移 |

| 备份服务器 | 1台 | 4核8GB内存，8TB HDD（RAID 5） | CentOS 7.9 | 备份脚本、备份数据存储 | 独立网络段，与生产环境隔离 |

**服务器部署原则：**
- 生产环境与开发测试环境物理隔离，禁止开发测试直接访问生产数据。
- 数据库服务器、缓存服务器、文件存储服务器部署在独立网段，通过防火墙规则限制访问来源，仅允许应用服务器IP访问。
- 所有服务器通过企业内网连接，不直接暴露公网IP。远程运维通过VPN或堡垒机（Jump Server）进行，所有操作留痕审计。

### 3.2 网络拓扑结构

系统网络拓扑采用分层分区设计，分为DMZ区（非军事化区）、应用区、数据区、管理区四个安全区域：

**（1）DMZ区（Demilitarized Zone）**
- 部署负载均衡服务器（Nginx），作为系统的唯一外部入口。
- 负载均衡服务器配置公网IP（或NAT映射），对外提供HTTP/HTTPS服务。
- DMZ区与内网之间通过防火墙严格限制端口和IP访问，仅允许HTTP/HTTPS流量进入应用区。

**（2）应用区（Application Zone）**
- 部署应用服务器集群（PHP-FPM）。
- 应用区服务器只开放80/443端口供负载均衡访问，开放22端口（SSH）供堡垒机运维访问。
- 应用区服务器可访问数据区的数据库、缓存、文件存储，但数据区服务器不可主动访问应用区。

**（3）数据区（Data Zone）**
- 部署数据库服务器（MySQL主从）、缓存服务器（Redis）、文件存储服务器（NAS）。
- 数据区是系统的核心资产区域，安全级别最高。仅开放数据库端口（3306）、Redis端口（6379）、NFS端口（2049）给应用区特定IP。
- 数据库区与管理区之间开放备份传输端口，用于定时备份数据到备份服务器。

**（4）管理区（Management Zone）**
- 部署堡垒机、监控服务器（ELK+Prometheus）、备份服务器、VPN网关。
- 管理区仅供信息中心运维人员通过VPN或堡垒机访问，所有运维操作通过堡垒机代理，全程录屏审计。
- 管理区可访问所有区域的服务器，但其他区域不可访问管理区。

### 3.3 负载均衡策略

负载均衡是保障系统高可用和高性能的关键机制，本系统采用多层负载均衡策略：

**（1）入口层负载均衡（Nginx反向代理）**
- 两台Nginx负载均衡器采用主备模式，通过Keepalived实现虚拟IP（VIP）漂移。主服务器故障时，备用服务器在3秒内接管VIP，确保服务不中断。
- 负载均衡算法采用加权轮询（Weighted Round Robin），根据应用服务器的性能配置权重。默认三台应用服务器权重相同，若某台服务器性能较弱，可降低其权重。
- 健康检查机制：Nginx每5秒对后端应用服务器发起健康检查请求（如访问/health接口），若连续3次检查失败，则将该服务器从可用列表中移除，待恢复后自动加入。

**（2）应用层负载均衡（PHP-FPM进程管理）**
- 每台应用服务器上的PHP-FPM配置动态进程池（pm = dynamic），根据请求负载自动调整工作进程数量。
- 配置参数：pm.max_children = 50（最大进程数），pm.start_servers = 10（初始进程数），pm.min_spare_servers = 5（最小空闲进程），pm.max_spare_servers = 20（最大空闲进程），pm.max_requests = 1000（每个进程处理1000个请求后重启，防止内存泄漏）。

**（3）数据库读写分离负载均衡**
- 写操作（INSERT/UPDATE/DELETE）固定路由到MySQL主库。
- 读操作（SELECT）通过数据访问层的路由策略分发到两台从库。路由策略支持轮询、权重、最小连接数等算法。
- 从库延迟检测：若某从库复制延迟超过5秒，临时将该从库读流量切换到其他从库或主库，避免读取到过期数据。

### 3.4 文件存储方案

工艺文件附件、CAD图纸、质量记录扫描件等非结构化数据量巨大，需要专门的文件存储方案：

**（1）存储架构**
- 采用独立文件服务器（NAS）集中存储，通过NFS（Network File System）协议挂载到各应用服务器，确保多台应用服务器访问同一文件池。
- 文件服务器配置RAID 5磁盘阵列，提供数据冗余保护。单块硬盘故障不影响数据可用性，更换硬盘后自动重建。
- 文件服务器定期快照备份，保留最近7天的快照，支持快速恢复到某个时间点。

**（2）目录组织**
```
/storage/
  ├── capp/
  │   ├── process_doc/          # 工艺文件附件
  │   │   ├── 2024/
  │   │   │   ├── 01/
  │   │   │   │   ├── 15/       # 按日期分目录
  │   │   │   │   │   ├── a1b2c3d4.pdf
  │   │   │   │   │   └── e5f6g7h8.dwg
  │   │   │   │   └── ...
  │   │   │   └── ...
  │   │   └── ...
  │   ├── cad_drawing/          # CAD图纸
  │   ├── quality_record/       # 质量记录扫描件
  │   ├── temp/                 # 临时文件（定时清理）
  │   └── backup/               # 文件备份
  └── ...
```

**（3）文件管理策略**
- 文件上传时，应用服务器接收文件后，通过NFS写入文件服务器。文件元数据（文件名、路径、大小、MD5校验值、上传人、上传时间）存入MySQL数据库。
- 文件下载时，应用服务器验证用户权限后，通过NFS读取文件内容，以流式方式返回给客户端。大文件支持断点续传。
- 对于频繁访问的公共文件（如系统Logo、CSS/JS文件），在Nginx负载均衡层配置静态资源缓存，直接由Nginx返回，不经过PHP处理。
- 文件定期清理：临时文件超过7天自动删除；已删除文件的物理文件在数据库标记删除后30天彻底清理（软删除机制，防止误删）。

**（4）容量规划**
- 初期配置4TB存储空间，预计可满足前2年使用。
- 监控存储容量使用率，达到80%时预警，达到90%时启动扩容（增加硬盘或更换更大容量NAS）。
- 历史文件（超过3年）可迁移到低成本的冷存储（如对象存储或磁带库），在线数据库保留元数据和访问链接。

### 3.5 缓存策略

缓存是提升系统性能、降低数据库压力的核心手段。本系统采用多级缓存架构：

**（1）客户端缓存（Browser Cache）**
- 静态资源（CSS、JS、图片、字体）通过Nginx配置Cache-Control响应头，允许浏览器缓存30天。文件内容变更时，通过文件名加哈希值（如app.a3f2b1c.js）强制刷新。
- 部分不经常变化的API响应（如数据字典列表）也设置适当的客户端缓存时间（如1小时），减少重复请求。

**（2）CDN缓存（可选）**
- 若企业有CDN节点或计划部署，可将静态资源部署到CDN，用户就近访问，降低服务器带宽压力和访问延迟。

**（3）应用服务器缓存（Opcode Cache）**
- PHP代码通过OPcache加速，将编译后的PHP字节码缓存到内存，避免每次请求都重新编译。OPcache配置合理的内存大小（如256MB）和缓存有效期。

**（4）分布式缓存（Redis）**
- **会话缓存**：用户登录会话存储在Redis，键名为session:{session_id}，过期时间8小时。用户主动退出或长时间无操作后自动清除。多应用服务器共享Redis会话，实现无状态部署和负载均衡下的会话一致性。
- **数据字典缓存**：材料牌号、设备型号、工序类型、检验项目等基础数据，全量加载到Redis哈希表，设置过期时间24小时。数据变更时主动刷新缓存。
- **热点数据缓存**：
  - 用户权限缓存：用户登录时计算其全部菜单权限、按钮权限、数据权限，缓存到Redis，过期时间2小时。权限变更时主动刷新。
  - 工艺文件列表缓存：首页待办工艺文件、最近浏览工艺文件等，缓存5分钟。
  - 报表统计缓存：日报、周报、月报等周期性报表结果，缓存1小时，避免重复复杂计算。
- **缓存更新策略**：采用Cache Aside模式（旁路缓存），读数据时先查缓存，未命中再查数据库并写入缓存；写数据时先更新数据库，再删除或更新缓存。确保数据库是数据的唯一真实来源。
- **缓存穿透防护**：对于数据库中不存在的数据（如恶意查询不存在的工艺编号），缓存空值（设置较短过期时间，如5分钟），避免重复查询数据库。
- **缓存击穿防护**：对于极热点的数据（如系统公告），使用互斥锁（Redis SETNX）防止缓存失效瞬间大量并发请求同时访问数据库。
- **缓存雪崩防护**：大量缓存同时过期可能导致数据库压力骤增。解决方案：为不同数据设置随机过期时间（基础过期时间±10%随机偏移）；热点数据永不过期，通过后台定时任务异步更新。

**（5）数据库查询缓存（Query Cache，MySQL 8.0已移除，改用应用层缓存）**
- MySQL 8.0已移除内置查询缓存，系统通过应用层缓存和Redis缓存替代。
- 对于极复杂的统计查询，使用MySQL物化视图或汇总表，定时任务刷新，避免实时计算。

### 3.6 容灾与高可用设计

**（1）应用层高可用**
- 三台应用服务器组成集群，任意一台故障时，Nginx健康检查自动将其剔除，剩余两台继续提供服务，整体容量下降33%但不中断服务。
- 应用服务器无状态设计，会话数据存储在Redis，本地不保存业务数据，故障服务器修复后可立即重新加入集群。

**（2）数据库高可用**
- MySQL主从复制：主库实时同步数据到两台从库。主库故障时，通过人工或自动化脚本将其中一台从库提升为主库（Failover），另一台从库重新指向新主库。RTO（恢复时间目标）控制在30分钟内，RPO（恢复点目标）接近0（取决于复制延迟，通常秒级）。
- 未来可升级为MySQL Group Replication或MGR半同步复制，实现自动故障转移，进一步降低RTO。

**（3）缓存高可用**
- Redis采用一主一从+哨兵（Sentinel）模式。主库故障时，哨兵自动在10秒内完成故障检测和主从切换，应用层通过哨兵获取新主库地址，实现自动故障转移。

**（4）负载均衡高可用**
- 两台Nginx通过Keepalived共享虚拟IP，主Nginx故障时，备用Nginx在3秒内接管VIP，用户无感知。

**（5）灾难恢复**
- 备份服务器每日凌晨2:00执行全量数据库备份（Percona XtraBackup物理备份），每6小时执行增量备份。备份文件保留30天。
- 文件存储每日执行增量备份（rsync），每周执行全量备份。备份数据存储在独立备份服务器，与生产环境物理隔离。
- 定期（每季度）进行灾难恢复演练，模拟主库崩溃、应用服务器全部故障等场景，验证备份数据可恢复性和恢复时间。

## 4. 安全架构

### 4.1 认证与授权体系

**（1）用户身份认证**
- **多因素认证**：系统登录采用"用户名+密码+验证码"的三因素认证。验证码为图形验证码或短信验证码，防止暴力破解和自动化攻击。
- **密码策略**：密码最小长度8位，必须包含大写字母、小写字母、数字、特殊字符中的至少三种。密码有效期90天，到期强制修改。历史密码不可复用（禁止最近5次使用过的密码）。
- **登录安全**：连续5次登录失败锁定账号30分钟。登录时记录客户端IP、浏览器指纹、登录时间，异常登录（如异地登录、非常用设备）触发二次验证或告警通知。
- **单点登录（SSO）**：集成企业微信扫码登录和LDAP/AD域账号登录，用户可使用企业统一身份认证访问CAPP系统，减少密码记忆负担，提升安全性。
- **会话管理**：用户登录后生成Session ID（存储在Cookie，HttpOnly和Secure标志），会话有效期8小时。用户长时间无操作（30分钟）自动失效。用户主动退出或管理员强制下线时，立即销毁Redis中的会话缓存。
- **API认证**：外部系统调用API时，采用AppKey+AppSecret签名认证或JWT Token认证。每个API调用都验证签名有效性和Token未过期。

**（2）权限授权模型**
- 采用RBAC（基于角色的访问控制）+ ACL（访问控制列表）的混合模型。
- **功能权限**：通过角色分配菜单访问权、页面访问权、按钮操作权、字段查看/编辑权。系统内置11个标准角色，支持自定义角色。
- **数据权限**：在功能权限基础上，通过数据规则控制用户可见的数据范围。数据规则包括：全部数据、本部门及下属部门数据、本部门数据、本人数据、指定项目数据、指定产品类型数据等。
- **审批权限**：审批流程中的节点权限与角色绑定，也可指定具体人员。支持代理人设置（如工艺工程师出差时，指定同事代理审批）。

### 4.2 数据安全保护

**（1）数据存储加密**
- **敏感字段加密**：用户密码采用bcrypt哈希存储；数据库连接密码、API密钥等配置信息采用AES-256加密存储在配置文件中，密钥通过环境变量或硬件加密机管理。
- **文件加密存储**：对于特别敏感的质量记录、工艺评定报告等文件，上传时进行AES加密存储，下载时解密。加密密钥由系统统一管理，与文件元数据分离存储。
- **数据库透明加密（TDE，可选）**：若企业安全要求极高，可启用MySQL TDE功能，对数据文件和日志文件进行透明加密，防止物理文件被盗取导致数据泄露。

**（2）数据访问控制**
- 数据库账号严格按最小权限原则分配：应用账号只拥有业务表的读写权限，无DROP、TRUNCATE等高危权限；备份账号只拥有SELECT和LOCK TABLES权限；管理账号（DBA）独立保管，不嵌入应用程序。
- 数据库访问限制来源IP，仅允许应用服务器和DBA运维终端连接。
- 生产数据库禁止直接修改数据，所有数据变更必须通过应用程序接口或经审批的DBA脚本执行，并记录操作日志。

**（3）数据脱敏**
- 在测试环境使用生产数据时，必须对敏感字段（如员工身份证号、手机号、材料供应商价格信息）进行脱敏处理，防止测试数据泄露。
- 报表导出和API返回时，根据用户角色对敏感字段进行脱敏显示（如手机号显示为138****8888）。

### 4.3 通信安全

**（1）传输层加密**
- 所有客户端与服务器之间的通信强制使用HTTPS协议，TLS版本不低于1.2。禁用不安全的SSLv2、SSLv3、TLS 1.0、TLS 1.1。
- HTTPS证书采用企业级CA签发的通配符证书或SAN证书，支持企业内部域名。证书到期前30天自动预警，及时续期。
- 负载均衡层（Nginx）负责SSL/TLS终止（SSL Offloading），内网应用服务器与负载均衡器之间可采用HTTP通信，降低应用服务器加密计算开销。若内网安全要求严格，也可配置内网HTTPS。

**（2）API通信安全**
- 外部系统API调用必须通过HTTPS。
- API请求采用时间戳+随机数+签名的防重放机制：请求头包含Timestamp（时间戳，有效期5分钟）、Nonce（随机字符串，单次有效）、Signature（签名，基于AppSecret对请求参数进行HMAC-SHA256计算）。服务端验证时间戳未过期、随机数未重复使用、签名正确。
- API调用频率限制：每个AppKey每分钟最多调用1000次，超出限制返回429状态码。防止外部系统异常调用或恶意攻击导致系统过载。

### 4.4 审计日志体系

审计日志是安全事件追溯、合规检查、责任认定的重要依据。本系统建立全面的审计日志体系：

**（1）日志分类**
- **操作日志**：记录用户在系统中的所有业务操作，包括登录、退出、新增、修改、删除、查询、导出、打印、审批等。记录要素：操作时间、操作人、操作类型、操作对象（表名+记录ID）、操作前数据快照、操作后数据快照、操作结果（成功/失败）、失败原因、客户端IP、浏览器User-Agent、会话ID。
- **登录日志**：专门记录用户登录行为，包括登录时间、登录账号、登录方式（密码/扫码/域账号）、登录结果（成功/失败）、失败原因、客户端IP、地理位置（通过IP解析）、设备信息。
- **系统日志**：记录系统运行状态、错误异常、性能告警、定时任务执行、数据备份结果、接口调用情况等。
- **安全日志**：记录安全相关事件，如密码修改、权限变更、账号锁定/解锁、异常访问拦截、SQL注入尝试、XSS攻击拦截、文件上传异常等。

**（2）日志存储与分析**
- 操作日志和登录日志同时写入MySQL数据库（便于业务查询）和ELK日志系统（便于大数据分析）。
- MySQL中的日志表按月份分表（如log_operation_202401），避免单表数据量过大。超过1年的日志表迁移到归档库。
- ELK系统（Elasticsearch + Logstash + Kibana）集中收集全系统日志，支持全文检索、多维度过滤、实时告警、可视化仪表盘。
- 关键安全日志（如登录失败、权限越权）实时推送企业微信告警给信息中心安全管理员。

**（3）日志保护**
- 日志数据属于敏感数据，只允许系统管理员和安全审计人员查询。
- 日志数据禁止修改和删除，确保审计追踪的完整性。数据库日志表只授予INSERT和SELECT权限，不授予UPDATE和DELETE权限。
- 日志定期（每月）导出为不可篡改格式（如WORM存储或区块链存证，可选），长期保存以满足法规要求（特种设备相关记录需保存至产品报废后至少5年）。

### 4.5 备份与恢复策略

**（1）数据库备份**
- **全量物理备份**：每日凌晨2:00使用Percona XtraBackup执行MySQL热备份，备份文件压缩后传输到备份服务器。保留最近30天全量备份。
- **增量备份**：每6小时（02:00、08:00、14:00、20:00）执行增量备份，基于上次全量或增量备份，只备份变化数据。保留最近7天增量备份。
- **逻辑备份**：每周日凌晨3:00执行mysqldump逻辑备份，导出为SQL文本文件。逻辑备份用于单表恢复、数据迁移、测试环境数据导入。保留最近4周逻辑备份。
- **Binlog归档**：开启MySQL Binlog（二进制日志），记录所有数据变更操作。Binlog实时同步到备份服务器，保留最近30天。Binlog用于精确到秒级的数据恢复（Point-in-Time Recovery）。

**（2）文件备份**
- 文件存储服务器每日凌晨3:00执行增量备份（rsync），每周日凌晨4:00执行全量备份。备份数据存储在备份服务器的独立磁盘阵列。
- 关键工艺文件、焊接工艺评定报告等同时备份到异地容灾中心（如企业分支机构或云存储），防止本地灾难（火灾、水灾）导致数据全部丢失。

**（3）恢复演练**
- 每季度进行一次恢复演练，随机选择某天的备份数据，在测试环境完整恢复数据库和文件，验证备份数据完整性和恢复流程可行性。
- 记录恢复演练结果（恢复时间、数据完整性验证、问题记录），持续优化恢复流程。

**（4）RPO与RTO目标**
- RPO（恢复点目标）：数据库数据丢失不超过6小时（基于增量备份频率），关键数据通过Binlog可实现接近0数据丢失。
- RTO（恢复时间目标）：单点故障（如应用服务器宕机）恢复时间不超过10分钟；数据库主库故障切换时间不超过30分钟；全系统灾难恢复时间不超过4小时。

### 4.6 安全运维管理

**（1）漏洞管理**
- 每月使用漏洞扫描工具（如Nessus、OpenVAS）对服务器、Web应用、数据库进行安全扫描，发现高危漏洞在7个工作日内修复，中危漏洞在30个工作日内修复。
- 关注PHP、MySQL、Nginx、Redis等组件的安全公告，及时升级到安全版本。
- 新功能上线前进行代码安全审计，重点检查SQL注入、XSS、文件上传、权限绕过等常见漏洞。

**（2）入侵检测与防御**
- 部署Web应用防火墙（WAF），拦截SQL注入、XSS、CSRF、路径遍历、恶意爬虫等攻击。
- 部署入侵检测系统（IDS）或入侵防御系统（IPS），监控网络流量中的异常行为。
- 服务器配置 fail2ban，自动封禁暴力破解SSH、MySQL的恶意IP。

**（3）安全审计**
- 每年至少进行一次第三方安全渗透测试，全面评估系统安全性。
- 配合企业信息安全等级保护（等保2.0）测评，确保系统符合三级等保要求（若企业定级为三级）。
- 配合特种设备监管部门的监督检查，提供工艺数据安全管理和审计追踪的相关证明材料。

## 5. 模块划分与依赖关系

### 5.1 模块划分总览

本CAPP系统按业务功能划分为11个一级模块，每个一级模块下包含若干二级子模块。模块划分遵循高内聚、低耦合原则，确保每个模块职责清晰、接口明确。

| 序号 | 一级模块 | 模块代码 | 核心职责 | 二级子模块 |
|-----|---------|---------|---------|-----------|
| 1 | 系统管理 | SYS | 基础配置、用户权限、日志审计 | 组织架构、用户管理、角色权限、数据字典、编码规则、流程配置、系统参数、日志审计、数据备份 |
| 2 | 工艺资源管理 | RES | 工艺基础数据维护 | 设备管理、工装模具管理、刀具量具管理、焊接材料管理、工艺参数库、人员资质管理 |
| 3 | 工艺文件管理 | DOC | 工艺文件全生命周期管理 | 文件分类、模板管理、在线编制、审批流程、版本管理、检索浏览、发放回收 |
| 4 | 工艺路线设计 | RTE | 工艺路线设计与维护 | 路线创建、工序定义、资源分配、路线审批、路线变更、可视化展示 |
| 5 | 工艺BOM管理 | BOM | 制造BOM与定额管理 | 设计BOM导入、工艺BOM转换、材料定额、辅料耗材、BOM版本、BOM查询 |
| 6 | 工艺定额管理 | QTA | 工时与材料定额管理 | 工时定额、材料定额、定额维护、定额版本、定额统计、定额优化 |
| 7 | 工艺变更管理 | CHG | 工艺变更全过程管理 | 变更申请、变更评估、变更审批、变更实施、变更验证、变更追溯 |
| 8 | 质量工艺控制 | QAC | 质量控制工艺管理 | 检验工艺、焊接工艺、热处理工艺、无损检测工艺、压力试验工艺、不合格品处理、质量记录 |
| 9 | 生产任务管理 | TSK | 工艺与生产衔接 | 任务接收、工艺分解、指令下发、进度跟踪、现场服务、完工确认 |
| 10 | 报表与统计分析 | RPT | 数据报表与决策支持 | 工艺文件统计、定额统计、资源统计、质量统计、效率统计、自定义报表 |
| 11 | 外部系统集成 | INT | 系统间数据交换 | PDM/PLM集成、ERP集成、MES集成、质量管理集成、企业微信集成、数据交换平台 |

### 5.2 核心模块详细说明

**（1）系统管理模块（SYS）**
系统管理模块是所有其他模块的基础支撑，提供组织架构、用户账号、角色权限、数据字典、编码规则、审批流程、系统参数、日志审计、数据备份等基础功能。该模块不依赖任何业务模块，但所有业务模块都依赖该模块提供的用户认证、权限校验、数据字典等基础服务。

- **组织架构子模块**：维护企业的部门、车间、班组、岗位层级结构，支持多级组织、组织调整历史记录。组织架构数据被所有业务模块引用，用于数据权限控制和流程审批路由。
- **用户管理子模块**：管理系统用户账号的生命周期，包括创建、启用、禁用、密码重置、密码策略、登录日志。用户数据是权限体系和操作日志的基础。
- **角色权限子模块**：定义角色、分配功能权限和数据权限、管理角色继承关系。权限数据在系统启动时加载到Redis缓存，每次请求时通过中间件校验。
- **数据字典子模块**：管理产品类型、材料牌号、设备类型、工序类型、检验类型、计量单位等基础数据字典。字典数据被多个业务模块共享，变更时触发缓存刷新。
- **编码规则子模块**：配置工艺文件编号、变更单号等的自动生成规则。其他业务模块在创建新记录时调用编码服务获取唯一编号。
- **流程配置子模块**：图形化配置审批流程，定义节点、路由、条件、操作。工艺文件审批、变更审批等流程都依赖此子模块。
- **日志审计子模块**：记录和查询系统操作日志、登录日志、安全日志。所有业务模块通过公共日志组件自动写入日志。

**（2）工艺资源管理模块（RES）**
工艺资源管理模块维护工艺设计所需的全部基础资源数据，为工艺文件编制、工艺路线设计提供数据支撑。

- **设备管理子模块**：管理生产设备台账，包括设备编码、名称、型号、技术参数、能力范围、精度等级、当前状态。工艺路线设计时调用设备查询服务，校验设备可用性。
- **工装模具管理子模块**：管理工装、模具、夹具、胎具台账，包括编号、适用产品、存放位置、使用次数、检定状态、寿命管理。工艺编制时查询所需工装是否存在且可用。
- **刀具量具管理子模块**：管理刀具、量具、检具台账，包括规格型号、适用工序、库存数量、检定周期、检定状态。支持检定到期预警。
- **焊接材料管理子模块**：管理焊条、焊丝、焊剂、保护气体等焊接材料。焊接工艺编制时关联焊材牌号，查询焊材化学成分和力学性能。
- **工艺参数库子模块**：管理各类加工工艺的标准参数范围，如切削速度、进给量、焊接电流、热处理温度等。工艺编制时推荐标准参数。
- **人员资质管理子模块**：管理焊工、无损检测人员、检验人员等的资质证书信息，包括证书编号、证书项目、有效期、发证机构。支持资质到期预警。

**（3）工艺文件管理模块（DOC）**
工艺文件管理模块是CAPP系统的核心模块之一，负责工艺文件的创建、编辑、审批、发布、归档、检索全生命周期管理。

- **文件分类子模块**：定义工艺文件的分类体系，如工艺路线卡、工艺过程卡、工序卡、检验卡、焊接工艺卡、热处理工艺卡、无损检测工艺卡、装配工艺卡、调试工艺卡、涂装工艺卡、包装工艺卡等。
- **模板管理子模块**：提供各类工艺文件的标准模板，支持模板自定义。模板中预定义固定字段、下拉选项、计算公式、自动填充规则。
- **在线编制子模块**：支持在Web页面中在线编制工艺文件，提供富文本编辑、表格编辑、公式插入、图片插入、CAD图纸引用等功能。
- **审批流程子模块**：驱动工艺文件的审批流程，支持多级审批、会签、转办、退回等操作。审批流程依赖系统管理模块的流程引擎。
- **版本管理子模块**：管理工艺文件的版本历史，支持版本对比、版本回滚。版本数据与文件存储关联，每个版本对应一个文件快照。
- **检索浏览子模块**：提供多条件组合检索、全文检索、模糊检索、高级检索。支持在线浏览、打印、导出PDF/Excel。
- **发放回收子模块**：管理工艺文件的发放对象、发放时间、回收状态。工艺变更时自动触发旧版文件回收通知。

**（4）工艺路线设计模块（RTE）**
工艺路线设计模块负责确定产品从原材料到成品的全部加工工序及其顺序，是连接设计与生产的关键桥梁。

- **路线创建子模块**：支持基于设计BOM自动创建工艺路线框架，或从典型工艺库复制相似工艺路线。依赖工艺BOM管理模块的设计BOM数据。
- **工序定义子模块**：支持工序的增删改查、拖拽排序、并行工序设置。工序属性包括工序号、名称、内容、工作中心、设备/工装、工艺参数、工时定额、检验要求等。依赖工艺资源管理模块的设备、工装、参数数据。
- **资源分配子模块**：为每道工序分配所需资源，系统自动校验资源可用性。依赖工艺资源管理模块的资源查询服务。
- **路线审批子模块**：驱动工艺路线的审批流程。审批通过后锁定工艺路线，作为生产排程依据。
- **路线变更子模块**：支持工艺路线的在线变更申请，变更内容高亮显示。变更需审批，通过后更新相关工艺文件和生产任务。依赖工艺变更管理模块的变更流程。
- **可视化展示子模块**：以甘特图、流程图形式展示工艺路线。依赖前端ECharts图表库。

**（5）工艺BOM管理模块（BOM）**
工艺BOM管理模块负责管理制造过程中的物料清单，是成本核算和生产物料准备的基础。

- **设计BOM导入子模块**：从PDM/PLM系统导入设计BOM，或手工创建。支持BOM结构展开、多级BOM浏览、BOM差异对比。依赖外部系统集成模块的PDM接口。
- **工艺BOM转换子模块**：基于设计BOM和工艺路线，自动生成工艺BOM，体现制造过程中的物料流转关系。
- **材料定额子模块**：根据零件尺寸、材料牌号、加工余量、下料排版方案等，自动计算材料消耗定额。依赖工艺资源管理模块的材料数据。
- **辅料耗材子模块**：管理焊接材料、切削液、润滑油、砂轮片、气体等辅料和耗材的消耗定额。
- **BOM版本子模块**：支持工艺BOM的版本管理，与设计BOM版本、工艺路线版本关联。
- **BOM查询子模块**：提供单级BOM、多级BOM、反查BOM等查询功能。提供材料汇总表、外购件清单、标准件清单等报表。

**（6）工艺定额管理模块（QTA）**
工艺定额管理模块负责工时定额、材料定额、能源定额等的制定、维护与统计分析。

- **工时定额子模块**：支持多种工时定额制定方法，提供工时定额计算模型和公式库。依赖工艺路线设计模块的工序数据。
- **材料定额子模块**：支持材料定额的制定、审核、发布。关联材料编码、规格型号、计量单位、单价信息。依赖工艺BOM管理模块的材料定额数据。
- **定额维护子模块**：支持定额数据的批量修改、批量导入、批量导出。定额版本管理记录变更历史。
- **定额统计子模块**：提供定额完成率分析、定额偏差分析、工时利用率分析、材料利用率分析等统计报表。依赖报表与统计分析模块的报表引擎。
- **定额优化子模块**：基于历史生产数据，运用统计分析方法，识别定额不合理之处，提供定额调整建议。

**（7）工艺变更管理模块（CHG）**
工艺变更管理模块负责工艺变更的申请、评估、审批、实施、验证全过程管理。

- **变更申请子模块**：支持在线发起工艺变更申请（ECR），填写变更原因、内容、影响范围、预计实施时间。关联相关工艺文件。
- **变更评估子模块**：系统自动分析变更影响范围，包括受影响的产品、零部件、工艺文件、BOM、生产任务、库存物料等。支持多部门会签评估。依赖工艺文件管理、工艺路线设计、工艺BOM管理模块的数据关联分析。
- **变更审批子模块**：配置变更审批流程，根据变更类型、影响程度自动选择审批路径。依赖系统管理模块的流程引擎。
- **变更实施子模块**：审批通过后，自动更新相关工艺文件、BOM、定额等数据。支持变更实施计划编制、任务分派、进度跟踪。依赖工艺文件管理、工艺路线设计、工艺BOM管理模块的数据更新接口。
- **变更验证子模块**：变更实施后，进行验证确认，记录验证结果。支持变更前后数据对比、效果评估。
- **变更追溯子模块**：完整记录变更全过程信息，支持变更历史查询、变更统计分析。

**（8）质量工艺控制模块（QAC）**
质量工艺控制模块负责管理产品制造过程中的质量控制工艺。

- **检验工艺子模块**：编制进货检验、过程检验、最终检验的检验工艺卡，定义检验项目、方法、设备、抽样方案、判定标准、记录表单。
- **焊接工艺子模块**：编制焊接工艺规程（WPS），关联焊接工艺评定报告（PQR）。管理焊工资质、焊接材料、焊接参数、预热后热要求、焊后热处理要求。依赖工艺资源管理模块的焊材数据和人员资质数据。
- **热处理工艺子模块**：编制热处理工艺卡，定义热处理类型、设备、装炉方式、升温速度、保温温度、保温时间、冷却方式等。支持热处理工艺曲线绘制。
- **无损检测工艺子模块**：编制射线检测、超声检测、磁粉检测、渗透检测等无损检测工艺卡。支持检测工艺与焊接工艺的关联。
- **压力试验工艺子模块**：编制耐压试验、气密性试验工艺卡，定义试验介质、试验压力、保压时间、合格标准、安全措施。
- **不合格品处理子模块**：记录不合格品信息，支持不合格品评审、返工/返修工艺编制、让步接收申请、报废处理等流程。返工/返修工艺编制依赖工艺文件管理模块和工艺路线设计模块。
- **质量记录子模块**：管理材料复验报告、焊接记录、热处理记录、无损检测报告、压力试验报告、外观检查记录等。支持记录与工艺文件的关联、归档、检索。质量记录文件存储依赖文件存储服务。

**（9）生产任务管理模块（TSK）**
生产任务管理模块负责接收生产计划，进行工艺分解，生成车间作业指令，跟踪任务执行情况。

- **任务接收子模块**：从ERP系统接收生产订单、生产计划，或手工创建生产任务。依赖外部系统集成模块的ERP接口。
- **工艺分解子模块**：根据工艺路线，将生产任务分解为各工序的作业任务，生成工序作业计划。支持正向排程、逆向排程、有限能力排程。依赖工艺路线设计模块的工艺路线数据。
- **指令下发子模块**：将工序作业任务、工艺卡片、图纸、NC程序等工艺指令下发至车间终端或MES系统。依赖外部系统集成模块的MES接口和工艺文件管理模块的文件服务。
- **进度跟踪子模块**：实时跟踪各工序任务的开工、完工、报工情况。支持进度看板、甘特图展示。异常任务自动预警。依赖报表与统计分析模块的图表展示能力。
- **现场服务子模块**：支持工艺人员现场处理技术问题，记录现场工艺变更、工艺问题、改进建议。支持移动端拍照上传、语音录入。依赖企业微信集成的移动端能力。
- **完工确认子模块**：工序完成后进行完工确认，记录实际工时、实际材料消耗、质量检验结果等。支持与定额数据的对比分析。依赖工艺定额管理模块的定额数据。

**（10）报表与统计分析模块（RPT）**
报表与统计分析模块提供多维度、多层次的工艺数据统计分析功能。

- **工艺文件统计子模块**：统计工艺文件编制数量、审批通过率、编制周期、变更频次等。按编制人、产品类型、时间段分析。
- **定额统计子模块**：统计工时定额、材料定额的制定情况、执行情况、偏差情况。支持定额趋势分析、定额对比分析。依赖工艺定额管理模块的数据。
- **资源统计子模块**：统计设备利用率、工装使用频次、焊材消耗量、刀具损耗率等。支持资源负荷分析、资源优化建议。依赖工艺资源管理模块的数据。
- **质量统计子模块**：统计一次交检合格率、返工返修率、废品率、质量事故次数等。按产品、车间、工序、时间段分析。依赖质量工艺控制模块的数据。
- **效率统计子模块**：统计工艺准备周期、工艺编制效率、工艺变更响应时间等。支持工艺效率趋势分析、标杆对比。
- **自定义报表子模块**：提供报表设计器，支持用户自定义报表格式、数据源、筛选条件、统计维度、图表类型。支持报表定时生成、自动推送、导出打印。自定义报表可查询全系统数据，受数据权限控制。

**（11）外部系统集成模块（INT）**
外部系统集成模块负责实现CAPP系统与周边系统的数据交换和业务协同。

- **PDM/PLM集成子模块**：接收设计BOM、图纸、技术规范、设计变更通知。支持设计数据与工艺数据的关联映射。通过REST API或数据库视图与PDM系统交互。
- **ERP集成子模块**：向ERP系统传递工艺BOM、工艺定额、工艺路线、物料需求计划。从ERP系统接收生产订单、库存信息、采购信息。通过REST API或中间数据库表与ERP系统交互。
- **MES集成子模块**：向MES系统下发工艺指令、作业计划、NC程序。从MES系统接收生产执行数据、设备状态数据、质量检测数据。通过REST API或消息队列与MES系统交互。
- **质量管理集成子模块**：传递检验工艺、无损检测工艺、质量记录。接收不合格品信息、质量改进要求。通过REST API与质量管理系统交互。
- **企业微信集成子模块**：通过企业微信开放平台API，实现组织架构同步、单点登录、消息推送、移动端审批。企业微信集成采用独立的适配器设计，便于未来替换为钉钉或飞书。
- **数据交换平台子模块**：提供标准WebService/REST API接口，支持JSON/XML数据格式。提供接口调用日志、接口异常告警、接口性能监控。所有外部接口统一在此子模块管理，包括接口注册、鉴权、限流、日志、监控。

### 5.3 模块间依赖关系

模块间的依赖关系遵循"上层依赖下层、业务依赖基础"的原则，避免循环依赖。以下是核心模块间的依赖关系图（文字描述）：

**基础支撑层（无外部依赖，被所有上层模块依赖）：**
- 系统管理模块（SYS）是所有模块的基础，提供用户认证、权限校验、数据字典、编码规则、流程引擎、日志记录等基础服务。所有其他模块都依赖SYS模块。
- 外部系统集成模块（INT）中的数据交换平台子模块提供API网关能力，部分模块通过INT模块与外部系统交互，但INT模块本身不依赖业务模块。

**数据资源层（依赖系统管理模块，被工艺设计层依赖）：**
- 工艺资源管理模块（RES）依赖SYS模块的组织架构、数据字典、编码规则、日志服务。
- 工艺资源管理模块为工艺文件管理（DOC）、工艺路线设计（RTE）、质量工艺控制（QAC）等模块提供设备、工装、材料、参数、人员资质等基础数据查询服务。

**工艺设计层（依赖基础支撑层和数据资源层，被生产管理层依赖）：**
- 工艺文件管理模块（DOC）依赖SYS模块的审批流程、版本管理、文件存储、日志服务；依赖RES模块的工艺资源数据（设备、工装、材料等）。
- 工艺路线设计模块（RTE）依赖SYS模块的审批流程、日志服务；依赖RES模块的设备、工装、参数数据；依赖BOM模块的设计BOM数据。
- 工艺BOM管理模块（BOM）依赖SYS模块的编码规则、日志服务；依赖INT模块的PDM/PLM集成接口获取设计BOM；依赖RTE模块的工艺路线数据进行工艺BOM转换。
- 工艺定额管理模块（QTA）依赖SYS模块的日志服务；依赖RTE模块的工序数据进行工时定额；依赖BOM模块的材料定额数据。
- 工艺变更管理模块（CHG）依赖SYS模块的审批流程、日志服务；依赖DOC模块的工艺文件数据；依赖RTE模块的工艺路线数据；依赖BOM模块的BOM数据；依赖QTA模块的定额数据。CHG模块是跨模块的协调者，变更实施时调用各模块的数据更新接口。
- 质量工艺控制模块（QAC）依赖SYS模块的审批流程、日志服务；依赖RES模块的焊接材料、人员资质数据；依赖DOC模块的工艺文件模板和版本管理；依赖RTE模块的工艺路线关联。QAC中的不合格品返工工艺会反向调用DOC和RTE模块创建返工工艺文件和路线。

**生产管理层（依赖工艺设计层，连接外部系统）：**
- 生产任务管理模块（TSK）依赖SYS模块的日志服务；依赖RTE模块的工艺路线数据进行工艺分解；依赖DOC模块的工艺文件和图纸进行指令下发；依赖QTA模块的定额数据进行完工对比；依赖INT模块的ERP接口接收生产订单、MES接口下发指令、企业微信接口推送移动端消息。

**分析决策层（依赖所有下层模块）：**
- 报表与统计分析模块（RPT）依赖所有业务模块的数据，通过数据访问层直接查询数据库或调用各模块的统计接口。RPT模块本身不修改任何业务数据，是只读分析型模块。

**依赖关系约束：**
- 禁止循环依赖：如DOC模块不能依赖CHG模块，RTE模块不能依赖TSK模块。若存在业务上需要跨模块回调的场景，通过事件总线（Event Bus）发布事件，由目标模块的事件监听器异步处理，避免直接的模块间调用循环。
- 上层模块可调用下层模块的服务接口，但下层模块不可调用上层模块。若下层模块需要通知上层模块，通过事件机制实现。
- 同层模块之间尽量减少直接调用，优先通过事件机制或共享数据层进行协作。

### 5.4 数据流向设计

系统内部的数据流向遵循"设计→工艺→生产→反馈"的业务主线，同时存在横向的变更和质量控制数据流。以下是主要数据流向的文字描述：

**（1）设计到工艺的数据流（横向流入）**
- PDM/PLM系统 → INT模块（PDM集成子模块）→ BOM模块（设计BOM导入子模块）→ 数据库（设计BOM表）
- 设计BOM数据进入系统后，触发BOM模块的转换流程，生成工艺BOM框架；同时RTE模块可基于设计BOM创建工艺路线框架。
- 设计变更通知从PDM系统流入，触发CHG模块的变更评估流程，分析受影响的工艺数据。

**（2）工艺编制的主数据流（纵向核心）**
- RES模块维护的工艺资源数据（设备、工装、材料、参数、人员资质）持续写入数据库，为工艺编制提供基础数据支撑。
- DOC模块的工艺文件编制流程：用户创建工艺文件 → 选择模板 → 填写内容（引用RES资源数据）→ 提交审批 → SYS模块的流程引擎驱动审批 → 审批通过后发布正式版本 → 文件存储到文件服务器 → 版本信息写入数据库。
- RTE模块的工艺路线设计流程：基于BOM创建路线 → 定义工序（引用RES资源）→ 分配工时定额（关联QTA数据）→ 提交审批 → 审批通过后锁定 → 路线数据写入数据库。
- BOM模块的工艺BOM转换流程：基于设计BOM + 工艺路线 → 生成工艺BOM → 计算材料定额 → 关联辅料耗材 → 版本管理 → 写入数据库。
- QTA模块的定额制定流程：基于工序和材料 → 计算工时定额和材料定额 → 提交审批 → 写入数据库。

**（3）变更管理的数据流（横向调控）**
- 用户发起变更申请（CHG模块）→ 系统分析影响范围（查询DOC、RTE、BOM、QTA、QAC相关数据）→ 提交审批（SYS流程引擎）→ 审批通过后 → 并发更新各模块数据：
  - DOC模块：更新工艺文件版本
  - RTE模块：更新工艺路线版本
  - BOM模块：更新BOM版本
  - QTA模块：更新定额版本
  - QAC模块：更新质量工艺文件
- 变更实施完成后，验证数据写入CHG模块的验证记录表。

**（4）工艺到生产的数据流（纵向流出）**
- ERP系统下发生产订单 → INT模块（ERP集成）→ TSK模块（任务接收子模块）→ 数据库（生产任务表）
- TSK模块读取RTE工艺路线 + DOC工艺文件 + BOM物料清单 → 进行工艺分解 → 生成工序作业任务 → 通过INT模块（MES集成）下发到MES系统
- MES系统执行生产任务 → 采集实际工时、实际材料消耗、质量检测数据 → 通过INT模块回传到TSK模块 → 与QTA定额数据对比分析 → 写入数据库（生产执行记录表）

**（5）质量数据流（横向监控）**
- QAC模块编制检验工艺、焊接工艺、热处理工艺、无损检测工艺、压力试验工艺 → 随生产任务下发到车间执行
- 车间执行质量检验 → 质量记录（报告、扫描件）→ 写入QAC模块（质量记录子模块）→ 文件存储到文件服务器
- 发现不合格品 → QAC模块（不合格品处理子模块）→ 发起评审 → 若需返工 → 触发CHG模块创建返工工艺变更 → 调用DOC/RTE模块编制返工工艺 → 重新下发执行

**（6）统计分析的数据流（只读汇聚）**
- RPT模块从数据库读取各业务模块的数据 → 进行聚合计算、趋势分析、对比分析 → 生成报表和图表 → 通过前端ECharts展示 → 支持导出Excel/PDF
- 自定义报表通过RPT模块的报表设计器配置数据源（跨模块SQL查询或API聚合）→ 定时任务生成报表结果 → 缓存到Redis或数据库汇总表 → 用户查询时快速返回

**（7）系统管理的数据流（基础支撑）**
- SYS模块的组织架构、用户、角色、权限、数据字典、编码规则、流程配置等基础数据 → 写入数据库 → 被所有业务模块读取引用
- 用户登录 → SYS模块验证身份 → 生成Session存入Redis → 返回客户端Cookie → 后续请求携带Cookie → SYS中间件校验Session和权限 → 允许或拒绝访问
- 所有业务模块的操作日志 → 通过SYS模块的日志组件 → 写入MySQL日志表 + 发送到ELK系统

## 6. 技术选型说明

### 6.1 为什么选择PHP原生

在企业级CAPP系统的技术选型过程中，开发团队对多种技术方案进行了充分评估，最终确定采用PHP原生开发（不使用任何第三方Web框架）。这一决策基于以下深入的技术和业务考量：

**（1）企业技术储备与团队能力匹配**
- 企业信息中心现有开发团队具备多年PHP原生开发经验，对PHP语言特性、性能优化、安全编码有深入理解。团队成员熟悉企业业务流程，能够快速将业务需求转化为技术实现。
- 引入大型PHP框架（如Laravel、ThinkPHP、Symfony）虽然可以加速初期开发，但团队需要额外学习框架的架构设计、ORM用法、模板语法、命令行工具等，学习曲线陡峭。对于企业级定制系统，框架的通用抽象层反而可能成为性能瓶颈和调试障碍。
- PHP原生开发允许团队完全掌控代码的每一行逻辑，不依赖框架的"魔法方法"和隐式约定，代码可读性和可维护性对于企业内部长期运维更为友好。

**（2）系统性能与资源效率**
- PHP原生代码没有框架层的额外开销（如路由解析、依赖注入容器初始化、ORM对象关系映射、模板编译等），执行效率更高。对于工艺文件查询、BOM展开、报表统计等计算密集型操作，原生PHP可以精细控制SQL语句、内存使用和缓存策略，避免ORM自动生成低效率SQL的问题。
- PHP-FPM的进程模型非常适合企业内网应用的特点：请求处理快速、内存占用稳定、无内存泄漏风险（配合pm.max_requests配置）。相比Java等需要JVM预热和大量内存占用的技术，PHP在同等硬件配置下可以支撑更高的并发访问量。
- 工艺CAPP系统的核心操作是数据库CRUD和文件读写，计算复杂度中等，PHP原生完全能够满足性能需求。实测表明，在相同硬件环境下，优化良好的PHP原生应用处理简单查询的QPS（每秒查询率）比重量级框架高30%-50%。

**（3）定制化需求与灵活控制**
- CAPP系统具有强烈的行业特性和企业个性化需求，工艺文件模板、审批流程、数据字典、编码规则、报表格式等都需要高度定制。第三方框架的通用功能（如用户管理、CMS功能）对本系统价值有限，而框架的约束（如固定的目录结构、强制的ORM使用、预设的认证流程）反而可能限制定制灵活性。
- PHP原生开发允许团队根据企业实际需求，从零设计最适合的目录结构、类库组织、数据库访问模式、缓存策略、安全机制，不受框架设计哲学的束缚。例如，本系统的数据访问层采用轻量级DAO模式而非重量级ORM，就是为了精确控制每一条SQL语句的执行计划，优化复杂报表查询性能。
- 工艺数据的结构复杂（如工艺路线是多层嵌套结构、BOM是树形结构、工艺文件是富文本+表格混合结构），原生PHP可以更灵活地处理这些复杂数据结构，而不必受限于框架的模型关系定义。

**（4）长期维护与版本可控**
- 第三方框架的升级可能带来破坏性变更（如Laravel的大版本升级常伴随大量语法和配置变更），企业系统一旦基于某个框架版本开发，后续升级成本高昂，不升级又可能面临安全漏洞无法修复的困境。
- PHP原生代码只依赖PHP语言本身和少量稳定的扩展（PDO、Redis、GD等），这些扩展由PHP官方或PECL维护，向后兼容性好，升级风险可控。PHP 8.x相比PHP 7.x带来了显著的性能提升和新特性（如JIT编译、命名参数、联合类型、match表达式），原生代码可以充分利用这些新特性，而不必等待框架适配。
- 企业系统的生命周期通常在10年以上，原生代码的维护不依赖第三方框架的社区活跃度，即使某个框架停止维护，也不会影响本系统的运行。

**（5）安全可控与代码审计**
- 企业级系统特别是涉及特种设备工艺数据的系统，对安全性要求极高。第三方框架虽然提供了安全功能（如CSRF防护、XSS过滤），但框架本身的漏洞（如历史版本的反序列化漏洞、SQL注入漏洞）也可能成为攻击入口。
- PHP原生开发使得安全机制完全透明可控，团队可以针对企业安全策略定制每一道安全防线，而不是依赖框架的默认配置。所有输入过滤、输出转义、密码加密、会话管理、权限校验的代码都在团队掌控之中，便于安全审计和渗透测试。
- 本系统的安全组件（见第4章）全部自研，针对SQL注入采用PDO参数化查询，针对XSS采用上下文感知的输出编码，针对CSRF采用Token+SameSite Cookie双重防护，这些安全机制不依赖任何框架，代码清晰可审计。

**（6）部署简单与运维成本低**
- PHP原生应用的部署极为简单：将代码文件通过Git或FTP同步到服务器，配置Nginx虚拟主机，重启PHP-FPM即可。无需像Java应用那样打包WAR/JAR、配置JVM参数、管理应用服务器（Tomcat/WebLogic）。
- 企业信息中心运维团队对Nginx+PHP-FPM的运维经验丰富，能够快速定位问题、调整配置、扩容服务器。原生PHP的错误日志直接明了，没有框架的堆栈嵌套，问题排查效率高。
- 系统的持续集成/持续部署（CI/CD）流水线可以简单高效：Git提交触发Webhook → Jenkins/自建脚本拉取代码 → 执行单元测试 → 同步到生产服务器 → 平滑重启PHP-FPM。整个过程可在5分钟内完成，支持每日多次发布。

**（7）成本效益分析**
- PHP是开源免费技术，无需购买商业软件许可（如Java EE应用服务器、.NET Windows Server授权等），降低企业IT投入成本。
- PHP原生开发虽然初期需要投入更多时间构建基础框架（如路由、数据库访问、缓存、日志等公共组件），但这些基础组件一旦建成，可在企业未来多个项目中复用。相比购买商业CAPP软件（动辄数百万元）或采用重量级框架的隐性学习成本，原生开发的总体拥有成本（TCO）更低。
- 企业现有服务器资源（基于Linux）可以充分利用，无需为运行Java应用而采购更高配置的服务器。

**（8）框架与原生并非对立，而是取舍**
- 需要明确的是，"PHP原生"不等于"从零开始造轮子"或"拒绝一切第三方库"。本系统在PHP原生的基础上，合理引入经过验证的、职责单一的第三方库（如PHPExcel/PhpSpreadsheet处理Excel读写、TCPDF/mpdf生成PDF、PHPMailer发送邮件、Predis连接Redis等），这些库只解决特定技术问题，不强制系统架构，与原生开发理念不冲突。
- 团队自研的基础框架（约5000行代码）涵盖路由分发、控制器调度、服务容器、DAO基础类、缓存封装、日志组件、安全过滤、事件总线等核心能力，代码量小、逻辑清晰、完全可控，这是"轻量级框架"而非"无框架"。

综上所述，选择PHP原生开发是基于企业实际情况、团队能力、系统特点、长期维护、安全可控、成本效益等多维度综合评估后的最优决策。这一选择确保了CAPP系统能够在企业环境中长期稳定运行，并随业务发展灵活演进。

### 6.2 MySQL数据库选型理由

MySQL作为本系统的核心数据库，选型理由如下：

**（1）成熟稳定与生态丰富**
- MySQL是全球最流行的开源关系型数据库，经过数十年的生产环境验证，稳定性极高。MySQL 8.0在性能、安全性、功能丰富度上有了质的飞跃，完全满足企业级应用需求。
- MySQL拥有丰富的工具生态：Percona XtraBackup（热备份）、MySQL Workbench（建模工具）、pt-query-digest（慢查询分析）、ProxySQL（读写分离代理）等，便于运维管理和性能优化。

**（2）性能与扩展性**
- MySQL 8.0的InnoDB存储引擎支持行级锁、MVCC（多版本并发控制）、自适应哈希索引，高并发读写性能优异。配合主从复制、读写分离，可以支撑数百并发用户的企业内网应用。
- 对于工艺数据的树形结构（BOM、工艺路线），MySQL 8.0支持递归CTE（Common Table Expressions），方便进行层级查询，无需复杂的自连接或应用层递归。
- 未来数据量增长时，可通过分库分表（如按年份分表、按产品类型分库）、TiDB分布式数据库迁移等方式扩展，MySQL生态提供了平滑的扩展路径。

**（3）与PHP的天然契合**
- PHP通过PDO扩展与MySQL交互，PDO是PHP官方维护的数据库抽象层，稳定可靠，支持预处理语句、事务、存储过程调用等完整功能。
- PHP+MySQL是经典的LAMP/LEMP组合，大量文档、案例、社区支持，问题解决方案丰富。

**（4）成本与许可**
- MySQL Community Edition采用GPL开源许可，免费使用，无需支付商业数据库（如Oracle、SQL Server）的高额许可费用。
- 企业若未来需要商业支持，可选择MySQL Enterprise Edition或Percona Server，获得官方技术支持，迁移成本低。

**（5）数据安全与恢复**
- MySQL 8.0默认采用caching_sha2_password认证插件，安全性更强。支持TDE透明数据加密、Binlog加密、审计日志插件等企业级安全特性。
- 支持基于Binlog的Point-in-Time Recovery，可将数据恢复到任意时间点，满足工艺数据不可丢失的严格要求。

### 6.3 前端技术选型说明

**（1）不采用大型前端框架（React/Vue/Angular）**
- 本系统是企业内网管理信息系统，以数据录入、查询、审批、报表为主，交互复杂度中等，不需要单页应用（SPA）的极致用户体验。

- Layui是国内流行的轻量级前端UI框架，采用原生JavaScript编写，不依赖其他库，提供完整的后台管理界面组件（表格、表单、弹层、导航、树、上传、富文本等），风格简洁专业，中文文档完善，学习成本低。

**（3）ECharts作为图表库**
- ECharts是百度开源的数据可视化库，功能强大、图表类型丰富、配置灵活、中文文档完善。本系统的报表统计模块大量使用ECharts绘制折线图、柱状图、饼图、雷达图、甘特图、漏斗图等，完全满足工艺数据分析的可视化需求。

**（4）富文本编辑器**

- 编辑器与后端集成文件上传接口，实现图片和附件的自动上传和插入。

### 6.4 中间件与工具选型

**（1）Nginx作为Web服务器和负载均衡器**
- Nginx以其高并发、低内存占用、稳定可靠著称，是PHP应用的最佳搭档。Nginx处理静态资源效率极高，动态请求通过FastCGI协议转发给PHP-FPM，分工明确。

## 7. 接口设计规范

### 7.1 内部接口规范

系统内部模块间通过PHP接口（类的方法调用）进行通信，遵循以下规范：

**（1）服务接口定义**
- 每个业务模块定义一个服务接口（Interface）和对应的实现类（Implementation），其他模块通过接口调用服务，不直接依赖实现类。
- 服务接口命名规范：{模块名}ServiceInterface，如ProcessDocServiceInterface、ProcessRouteServiceInterface。
- 服务实现类命名规范：{模块名}Service，如ProcessDocService、ProcessRouteService。
- 服务接口定义在App\Contract命名空间下，实现类定义在App\Service命名空间下。

**（2）依赖注入**
- 服务实例通过服务容器（Service Container）统一管理，支持构造函数注入、属性注入、方法注入。
- 服务容器支持单例模式（Singleton）和原型模式（Prototype），根据服务特性选择合适生命周期。
- 依赖注入配置集中管理，便于替换服务实现（如替换企业微信集成为钉钉集成，只需修改配置，无需修改调用代码）。

**（3）数据传输对象（DTO）**
- 模块间传递的数据封装为DTO对象，避免直接传递数组或原始数据，确保类型安全和数据完整性。
- DTO命名规范：{操作名}{模块名}Dto，如CreateProcessDocDto、UpdateProcessRouteDto。
- DTO属性定义为public或protected，通过类型声明（PHP 8.0+）确保数据类型正确。

**（4）异常处理**
- 模块内部异常统一转换为业务异常（BusinessException）或系统异常（SystemException），包含错误码、错误消息、错误详情。
- 异常通过全局异常处理器捕获，转换为友好的错误响应（Web页面返回错误页，API返回JSON错误）。
- 错误码采用分层设计：SYS（系统级）、DOC（工艺文件）、RTE（工艺路线）、BOM（BOM）、QTA（定额）、CHG（变更）、QAC（质量）、TSK（任务）、RPT（报表）、INT（集成），如SYS_001（参数错误）、DOC_001（工艺文件不存在）。

### 7.3 接口安全机制

**（1）认证机制**
- REST API采用AppKey+AppSecret签名认证：
  - 外部系统申请AppKey和AppSecret，AppKey公开，AppSecret严格保密。
  - 每次请求在HTTP Header中携带：X-AppKey（应用标识）、X-Timestamp（时间戳，Unix时间戳，有效期5分钟）、X-Nonce（随机字符串，16位，单次有效）、X-Signature（签名）。
  - 签名生成规则：将请求参数（URL参数+Body JSON字符串）按参数名ASCII排序，拼接为字符串，末尾追加AppSecret，进行HMAC-SHA256计算，结果为X-Signature。
  - 服务端验证：检查时间戳未过期（与服务器时间差≤5分钟）、检查Nonce未重复使用（Redis记录最近5分钟Nonce）、验证签名正确性。
- WebService采用WS-Security UsernameToken或HTTP Basic Auth，配合HTTPS传输。

**（2）授权机制**
- 每个AppKey绑定可访问的接口白名单，未授权的接口调用返回403禁止访问。
- 接口调用频率限制：每个AppKey每分钟最多1000次请求，超出返回429 Too Many Requests。
- 数据权限：外部系统通过API只能访问其被授权的数据范围（如ERP系统只能访问与其对接的生产订单相关工艺数据）。

**（3）传输安全**
- 所有外部接口强制HTTPS，TLS 1.2+。
- 敏感数据（如工艺定额、材料价格）在API响应中加密或脱敏处理。

**（4）日志与监控**
- 所有API调用记录详细日志：调用时间、AppKey、接口路径、请求参数（脱敏）、响应状态码、响应时间、客户端IP。
- API性能监控：统计每个接口的QPS、平均响应时间、错误率、慢请求比例，通过Grafana仪表盘展示。
- API异常告警：接口错误率超过5%或平均响应时间超过5秒时，自动发送企业微信告警。

## 8. 数据库架构设计要点

### 8.1 数据库选型与版本

- **数据库产品**：MySQL Community Server 8.0.x
- **存储引擎**：InnoDB（支持事务、行级锁、外键、崩溃恢复）
- **字符集**：UTF-8mb4（支持4字节Unicode字符，包括中文、Emoji、特殊符号）
- **排序规则**：utf8mb4_unicode_ci（通用Unicode排序，不区分大小写）
- **事务隔离级别**：READ COMMITTED（避免脏读，同时减少锁竞争，适合读写并发高的企业应用）

### 8.2 数据库分层设计

数据库按业务模块划分为多个逻辑数据库（Schema），便于权限管理和维护：

| 数据库名 | 说明 | 主要数据表 |
|---------|------|-----------|
| capp_sys | 系统管理数据 | 组织架构表、用户表、角色表、权限表、数据字典表、编码规则表、流程定义表、操作日志表、登录日志表、系统参数表 |
| capp_res | 工艺资源数据 | 设备台账表、工装模具表、刀具量具表、焊接材料表、工艺参数表、人员资质表 |
| capp_doc | 工艺文件数据 | 工艺文件主表、工艺文件版本表、工艺文件内容表、文件模板表、文件分类表、文件发放记录表 |
| capp_rte | 工艺路线数据 | 工艺路线主表、工序定义表、工序资源分配表、典型工艺库表、工艺路线版本表 |
| capp_bom | BOM数据 | 设计BOM表、工艺BOM表、BOM版本表、材料定额表、辅料定额表、材料汇总表 |
| capp_qta | 定额数据 | 工时定额表、材料定额主表、定额版本表、定额计算参数表、定额统计汇总表 |

| capp_qac | 质量工艺数据 | 检验工艺表、焊接工艺表、热处理工艺表、无损检测工艺表、压力试验工艺表、不合格品记录表、质量记录文件表 |

| capp_rpt | 报表数据 | 报表定义表、报表数据源表、报表生成记录表、报表结果缓存表、自定义报表收藏表 |

**设计原则：**
- 每个数据库独立管理权限，应用账号按模块分配数据库访问权限，实现数据隔离。
- 跨模块关联查询通过应用程序层进行数据聚合，避免跨库JOIN（若部署在同一MySQL实例，跨库JOIN技术上可行，但不利于未来分库拆分）。
- 公共基础数据（如组织架构、用户、数据字典）存储在capp_sys库，其他库通过冗余字段或缓存引用，减少跨库查询。

### 8.3 主从复制与读写分离

**（1）主从复制架构**
- 一主两从架构：1台Master（主库）+ 2台Slave（从库）。
- 复制模式：异步复制（Asynchronous Replication）。主库事务提交后立即返回，不等待从库确认，确保主库写性能。从库通过IO线程读取主库Binlog，通过SQL线程重放数据变更。
- 复制监控：通过SHOW SLAVE STATUS监控复制延迟（Seconds_Behind_Master），正常情况下延迟在1秒以内。若延迟超过5秒，触发告警并临时将读流量切回主库。

**（2）读写分离实现**
- 数据访问层（DAO）封装读写分离逻辑，对业务层透明。
- 写操作（INSERT、UPDATE、DELETE、REPLACE、DDL）自动路由到主库。
- 读操作（SELECT）默认路由到从库，通过轮询算法选择负载较低的从库。
- 特殊场景强制读主库：
  - 刚写入数据后立即读取（如插入工艺文件后马上查询详情），避免从库延迟导致读不到新数据。
  - 报表统计涉及大量数据聚合时，为避免影响从库复制性能，可配置为读主库或在专用从库执行。
- 事务内的所有操作（包括SELECT）路由到主库，确保事务内数据一致性。

**（3）未来扩展**
- 若读压力持续增长，可水平扩展从库数量（一主四从、一主六从）。
- 若写压力成为瓶颈，可考虑分库分表或升级到MySQL Group Replication / InnoDB Cluster实现多主写入。

### 8.4 分库分表策略

初期系统数据量可控，采用单实例多库（Schema）设计。未来数据量增长时，按以下策略进行分库分表：

**（1）垂直分库（按业务拆分）**
- 当单实例性能达到瓶颈（CPU>70%、内存>80%、连接数>80%容量）时，将不同业务库迁移到独立MySQL实例。
- 优先拆分访问频率低、数据量大的历史库（如操作日志库、报表结果库）到独立实例，减轻主实例压力。
- 垂直分库后，跨库事务通过分布式事务（如Saga模式、TCC模式）或最终一致性（消息队列）保证。

**（2）水平分表（按数据拆分）**
- 对于数据量增长极快的表，按时间或ID范围进行水平分表：
  - 操作日志表：按月份分表，如sys_log_202401、sys_log_202402，通过定时任务自动创建新表。查询时根据时间范围路由到对应表。
  - 工艺文件版本表：按年份分表，如doc_version_2023、doc_version_2024。
  - 接口调用日志表：按月份分表。
- 分表路由逻辑封装在基础DAO中，对业务层透明。基础DAO根据分表字段（如创建时间）自动计算表名，执行SQL时动态替换表名。

**（3）归档策略**
- 对于历史数据（如3年前的工艺文件版本、已完成的变更记录、过期的操作日志），通过定时任务迁移到归档库（Archive Database）。
- 归档库采用压缩存储（MySQL InnoDB Page Compression或MyISAM压缩表），降低存储成本。
- 归档数据在线可查，但查询性能较低，主要用于审计和法规追溯。日常业务查询只访问在线库。

### 8.5 数据库性能优化

**（1）索引设计规范**
- 每个表必须有主键，优先使用自增整数（BIGINT UNSIGNED AUTO_INCREMENT）或雪花算法ID（BIGINT）。
- 外键字段必须建立索引，加速JOIN查询和级联操作。
- WHERE条件中的等值查询字段、范围查询字段、ORDER BY字段、GROUP BY字段建立索引。
- 组合索引遵循最左前缀原则，将区分度高的字段放在前面。
- 避免过多索引（单表不超过10个），索引会减慢写操作速度并占用存储空间。
- 定期使用EXPLAIN分析慢查询，优化索引策略。

**（2）查询优化**
- 禁止使用SELECT *，只查询需要的字段，减少网络传输和内存占用。
- 复杂报表查询使用汇总表或物化视图（MySQL 8.0支持物化视图需通过触发器或定时任务模拟），避免实时全表扫描。
- 分页查询采用延迟关联（Deferred Join）或覆盖索引优化，避免深分页（如LIMIT 100000, 20）导致的性能问题。
- 大数据量导出采用流式查询（PDO unbuffered query），避免一次性加载到内存。

**（3）表结构优化**
- 字段类型选择合适的最小类型：状态字段用TINYINT，ID用BIGINT，金额用DECIMAL(18,4)，短字符串用VARCHAR，长文本用TEXT，日期时间用DATETIME或TIMESTAMP。
- 避免使用TEXT/BLOB类型存储大量数据，工艺文件内容、质量记录等大数据存储在文件服务器，数据库只存文件路径。
- 适当冗余：对于频繁查询但很少变更的关联字段（如工艺文件中的产品型号名称），可在主表中冗余存储，避免JOIN查询。

**（4）连接池与并发控制**
- PHP-FPM每个进程独立连接数据库，不共享连接池（PHP的进程模型决定）。通过控制FPM进程数（pm.max_children）间接控制数据库连接数。
- 数据库最大连接数配置为（FPM最大进程数 × 应用服务器数量 + 预留管理连接），如3台应用服务器×50进程=150，配置max_connections=200。
- 慢查询阈值设置为1秒，超过1秒的查询记录到慢查询日志，每日分析优化。

**（5）定期维护**
- 每周执行OPTIMIZE TABLE整理表碎片（对于频繁UPDATE/DELETE的表）。
- 每月分析表结构（ANALYZE TABLE）更新统计信息，帮助优化器生成更优执行计划。
- 定期清理过期数据（如临时文件记录、超过2年的操作日志），释放存储空间。

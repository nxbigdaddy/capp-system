## 1. 概述

本章节详细阐述 CAPP（计算机辅助工艺规划）系统与外部核心系统的对接设计方案。工业压缩机及压力容器研发设计生产企业信息化建设通常以 PLM（产品生命周期管理）为数据源源头，以 ERP（企业资源计划）为业务运营核心，以 MES（制造执行系统）为生产执行终端。CAPP 系统作为连接设计与制造的桥梁，必须与上述三大系统实现深度集成，确保产品数据、工艺数据、生产数据在系统间高效、准确、安全地流转。

本设计遵循以下核心原则：

- **松耦合原则**：各系统间通过标准接口或中间层进行数据交换，避免直接操作对方核心数据库。
- **数据一致性原则**：建立统一的数据映射规范与校验机制，确保跨系统数据语义一致。
- **高可用性原则**：对接服务具备故障转移、重试、补偿能力，保障关键业务不中断。
- **安全性原则**：数据传输加密、身份认证、访问控制、操作审计全覆盖。
- **可扩展性原则**：通用对接框架支持未来新系统的快速接入。

## 2. CAXA PLM 对接设计

### 2.1 CAXA PLM 系统简介

CAXA PLM（Product Lifecycle Management）是北京数码大方科技股份有限公司研发的国产产品全生命周期管理系统，广泛应用于装备制造、汽车、电子等行业。该系统以 CAD 图纸和 BOM（物料清单）为核心，覆盖产品设计、工艺设计、变更管理、文档管理、项目管理等业务领域。对于工业压缩机及压力容器企业而言，CAXA PLM 是产品数据源头的权威系统，存储着产品设计 BOM、三维模型、二维图纸、技术参数、变更记录等关键数据。

CAXA PLM 提供以下对外数据交换能力：

- **CAXA EAP 平台**：提供基于 SOAP 协议的 WebService 接口，支持数据查询、写入、变更通知。
- **数据库视图/中间表**：支持在 PLM 数据库中创建只读视图或同步中间表，供外部系统读取。
- **文件 FTP/SFTP 服务**：支持图纸、模型等文件的批量导出与目录同步。
- **事件触发器**：支持在 PLM 业务对象状态变更时触发外部调用或写入消息队列。

### 2.2 对接目标与范围

CAPP 系统与 CAXA PLM 的对接旨在打通从产品设计到工艺设计的数字化链路，消除信息孤岛，避免重复录入。具体对接范围如下：

| 数据类别 | 同步方向 | 数据内容 | 同步频率 |
|---------|---------|---------|---------|
| 产品主数据 | PLM → CAPP | 产品编码、名称、型号、规格、技术参数、设计状态 | 实时/定时 |
| BOM 数据 | PLM → CAPP | 设计 BOM 结构、零部件层级关系、数量、版本 | 实时/定时 |
| 工艺数据 | 双向同步 | 工艺路线、工序信息、工艺参数、工艺版本 | 实时/定时 |
| 图纸文件 | PLM → CAPP | 二维工程图（PDF/DWG）、三维模型、工艺简图 | 定时/手动 |
| 变更数据 | PLM → CAPP | ECO（工程变更单）信息、变更前后差异、生效日期 | 实时 |
| 物料主数据 | PLM → CAPP | 物料编码、名称、材质、规格、图号、重量、设计版本 | 定时 |

**对接边界说明**：

- CAPP 系统不直接修改 PLM 中的设计 BOM 和产品结构，仅接收并引用。
- CAPP 系统生成的工艺路线和工艺文件，在审核发布后可反向回写至 PLM 的工艺管理模块，实现设计工艺一体化。
- 图纸文件以只读引用为主，CAPP 系统本地缓存副本，不修改源文件。

### 2.4 对接方式

综合考虑数据安全性、实时性要求及企业现有 IT 基础设施，CAPP 与 CAXA PLM 采用**多通道混合对接模式**：

#### 2.4.1 主通道：WebService API（SOAP/XML）

- **适用场景**：产品主数据查询、BOM 结构获取、工艺数据回写、变更单接收。
- **技术实现**：PHP 通过 `SoapClient` 扩展调用 CAXA PLM 发布的 SOAP 接口。
- **接口规范**：遵循 CAXA EAP 平台标准接口规范，请求/响应报文采用 XML 格式，UTF-8 编码。
- **地址配置**：在 CAPP 系统管理后台可配置 PLM WebService 的 WSDL 地址、命名空间、超时时间。

#### 2.4.2 辅助通道：数据库中间表（只读视图）

- **适用场景**：大批量 BOM 全量同步、历史数据迁移、定时对账。
- **技术实现**：在 PLM 数据库中创建只读视图（如 `V_PLM_BOM`、`V_PLM_PRODUCT`），CAPP 通过独立数据库连接（只读账号）定时抽取数据。
- **安全控制**：中间表/视图仅暴露必要字段，CAPP 使用独立只读数据库账号，IP 白名单限制。

#### 2.4.3 文件通道：SFTP/文件共享

- **适用场景**：图纸文件（PDF、DWG）、三维模型、工艺简图的批量同步。
- **技术实现**：PLM 系统将文件发布至 SFTP 服务器指定目录，CAPP 通过 `phpseclib` 或系统级 SFTP 客户端定时扫描、下载、缓存至本地文件仓库。
- **文件命名规范**：`{物料编码}_{版本号}_{文件类型}.{扩展名}`，如 `GMJ-2024-001_A_2D.pdf`。

### 2.5 同步策略

| 同步策略 | 适用数据 | 触发方式 | 技术实现 | 优先级 |
|---------|---------|---------|---------|--------|
| **实时同步** | ECO 变更单、工艺状态变更 | PLM 事件触发 → 调用 CAPP API | WebService 推送 + 消息队列 | 高 |
| **定时同步** | BOM 全量、物料主数据、图纸文件 | CAPP 定时任务（Cron） | 每 15 分钟/每小时/每日凌晨 | 中 |
| **手动同步** | 指定产品 BOM、指定工艺路线 | 用户在 CAPP 界面触发 | 异步任务队列，进度条展示 | 中 |
| **增量同步** | 产品属性变更、BOM 版本变更 | 基于 `LAST_MODIFY_TIME` 或版本号比对 | 记录上次同步时间戳，只拉取变更数据 | 高 |

**增量同步机制详解**：

1. CAPP 系统在每次成功同步后，记录该数据类别的 `last_sync_time` 和 `last_sync_version`。
2. 下次同步时，向 PLM 发送请求参数 `sync_since = last_sync_time`。
3. PLM 返回该时间戳之后发生变更的数据集合。
4. CAPP 对增量数据进行差异比对（Diff），识别新增、修改、删除操作。
5. 执行本地数据更新，并记录同步日志。

### 2.7 冲突处理机制

在多系统双向同步场景下，数据冲突不可避免。CAPP 系统建立以下冲突检测与处理机制：

#### 2.7.1 冲突类型定义

| 冲突类型 | 描述 | 示例 |
|---------|------|------|
| **版本冲突** | 同一对象在 PLM 和 CAPP 中版本不一致 | PLM 中 BOM 已升级至 V2.0，CAPP 中仍为 V1.0 |
| **状态冲突** | 同一对象状态流转不一致 | PLM 中产品已归档，CAPP 中工艺仍在编制 |
| **字段冲突** | 同一字段双向修改导致值不一致 | 工艺参数在 PLM 和 CAPP 中同时被修改 |
| **结构冲突** | BOM 结构在同步窗口期内发生变更 | 同步过程中 PLM 又新增了一个子件 |

#### 2.7.2 冲突检测规则

1. **版本号比对**：同步时比较 PLM 版本号与 CAPP 本地版本号，若 PLM 版本 > CAPP 版本，判定为 PLM 侧有更新。
2. **时间戳比对**：比较 `last_modify_time`，若 PLM 侧时间戳晚于 CAPP 侧，判定为 PLM 数据更新。
3. **哈希值比对**：对关键字段计算 MD5 哈希，快速检测内容差异。

#### 2.7.3 冲突解决策略

| 冲突场景 | 解决策略 | 说明 |
|---------|---------|------|
| PLM 版本 > CAPP 版本 | **PLM 优先覆盖** | 设计数据以 PLM 为权威源，CAPP 自动更新 |
| CAPP 工艺已发布，PLM 设计变更 | **变更通知 + 人工确认** | 系统标记冲突，推送消息给工艺人员，由人工决定是否接受变更 |
| 双向同时修改工艺参数 | **时间戳优先 + 人工仲裁** | 以最后修改时间为准，同时记录冲突日志，保留双方版本供追溯 |
| 同步过程中 PLM 结构变更 | **中断当前同步 + 重新拉取** | 检测到版本变化后，放弃当前批次，重新发起全量同步 |

#### 2.7.4 冲突处理数据流

```
[同步数据到达]
  │
  ▼
[冲突检测引擎运行]
  │
  ├─ 无冲突 ──→ [正常写入本地数据库]
  │
  ├─ 轻微冲突（版本落后）──→ [自动覆盖，记录变更日志]
  │
  ├─ 中度冲突（已发布工艺遇设计变更）──→ [标记冲突状态，推送待办任务给工艺员]
  │
  └─ 严重冲突（核心参数双向修改）──→ [锁定记录，通知双方系统管理员，进入仲裁流程]
  │
  ▼
[冲突处理结果记录至 sync_conflict_log 表]
```

### 2.8 对接安全设计

#### 2.8.1 传输安全

- **协议层**：所有 WebService 调用均通过 HTTPS 传输，TLS 1.2 以上版本，禁用 SSLv3、TLS 1.0/1.1。
- **证书管理**：CAPP 服务端配置 PLM 服务器 CA 证书，可选双向 TLS 认证（mTLS）。
- **SFTP 文件传输**：使用 SSH-2 协议，RSA/ED25519 密钥认证，禁用密码登录。

#### 2.8.2 身份认证与授权

- **API 认证**：SOAP 请求 Header 中携带 `AppID`、`Timestamp`、`Nonce`、`Signature`。签名算法为 HMAC-SHA256，密钥由双方系统管理员在配置界面手动录入，定期轮换（建议 90 天）。
- **IP 白名单**：PLM 服务端配置 CAPP 服务器出口 IP 白名单，拒绝非授权 IP 请求。
- **数据库中间表**：CAPP 使用独立只读账号，最小权限原则，仅授权 SELECT 权限至指定视图。

#### 2.8.3 数据安全

- **敏感字段脱敏**：同步过程中如涉及供应商价格、客户信息等敏感数据，在中间层进行脱敏处理。
- **数据加密存储**：对接配置表中的密码、API Key 等敏感信息采用 AES-256-CBC 加密存储，密钥托管于 CAPP 系统配置文件（文件权限 600）。
- **防 SQL 注入**：所有数据库中间表查询使用 PDO 预处理语句，参数化绑定。

#### 2.8.4 审计与追溯

- 每一次 API 调用、数据库读取、文件传输均记录完整日志，包括：请求时间、请求方 IP、调用接口、请求参数（脱敏后）、响应状态、耗时、异常信息。
- 日志保留期限不少于 2 年，定期归档至独立日志服务器或对象存储。

## 3. 用友 U8 ERP 对接设计

### 3.1 U8 系统简介

用友 U8+ 是国内主流的中大型企业管理软件，涵盖财务、供应链、生产制造、人力资源等核心模块。对于工业压缩机及压力容器制造企业，U8 ERP 是业务运营的核心系统，管理着物料主数据、库存、采购、销售、生产订单、成本核算等关键业务流程。CAPP 系统与 U8 ERP 的对接，旨在实现工艺数据到生产执行的数据贯通，以及生产实际数据（成本、工时）向工艺优化的反馈闭环。

U8 对外提供的数据交换方式包括：

- **U8 OpenAPI**：用友官方提供的 RESTful API 接口，支持 JSON 格式，覆盖常见业务对象的增删改查。
- **U8 EAI（企业应用集成）**：基于 XML 数据交换标准，通过 HTTP POST 或消息中间件进行批量数据交换。
- **U8 数据库直连**：U8 采用 SQL Server 数据库，可通过创建中间库或只读视图方式供外部系统访问。
- **U8 单据模板导入导出**：通过 Excel/TXT 模板进行批量数据导入导出，适用于初始化或大批量数据迁移。

### 3.2 对接目标与范围

| 数据类别 | 同步方向 | 数据内容 | 业务价值 |
|---------|---------|---------|---------|
| 物料主数据 | U8 → CAPP | 物料编码、名称、规格、计量单位、物料属性（自制/外购/委外）、库存分类 | 保证 CAPP 使用与 ERP 一致的物料字典 |
| BOM 数据 | CAPP → U8 | 制造 BOM（MBOM）、工艺路线关联的物料定额、工时定额 | 将设计 BOM 转化为制造 BOM 下发至 ERP |

| 生产订单 | U8 → CAPP | 生产订单号、产品编码、数量、计划开工/完工日期、生产车间 | CAPP 基于生产订单组织工艺派工 |

| 工艺路线 | CAPP → U8 | 工序序列、工作中心、标准工时、设备要求 | 作为 ERP 生产订单排产与成本核算基础 |

### 3.4 对接方式

综合考虑 U8 版本（U8+V16.0）、企业现有集成经验及数据量，采用以下混合对接架构：

#### 3.4.1 主通道：U8 OpenAPI（REST/JSON）

- **适用场景**：物料主数据查询、生产订单接收、库存查询、成本数据获取。
- **技术实现**：PHP 通过 `curl` 调用 U8 OpenAPI，请求/响应采用 JSON 格式。
- **认证方式**：U8 用户账号 + AppKey + Timestamp + Signature（HMAC-SHA1）。
- **接口地址**：`https://{u8-server}/api/{module}/{action}`，如 `https://u8.company.com/api/inventory/GetInventoryList`。

#### 3.4.2 批量通道：U8 EAI + 中间库

- **适用场景**：制造 BOM 批量下发、工艺路线批量下发、生产订单批量回传。
- **技术实现**：
  1. CAPP 将待下发数据写入 SQL Server 中间库（独立数据库实例，与 U8 生产库隔离）。
  2. U8 EAI 服务定时扫描中间库，读取数据并转换为 U8 内部格式。
  3. U8 EAI 调用 U8 标准接口写入业务数据，并返回处理结果至中间库。
  4. CAPP 定时读取中间库结果状态，更新本地同步记录。
- **优势**：大批量数据下发性能高，U8 事务完整性由 EAI 保障，降低直接调用 API 的频率限制风险。

#### 3.4.3 辅助通道：数据库视图（只读）

- **适用场景**：库存实时查询、物料属性快速校验。
- **技术实现**：在 U8 数据库中创建只读视图（如 `V_U8_INVENTORY`、`V_U8_MOMain`），CAPP 通过独立只读账号查询。

### 3.5 同步策略

| 数据类别 | 同步方向 | 策略 | 触发条件 | 频率 |
|---------|---------|------|---------|------|
| 物料主数据 | U8 → CAPP | 增量同步 | U8 物料新增/修改 | 每 30 分钟 |
| 库存数据 | U8 → CAPP | 定时同步 | 固定周期拉取 | 每 15 分钟 |
| 生产订单 | U8 → CAPP | 增量 + 事件 | U8 订单审核/下达 | 每 10 分钟 + U8 推送 |
| 制造 BOM | CAPP → U8 | 手动 + 审批触发 | 工艺发布时人工确认下发 | 业务触发 |
| 工艺路线 | CAPP → U8 | 手动 + 审批触发 | 工艺发布时人工确认下发 | 业务触发 |
| 成本数据 | U8 → CAPP | 定时同步 | 月末成本卷积完成后 | 每月 1 次 |

### 3.6 业务场景

#### 3.6.1 物料同步场景

**场景描述**：U8 中新增或修改了原材料、标准件信息，需要同步至 CAPP，确保工艺编制时引用的物料信息准确。

**业务流程**：

1. U8 物料管理员维护物料档案（如新增一种工业压缩机用特种不锈钢材料）。
2. U8 物料保存后，`ModifyDate` 字段更新。
3. CAPP 定时任务（每 30 分钟）调用 U8 OpenAPI `GetInventoryList(sync_since)`。
4. U8 返回增量物料列表。
5. CAPP 数据校验：必填字段完整性、编码唯一性、单位有效性。
6. CAPP 写入/更新本地物料字典表 `material_dict`。
7. 若物料为关键原材料（如密封件材料），触发消息通知相关工艺员关注。

#### 3.6.2 BOM 下发场景

**场景描述**：CAPP 完成某型号工业压缩机制造 BOM 和工艺路线编制并审核通过后，将制造 BOM 下发至 U8，作为生产订单排产和物料需求计划（MRP）的依据。

**业务流程**：

1. 工艺员在 CAPP 中完成制造 BOM 编制，关联工艺路线、工序物料定额、工时定额。
2. 工艺路线提交审核，经工艺主管、技术部长审批通过，状态变为"已发布"。
3. 系统在工艺发布界面提示"是否下发至 ERP"，工艺主管确认下发。
4. CAPP 调用 BOM 下发服务：
   - 将 CAPP 制造 BOM 转换为 U8 EAI 标准 XML 格式。
   - 写入 SQL Server 中间库 `EAI_BOM_IMPORT` 表。
5. U8 EAI 服务（每 5 分钟扫描）读取中间库数据。
6. U8 EAI 校验数据合法性（物料编码存在性、数量有效性、层级合法性）。
7. U8 EAI 调用 U8 内部接口创建/更新制造 BOM。
8. U8 返回处理结果（成功/失败及原因）至中间库 `EAI_BOM_IMPORT_RESULT` 表。
9. CAPP 读取结果，更新本地 BOM 下发状态：
   - 成功：`erp_sync_status = 1`，记录 U8 BOM 版本号。
   - 失败：`erp_sync_status = 2`，记录失败原因，推送告警给工艺主管和 ERP 管理员。

#### 3.6.3 生产订单接收场景

**场景描述**：销售部门在 U8 中录入销售订单并跑完 MRP 后，生成生产订单。CAPP 需要接收生产订单信息，以便组织工艺派工、生成工序作业计划。

**业务流程**：

1. U8 生产订单审核并下达后，触发 EAI 事件或更新订单状态。
2. CAPP 定时任务（每 10 分钟）调用 U8 OpenAPI `GetMOList(status='已下达')`。
3. 或 U8 通过 WebHook 主动推送生产订单 JSON 至 CAPP 接收接口。
4. CAPP 接收订单数据，校验产品编码是否在 CAPP 中存在有效工艺路线。
5. 若存在有效工艺：
   - 创建 CAPP 内部"生产任务单"，关联 U8 生产订单号。
   - 复制标准工艺路线至任务单，生成工序作业计划。
   - 推送待办给车间工艺员/调度员。
6. 若不存在有效工艺：
   - 标记为"待编制工艺"。
   - 紧急推送告警给技术部长和工艺主管，要求限期完成工艺编制。

#### 3.6.4 成本回传场景

**场景描述**：生产完工后，U8 成本管理模块卷积出各产品、各工序的实际成本。CAPP 接收成本数据，用于工艺成本分析、工时定额优化、材料消耗优化。

**业务流程**：

1. 月末 U8 成本会计执行成本卷积计算。
2. 成本计算完成后，U8 成本数据更新。
3. CAPP 定时任务（每月 1 日凌晨 2:00）调用 U8 OpenAPI `GetCostData(period)`。
4. U8 返回各生产订单、各工序的实际成本明细（材料费、人工费、制造费用）。
5. CAPP 将成本数据写入 `cost_actual` 表，关联至对应工艺路线和工序。
6. CAPP 成本分析引擎运行：
   - 对比标准成本（工艺定额）与实际成本。
   - 识别偏差 > 10% 的工序，生成成本偏差分析报告。
7. 报告推送至技术部长、工艺主管、财务经理。
8. 工艺主管根据分析报告，在下一版本工艺优化中调整工时定额或材料定额。

### 3.8 异常处理与补偿机制

#### 3.8.1 异常分类

| 异常级别 | 异常类型 | 示例 | 处理策略 |
|---------|---------|------|---------|
| **致命** | 网络中断、U8 服务宕机 | 调用 U8 API 超时，连接拒绝 | 立即告警，进入重试队列，人工介入 |
| **严重** | 数据校验失败、关键字段缺失 | BOM 下发时子件物料编码在 U8 不存在 | 记录失败明细，通知业务人员修正源数据，支持手动重试 |
| **一般** | 部分记录处理失败 | 批量同步 100 条物料，其中 3 条编码重复 | 标记部分成功，成功记录正常入库，失败记录进入失败重试队列 |
| **提示** | 数据延迟、非关键字段差异 | 库存数据同步延迟 5 分钟 | 记录日志，无需人工处理 |

#### 3.8.2 补偿机制

1. **失败重试队列**：
   - 所有同步失败的数据进入 `sync_retry_queue` 表。
   - 重试策略：首次失败后 5 分钟重试，第二次 15 分钟，第三次 1 小时，最多重试 5 次。
   - 超过 5 次仍失败，标记为"死信"，推送告警给系统管理员和业务负责人。

2. **事务补偿（Saga 模式）**：
   - 对于跨系统长事务（如 BOM 下发涉及 CAPP 状态更新、中间库写入、U8 处理、结果回写），采用 Saga 补偿模式。
   - 若下游步骤失败，触发补偿操作：回滚 CAPP 本地状态、清理中间库数据、记录补偿日志。

3. **对账机制**：
   - 每日凌晨 2:00 执行自动对账任务。
   - 比对 CAPP 与 U8 的关键数据总量（如物料总数、BOM 版本数、生产订单数）。
   - 差异 > 阈值（如 1%）时，触发全量比对，生成差异报告。

4. **手动补偿工具**：
   - CAPP 管理后台提供"同步异常处理中心"界面。
   - 展示所有失败记录，支持单条重试、批量重试、强制忽略、数据修正后重试。
   - 所有手动操作记录审计日志。

## 4. MES 系统对接设计

### 4.1 MES 系统简介

MES（Manufacturing Execution System，制造执行系统）是位于上层计划管理系统（ERP）与底层工业控制之间的面向车间层的管理信息系统。对于工业压缩机及压力容器制造企业，MES 负责生产现场的详细排产、工序派工、作业指导书下发、工序报工、质量检验、设备管理、物料追溯等核心业务。CAPP 系统与 MES 的对接，实现了从工艺设计到生产执行的数字化贯通，确保车间现场执行的是最新、最准确的工艺指令，同时将生产现场的执行数据（实际工时、质量结果、设备参数）回传至 CAPP，形成工艺优化的数据闭环。

本企业 MES 系统采用自研或国内主流 MES 平台，对外提供以下集成能力：

- **REST API**：基于 HTTP/HTTPS 的 JSON 接口，支持工艺路线接收、工单创建、报工数据上传。
- **WebService（SOAP）**：部分传统 MES 模块仍采用 SOAP/XML 接口。
- **消息队列（RabbitMQ/ActiveMQ）**：用于高并发、实时性要求高的场景，如设备状态上报、质量数据实时采集。
- **数据库中间表**：MES 通常采用 SQL Server 或 MySQL 数据库，可通过中间表进行批量数据交换。

### 4.2 对接目标与范围

| 数据类别 | 同步方向 | 数据内容 | 实时性要求 |
|---------|---------|---------|-----------|
| 工艺路线 | CAPP → MES | 工序序列、作业指导书、工艺参数、图纸附件、工装模具要求 | 分钟级（工单开工前） |
| 生产工单 | CAPP → MES | 工单号、产品编码、数量、计划起止时间、优先级、关联工艺版本 | 分钟级 |

| 质量数据 | MES → CAPP | 检验项、实测值、检验结果、不合格原因、检验员、检验时间 | 实时 |
| 设备状态 | MES → CAPP | 设备开机/关机/故障/维修状态、设备运行参数（温度、压力、转速） | 实时（秒级/分钟级） |

### 4.4 对接方式

#### 4.4.1 主通道：REST API（JSON/HTTPS）

- **适用场景**：工艺路线下发、工单创建、报工数据接收、质量数据接收。
- **技术实现**：
  - CAPP → MES：PHP `curl` 发送 POST/PUT 请求，Body 为 JSON。
  - MES → CAPP：MES 调用 CAPP 提供的 RESTful WebHook 接口，CAPP 采用原生 PHP 编写路由分发器接收请求。
- **接口规范**：
  - 请求头：`Content-Type: application/json`、`Authorization: Bearer {token}`、`X-Request-ID: {uuid}`。
  - 响应格式：`{ "code": 0, "message": "success", "data": {}, "requestId": "xxx" }`。

#### 4.4.2 实时通道：消息队列（RabbitMQ）

- **适用场景**：设备状态实时上报、质量数据实时采集、高并发报工场景。
- **技术实现**：
  - MES 作为生产者，将实时数据发布至 RabbitMQ 指定 Exchange（Topic 模式）。
  - CAPP 作为消费者，通过 PHP AMQP 扩展（`php-amqplib`）订阅队列，异步消费消息。
  - 队列设计：
    - `mes.device.status`：设备状态变更消息。
    - `mes.quality.data`：质量检验数据消息。
    - `mes.report.operation`：工序报工消息。
- **优势**：削峰填谷，解耦系统，确保高并发场景下 CAPP 不会被压垮。

#### 4.4.3 批量通道：数据库中间表

- **适用场景**：历史报工数据批量导入、夜班/节假日期间 MES 离线数据补录、大批量质量数据回传。
- **技术实现**：MES 将数据写入中间库（独立 MySQL 实例），CAPP 定时扫描并抽取。

### 4.5 同步策略

| 数据类别 | 同步方向 | 策略 | 触发条件 | 技术实现 |
|---------|---------|------|---------|---------|
| 工艺路线 | CAPP → MES | 版本化全量下发 | 工艺发布/变更时 | REST API 推送 |
| 生产工单 | CAPP → MES | 增量同步 | ERP 生产订单下达后，CAPP 生成工单并推送 | REST API 推送 |
| 工序报工 | MES → CAPP | 准实时同步 | MES 报工提交后 | REST API 回调 + 消息队列 |
| 质量数据 | MES → CAPP | 实时同步 | 检验完成后 | 消息队列 + REST API |
| 设备状态 | MES → MES | 实时流 | 设备 PLC 状态变更 | 消息队列（秒级） |
| 物料追溯 | MES → CAPP | 实时同步 | 工序领料/投料时 | REST API 回调 |

### 4.6 业务场景

#### 4.6.1 工艺下发场景

**场景描述**：某型号工业压缩机（如 GMJ-2024-006）的工艺路线在 CAPP 中编制完成并审核发布后，需要将完整的工艺信息下发至 MES，以便车间现场按工艺执行。

**业务流程**：

1. CAPP 工艺路线状态变更为"已发布"。
2. 系统自动触发"工艺下发 MES"事件（或工艺主管手动触发）。
3. CAPP 工艺下发服务执行：
   - 读取该产品的完整工艺路线、所有工序信息、工艺参数、作业指导书、关联图纸文件。
   - 将数据组装为 MES 标准 JSON 格式。
   - 调用 MES API `POST /api/v1/process/import`。
4. MES 接收工艺数据：
   - 校验工艺版本是否已存在（版本控制）。
   - 若为新版本，创建工艺路线主记录和工序明细记录。
   - 下载图纸文件至 MES 文件服务器，生成内部访问 URL。
   - 将作业指导书内容关联至对应工序的工位终端（触摸屏/平板）。
5. MES 返回处理结果：
   - 成功：返回 MES 工艺版本 ID，CAPP 更新 `mes_sync_status = 1`。
   - 失败：返回错误码和原因，CAPP 记录失败日志，进入重试队列，通知工艺主管。
6. 车间工位终端刷新后，操作工可在屏幕上查看最新作业指导书和图纸。

#### 4.6.2 工单接收场景

**场景描述**：U8 ERP 下达生产订单后，CAPP 生成内部生产任务单，并进一步拆分为 MES 生产工单，下发至车间执行。

**业务流程**：

1. CAPP 接收 U8 生产订单（见 3.6.3 场景）。
2. CAPP 生产调度模块运行排产算法：
   - 根据产品工艺路线，将生产订单拆分为若干工序级工单。
   - 计算每道工序的计划开工/完工时间（考虑设备产能、人员班次）。
   - 分配具体设备（如数控车床 CK-03、焊接机器人 HW-01）。
3. 调度员在 CAPP 界面确认工单拆分结果，点击"下发 MES"。
4. CAPP 调用 MES API `POST /api/v1/workorder/create`，发送工单列表。
5. MES 创建工单：
   - 校验产品编码、工艺版本有效性。
   - 创建工单主记录和工序作业计划。
   - 向对应工位推送"新工单待开工"通知。
6. MES 返回工单创建结果，CAPP 更新工单状态为"已下发"。

#### 4.6.3 报工数据回传场景

**场景描述**：车间操作工在 MES 工位终端完成某道工序加工后，进行报工（录入实际工时、完工数量、报废数量等）。MES 将报工数据实时回传至 CAPP，用于生产进度跟踪和工时定额分析。

**业务流程**：

1. 操作工在 MES 工位终端点击"完工报工"。
2. MES 校验报工数据合法性（数量不能为负、工时不能超限）。
3. MES 保存报工记录，同时触发数据回传：
   - 方式 A（实时）：调用 CAPP API `POST /api/v1/mes/report` 推送报工数据。
   - 方式 B（消息队列）：将报工消息发布至 RabbitMQ `mes.report.operation` 队列。
4. CAPP 接收报工数据：
   - 校验工单号、工序序号有效性。
   - 写入 `mes_operation_report` 表。
   - 更新对应生产任务单的累计完工数量、进度百分比。
5. 若实际工时与标准工时偏差 > 20%，系统自动标记该记录，推送告警给工艺主管，提示可能需要优化工时定额。
6. 若报废数量 > 0，触发质量异常流程，通知质检员介入。

#### 4.6.4 质量追溯场景

**场景描述**：工业压缩机作为高压特种设备，质量追溯要求极高。每一道工序的检验数据、物料批次、设备参数都需要完整记录，实现单台产品的全生命周期质量追溯。

**业务流程**：

1. 工序加工完成后，质检员在 MES 中进行质量检验（首检、巡检、完工检）。
2. MES 记录检验数据：检验项、实测值、检验结果、不合格原因、检验员、时间戳。
3. 对于关键工序（如密封件成型、缸体焊接、气密性试验），MES 同时记录：
   - 设备运行参数（成型温度、焊接电流、试验压力）。
   - 物料批次信息（原材料炉批号、供应商批次号）。
4. MES 将质量数据和追溯数据实时推送至 CAPP。
5. CAPP 质量追溯模块构建追溯链：
   - 以产品序列号为根节点，关联所有工序的检验记录、设备参数、物料批次、操作人员。
   - 生成"单台产品质量档案"。
6. 若后续发现某批原材料存在质量问题，CAPP 可通过追溯链反向查询使用了该批次的所有产品序列号，快速定位受影响范围。

### 4.8 实时数据交互设计

#### 4.8.1 消息队列架构

```
┌─────────────┐     ┌─────────────────┐     ┌─────────────┐
│   MES 系统   │────▶│  RabbitMQ Broker │────▶│  CAPP 系统   │
│  (生产者)   │     │  (消息中间件)     │     │  (消费者)   │
└─────────────┘     └─────────────────┘     └─────────────┘
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
        ┌─────────┐  ┌─────────┐  ┌─────────┐
        │mes.device│  │mes.quality│  │mes.report│
        │.status   │  │.data    │  │.operation│
        └─────────┘  └─────────┘  └─────────┘
```

#### 4.8.2 队列设计规范

| 队列名称 | Exchange | Routing Key | 消息格式 | 持久化 | TTL |
|---------|---------|------------|---------|--------|-----|
| `mes.device.status` | `mes.topic` | `device.status.{workshop}` | JSON | 是 | 24小时 |
| `mes.quality.data` | `mes.topic` | `quality.data.{workshop}` | JSON | 是 | 72小时 |
| `mes.report.operation` | `mes.topic` | `report.operation.{workshop}` | JSON | 是 | 72小时 |
| `mes.material.trace` | `mes.topic` | `material.trace.{workshop}` | JSON | 是 | 30天 |

#### 4.8.3 消费者设计（PHP）

CAPP 系统部署独立的 PHP CLI 消费者进程（使用 `php-amqplib` 库），以守护进程方式运行：

- **进程管理**：使用 `supervisord` 或 systemd 管理消费者进程，确保崩溃后自动重启。
- **并发消费**：每个队列启动 2-4 个消费者进程，提升吞吐量。
- **消息确认**：消费者处理成功后发送 `basic_ack`，处理失败发送 `basic_nack` 并选择是否重新入队（超过最大重试次数后转入死信队列）。
- **死信队列（DLQ）**：`mes.dlq.{original_queue}`，用于存储无法处理的消息，人工排查后手动重放或丢弃。

#### 4.8.4 实时数据展示

- CAPP 生产监控大屏通过 WebSocket（PHP 可借助 `Workerman` 或 `Swoole`）将实时报工、设备状态、质量告警推送至前端。
- 车间主任、调度员可在监控中心实时查看各工位生产状态、设备利用率、质量合格率。

## 5. 通用对接框架

### 5.1 统一对接网关设计

为避免 CAPP 系统与每个外部系统直接耦合，引入**统一对接网关（Integration Gateway）**层。该层作为所有外部系统通信的统一出入口，负责协议转换、认证鉴权、流量控制、路由分发。

#### 5.1.1 网关架构

#### 5.1.2 网关核心功能

| 功能模块 | 职责 | 技术实现（PHP原生） |
|---------|------|-------------------|
| **协议适配** | 支持 SOAP、REST、消息队列、数据库等多种协议的无缝切换 | 工厂模式：`SoapAdapter`、`RestAdapter`、`MqAdapter`、`DbAdapter` |
| **认证鉴权** | 统一验证外部系统身份，防止未授权访问 | HMAC-SHA256 签名验证、Bearer Token 解析、IP 白名单校验 |
| **流量控制** | 限流、熔断、防重放攻击 | 基于 Redis 的令牌桶算法限流；失败率 > 阈值时自动熔断 |
| **路由分发** | 根据请求路径/消息类型路由至对应业务处理器 | 路由表配置在 `sync_gateway_route` 表中，支持动态刷新 |
| **请求/响应转换** | 统一外部报文格式与 CAPP 内部数据格式的转换 | 数据转换引擎（见 5.2） |
| **日志拦截** | 记录所有经过网关的请求和响应 | 中间件模式，记录至 `sync_gateway_log` 表 |

### 5.2 数据转换引擎

数据转换引擎负责在不同系统的数据格式、编码规范、字段语义之间进行自动化转换。

#### 5.2.1 引擎架构

```
[源数据] ──▶ [解析器 Parser] ──▶ [映射层 Mapper] ──▶ [转换器 Transformer] ──▶ [校验器 Validator] ──▶ [目标数据]
                │                    │                    │                    │
                ▼                    ▼                    ▼                    ▼
           XML/JSON/CSV        字段映射规则          类型转换/编码转换      必填/范围/正则
           解析为PHP数组        数据映射表配置         自定义转换脚本         业务规则校验
```

#### 5.2.2 转换规则类型

| 规则类型 | 说明 | 示例 |
|---------|------|------|
| **直接映射** | 字段一对一复制 | `cInvCode` → `material_code` |
| **类型转换** | 数据类型转换 | U8 中 `iStatus` 为 INT，CAPP 中映射为 TINYINT 并 +1 偏移 |
| **编码映射** | 枚举值字典转换 | PLM 设计状态 `Design` → CAPP `0`，`Release` → CAPP `2` |
| **日期格式转换** | 不同日期字符串格式互转 | PLM `2024/06/15 08:30:00` → CAPP `2024-06-15 08:30:00` |
| **单位换算** | 计量单位换算 | U8 工时单位为小时，CAPP 为分钟，转换规则 `×60` |
| **JSON 展开/聚合** | 嵌套结构扁平化或反向 | PLM `SPECIFICATION` JSON 展开为 CAPP 多个字段 |
| **自定义脚本** | 复杂业务逻辑转换 | PHP 闭包函数，支持自定义计算和条件判断 |

#### 5.2.3 转换规则配置表 `sync_transform_rule`

```sql
CREATE TABLE `sync_transform_rule` (
```

### 5.3 消息队列设计

消息队列作为 CAPP 与外部系统异步解耦的核心基础设施，承担削峰填谷、可靠传输、顺序保证等关键职责。

#### 5.3.1 队列总体架构

```
┌─────────────────────────────────────────────────────────────┐
│                    RabbitMQ 消息中间件                       │
│                                                             │
│  Exchange: capp.topic                                       │
│                                                             │
│  Routing Keys:                                              │
│    - plm.product.change    ──▶ Queue: plm_product_queue     │
│    - plm.bom.change        ──▶ Queue: plm_bom_queue         │
│    - plm.eco.notify        ──▶ Queue: plm_eco_queue         │
│    - u8.mo.new             ──▶ Queue: u8_mo_queue            │
│    - u8.inventory.update   ──▶ Queue: u8_inventory_queue      │
│    - mes.report.operation  ──▶ Queue: mes_report_queue       │
│    - mes.quality.data      ──▶ Queue: mes_quality_queue     │
│    - mes.device.status     ──▶ Queue: mes_device_queue      │
│                                                             │
│  Dead Letter Exchange: capp.dlx                              │
│  Dead Letter Queues:                                        │
│    - dlq.plm_product_queue                                  │
│    - dlq.mes_report_queue                                   │
│    ...                                                      │
└─────────────────────────────────────────────────────────────┘
```

#### 5.3.2 消息格式规范

所有经过消息队列传输的消息采用统一信封格式：

```json
{
  "messageId": "uuid-v4",
  "messageType": "mes.report.operation",
  "version": "1.0",
  "timestamp": "2024-06-15T08:30:00.000+08:00",
  "sourceSystem": "MES",
  "targetSystem": "CAPP",
  "priority": 1,
  "payload": {
    // 具体业务数据
  },
  "traceId": "trace-uuid-for-distributed-tracing"
}
```

#### 5.3.3 消息可靠性保障

- **生产者确认（Publisher Confirm）**：CAPP 作为生产者发送消息时，等待 Broker 返回 ACK 后才认为发送成功。
- **消费者确认（Consumer Ack）**：消费者处理完业务逻辑后，显式发送 ACK；处理失败时发送 NACK 并根据重试策略决定重新入队或转入死信队列。
- **消息持久化**：队列和消息均标记为持久化（`durable=true`，`delivery_mode=2`），确保 RabbitMQ 重启后消息不丢失。
- **幂等性设计**：消费者根据 `messageId` 进行幂等校验，防止重复消费导致数据重复写入。

### 5.4 监控与告警

#### 5.4.1 监控指标体系

| 监控维度 | 指标名称 | 采集方式 | 告警阈值 |
|---------|---------|---------|---------|
| **可用性** | 外部系统 API 可用率 | 定时探测（每 5 分钟） | 可用率 < 95% 告警 |
| **性能** | API 平均响应时间 | 网关日志统计 | P99 > 5s 告警 |
| **吞吐量** | 每分钟同步记录数 | 同步日志统计 | 突降 50% 告警 |
| **准确性** | 同步失败率 | 同步日志统计 | 失败率 > 5% 告警 |
| **延迟** | 消息队列消费延迟 | RabbitMQ 管理 API | 堆积 > 1000 条告警 |
| **数据一致性** | 日终对账差异率 | 对账任务结果 | 差异率 > 0.1% 告警 |

#### 5.4.2 告警通道

- **即时通知**：企业微信/钉钉/短信，用于致命和严重级别异常。
- **邮件通知**：用于一般级别异常和每日同步汇总报告。
- **系统内通知**：CAPP 系统消息中心推送待办和告警，登录用户即时可见。

#### 5.4.3 监控大屏

CAPP 管理后台提供"系统对接监控中心"大屏，实时展示：

- 各外部系统连接状态（在线/离线）。
- 最近 24 小时同步成功/失败趋势图。
- 各同步类型实时吞吐量（折线图）。
- 消息队列各队列堆积情况（柱状图）。
- 当前待处理冲突列表（表格）。
- 最近 10 条异常告警（滚动列表）。

### 5.5 日志与审计

#### 5.5.1 日志分级

| 级别 | 标识 | 记录内容 | 保留期限 |
|------|------|---------|---------|
| **DEBUG** | 调试 | 详细请求/响应报文、SQL 语句 | 7 天 |
| **INFO** | 信息 | 同步开始/结束、正常处理记录 | 90 天 |
| **WARN** | 警告 | 重试发生、响应慢、非关键字段缺失 | 180 天 |
| **ERROR** | 错误 | 同步失败、校验失败、API 异常 | 2 年 |
| **FATAL** | 致命 | 系统宕机、数据库连接中断、安全攻击 | 永久 |

#### 5.5.2 审计要求

- **操作审计**：所有手动触发的同步操作（如"手动下发 BOM"、"强制覆盖冲突"）记录操作人、操作时间、操作内容、操作结果。
- **数据审计**：关键业务数据（如 BOM 版本、工艺参数）的每次变更记录变更前/后值、变更人、变更原因。
- **安全审计**：所有 API 认证失败、越权访问、异常 IP 请求记录至安全审计日志，保留永久。

#### 5.5.3 日志存储

- **数据库日志**：结构化日志（同步记录、冲突记录、审计记录）存储于 MySQL，按时间分区（每月独立分区）。
- **文件日志**：PHP 应用日志使用 `error_log` 或独立日志类写入本地文件，按日期轮转（`capp_sync_YYYY-MM-DD.log`）。
- **归档策略**：超过保留期限的日志自动归档至对象存储或压缩备份，释放在线存储空间。

### 6.2 对接开发规范

1. **接口版本控制**：所有 REST API 路径包含版本号（如 `/api/v1/...`），版本升级时保留旧版本至少 6 个月。
2. **幂等性设计**：所有写操作接口支持幂等键（`Idempotency-Key` Header），防止网络重试导致重复写入。
3. **超时与重试**：HTTP 调用超时默认 30 秒，重试间隔采用指数退避（1s, 2s, 4s, 8s, 16s）。
4. **错误码规范**：统一错误码格式 `{ "code": 10001, "message": "物料编码不存在", "detail": "..." }`，错误码文档集中维护。
5. **测试规范**：每个对接接口必须包含单元测试（Mock 外部服务）和联调测试（连接真实环境测试库）。

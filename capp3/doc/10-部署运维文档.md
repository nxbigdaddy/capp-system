## 1. 系统环境要求

### 1.1 服务器硬件配置

CAPP系统作为企业核心工艺管理系统，其服务器硬件配置需根据并发用户规模、数据量和业务复杂度进行合理规划。以下为不同规模企业的推荐配置方案：

**小型部署方案（并发用户≤50，工艺数据≤10万条）**

| 组件 | 配置要求 | 说明 |
|------|---------|------|
| CPU | 4核 Intel Xeon 或 AMD EPYC | 主频≥2.4GHz |
| 内存 | 16GB DDR4 ECC | 操作系统及数据库缓存使用 |
| 系统盘 | 256GB SSD | 操作系统、应用程序、日志文件 |
| 数据盘 | 500GB SSD RAID1 | 数据库文件、附件存储 |
| 网卡 | 千兆以太网×2 | 双网卡绑定冗余 |

**中型部署方案（并发用户50-200，工艺数据10-100万条）**

| 组件 | 配置要求 | 说明 |
|------|---------|------|
| CPU | 8核 Intel Xeon 或 AMD EPYC | 主频≥2.6GHz |
| 内存 | 32GB DDR4 ECC | 支持MySQL InnoDB Buffer Pool扩展 |
| 系统盘 | 512GB NVMe SSD | 高IOPS保障系统响应速度 |
| 数据盘 | 1TB SSD RAID10 | 数据库与附件分离存储 |
| 网卡 | 千兆以太网×2 | 业务网与管理网分离 |

**大型部署方案（并发用户≥200，工艺数据≥100万条）**

| 组件 | 配置要求 | 说明 |
|------|---------|------|
| CPU | 16核 Intel Xeon 或 AMD EPYC | 主频≥2.8GHz，支持虚拟化 |
| 内存 | 64GB DDR4 ECC | 支持多实例数据库缓存 |
| 系统盘 | 512GB NVMe SSD RAID1 | 操作系统与应用程序高可用 |
| 数据盘 | 2TB SSD RAID10 | 数据库专用存储阵列 |
| 附件存储 | 4TB SATA HDD RAID5 | 工艺文件、图纸附件冷存储 |
| 网卡 | 万兆以太网×2 | 高并发数据传输保障 |

### 1.2 操作系统要求

系统支持以下Linux发行版作为服务器操作系统，推荐使用CentOS Stream或Ubuntu LTS版本以获得长期支持：

| 操作系统 | 推荐版本 | 支持状态 | 备注 |
|---------|---------|---------|------|
| CentOS Stream | 9.x | 首选推荐 | 与RHEL生态兼容，企业级稳定性 |
| Ubuntu Server | 22.04 LTS | 推荐 | 社区活跃，软件包更新及时 |
| Rocky Linux | 9.x | 支持 | CentOS替代方案，二进制兼容RHEL |
| AlmaLinux | 9.x | 支持 | 同样为CentOS替代方案 |
| Windows Server | 2019/2022 | 有限支持 | 仅用于特定场景，性能较Linux低 |

**操作系统基础配置要求**

- 文件系统：根分区使用ext4或xfs，数据库分区建议使用xfs以支持大文件
- 时区设置：统一设置为Asia/Shanghai（CST，UTC+8），确保日志时间戳和业务时间一致
- 主机名规范：采用`capp-[环境]-[角色]-[序号]`格式，如`capp-prod-web-01`
- 防火墙：启用firewalld或ufw，仅开放业务所需端口
- SELinux：生产环境建议启用Enforcing模式，需配置CAPP系统所需策略规则
- 内核参数：调整文件描述符限制（fs.file-max≥65535）、TCP连接参数、内存分配策略

### 1.3 PHP运行环境

CAPP系统基于PHP原生开发，不依赖任何第三方框架，对PHP版本和扩展有明确要求：

**PHP版本要求**

- 最低版本：PHP 8.0.0
- 推荐版本：PHP 8.2.x
- 禁止版本：PHP 7.x及以下（已停止安全更新，且不支持现代语法特性）

**必需PHP扩展**

| 扩展名称 | 最低版本 | 功能说明 | 安装方式 |
|---------|---------|---------|---------|
| mysqli/pdo_mysql | 内置 | MySQL数据库连接与操作 | 编译或包管理器安装 |
| gd | 2.3.0 | 图像处理（验证码、缩略图、水印） | 编译或包管理器安装 |
| mbstring | 内置 | 多字节字符串处理（中文支持） | 编译或包管理器安装 |
| json | 内置 | JSON数据编码解码 | 默认启用 |
| openssl | 内置 | HTTPS请求、数据加密、密码哈希 | 默认启用 |
| fileinfo | 内置 | 文件类型检测（上传文件安全检查） | 默认启用 |
| zip | 内置 | 压缩包处理（批量导入导出） | 编译或包管理器安装 |
| xml | 内置 | XML数据解析（与PDM/ERP集成） | 默认启用 |
| curl | 内置 | HTTP客户端（企业微信API、AI服务调用） | 编译或包管理器安装 |
| redis | 5.3.0 | Redis缓存与会话存储（可选但强烈推荐） | PECL安装 |
| bcmath | 内置 | 高精度数学计算（工时定额、材料核算） | 默认启用 |
| intl | 内置 | 国际化支持（日期格式、货币格式） | 编译或包管理器安装 |

**PHP核心配置参数**

```ini
; 内存限制，根据业务复杂度调整，工艺卡片生成可能消耗较大内存
memory_limit = 512M

; 上传文件大小限制，需支持工艺图纸、三维模型等大文件
upload_max_filesize = 50M
post_max_size = 50M

; 执行时间限制，复杂报表生成和批量导出需要较长时间
max_execution_time = 300
max_input_time = 300

; 会话配置，使用Redis存储会话以支持多实例部署
session.save_handler = redis
session.save_path = "tcp://127.0.0.1:6379?auth=password"
session.gc_maxlifetime = 3600

; 时区设置
date.timezone = Asia/Shanghai

; 错误显示，生产环境关闭错误输出至页面
display_errors = Off
log_errors = On
error_log = /var/log/php/error.log

; OPcache配置，生产环境必须启用以提升性能
opcache.enable = 1
opcache.memory_consumption = 256
opcache.max_accelerated_files = 10000
opcache.revalidate_freq = 60
opcache.validate_timestamps = 0  ; 生产环境关闭，升级时手动刷新
```

### 1.4 MySQL数据库环境

MySQL作为CAPP系统的数据持久化存储，其版本和配置直接影响系统性能和数据安全：

**MySQL版本要求**

- 最低版本：MySQL 8.0.20
- 推荐版本：MySQL 8.0.35+ 或 MySQL 8.1.x
- 替代方案：MariaDB 10.6.x（需验证兼容性）
- 禁止版本：MySQL 5.7及以下（已停止官方支持，且不支持JSON类型、窗口函数等现代特性）

**MySQL核心配置参数**

```ini
[mysqld]
; 服务器标识
server-id = 1

; 数据目录与字符集
datadir = /var/lib/mysql
character-set-server = utf8mb4
collation-server = utf8mb4_unicode_ci

; InnoDB引擎配置
default_storage_engine = InnoDB
innodb_buffer_pool_size = 8G          ; 建议设置为物理内存的50%-75%
innodb_buffer_pool_instances = 8
innodb_log_file_size = 1G
innodb_log_buffer_size = 64M
innodb_flush_log_at_trx_commit = 2    ; 平衡性能与持久性
innodb_flush_method = O_DIRECT
innodb_file_per_table = 1

; 连接配置
max_connections = 500
max_connect_errors = 1000
wait_timeout = 3600
interactive_timeout = 3600

; 查询缓存与优化（MySQL 8.0已移除查询缓存，依赖应用层缓存）
query_cache_type = 0
query_cache_size = 0

; 临时表与排序
tmp_table_size = 128M
max_heap_table_size = 128M
sort_buffer_size = 8M
join_buffer_size = 8M

; 日志配置
slow_query_log = 1
slow_query_log_file = /var/log/mysql/slow.log
long_query_time = 2
log_error = /var/log/mysql/error.log

; 二进制日志（主从复制必需）
log_bin = /var/lib/mysql/binlog
binlog_format = ROW
binlog_expire_logs_seconds = 604800   ; 7天自动清理

; 性能模式（监控诊断使用）
performance_schema = ON
```

### 1.5 Web服务器配置

系统支持Nginx和Apache作为Web服务器，强烈推荐使用Nginx以获得更高的并发处理能力和更低的资源消耗：

**Nginx推荐版本**：1.24.x（稳定版）或 1.25.x（主线版）

**Nginx核心配置**

```nginx
# 工作进程与连接数
worker_processes auto;
worker_rlimit_nofile 65535;

events {
    worker_connections 4096;
    use epoll;
    multi_accept on;
}

http {
    # 基础配置
    include       mime.types;
    default_type  application/octet-stream;
    
    # 日志格式
    log_format main '$remote_addr - $remote_user [$time_local] "$request" '
                    '$status $body_bytes_sent "$http_referer" '
                    '"$http_user_agent" "$http_x_forwarded_for" '
                    '$request_time $upstream_response_time';
    
    access_log /var/log/nginx/access.log main;
    error_log /var/log/nginx/error.log warn;
    
    # 性能优化
    sendfile on;
    tcp_nopush on;
    tcp_nodelay on;
    keepalive_timeout 65;
    keepalive_requests 1000;
    
    # Gzip压缩
    gzip on;
    gzip_vary on;
    gzip_proxied any;
    gzip_comp_level 6;
    gzip_types text/plain text/css text/xml application/json 
               application/javascript application/xml+rss 
               application/atom+xml image/svg+xml;
    
    # 客户端上传限制
    client_max_body_size 50M;
    client_body_buffer_size 512k;
    
    # 限流配置（防暴力破解）
    limit_req_zone $binary_remote_addr zone=login:10m rate=10r/s;
    limit_req_zone $binary_remote_addr zone=api:10m rate=100r/s;
}
```

### 2.3 高可用设计

**Web层高可用**

- 负载均衡：采用Nginx或HAProxy实现多Web服务器的负载分发，支持轮询、最少连接、IP哈希等策略
- 会话保持：使用Redis集中存储用户会话，任意Web节点故障时用户无感知切换
- 健康检查：负载均衡器每5秒检测后端节点健康状态，连续2次失败即剔除，恢复后自动加入

**应用层高可用**

- PHP-FPM多实例：单台服务器运行多个PHP-FPM进程池，配置pm.max_children根据内存动态计算
- 无状态设计：应用层不保存本地状态，所有状态数据（会话、缓存、队列）存储于Redis或MySQL
- 快速扩容：新节点部署后仅需配置Nginx upstream即可加入集群，无需数据迁移

**数据层高可用**

- MySQL主从复制：一主两从架构，主库负责写操作，从库负责读操作和备份
- 自动故障转移：使用Orchestrator或MHA实现主库故障时的自动切换，切换时间≤30秒
- 数据一致性：主从复制采用ROW格式，确保数据变更的精确复制；关键业务读取主库避免延迟

### 6.4 配置文件管理规范

- 生产环境配置文件（`.env`）禁止提交至版本控制系统（Git）

- 定期（每季度）轮换数据库密码和API密钥

**配置变更流程**

1. 配置变更需在测试环境验证通过后，通过运维工单提交变更申请
2. 变更操作由双人复核，一人执行、一人确认
3. 变更前自动备份原配置文件至 `/var/www/capp/backup/config/`
4. 变更后重启应用服务并验证健康检查接口
5. 变更记录登记至配置管理台账

| 二进制日志 | 实时 | 7天 | 本地NAS | 持续 |
| 关键表导出 | 每日 | 30天 | 本地NAS | 01:30 |

**全量备份脚本**

```bash
#!/bin/bash
# /opt/scripts/backup_mysql_full.sh

BACKUP_DIR="/var/www/capp/backup/db"
DATE=$(date +%Y%m%d_%H%M%S)
DB_NAME="capp_db"
RETENTION_DAYS=28

# 创建备份目录
mkdir -p ${BACKUP_DIR}/${DATE}

# 执行物理全量备份（使用xtrabackup或mysqldump）
mysqldump -u capp_backup -p'BackupP@ssw0rd_2024' \
    --single-transaction \
    --routines \
    --triggers \
    --events \
    --master-data=2 \
    --databases ${DB_NAME} \
    | gzip > ${BACKUP_DIR}/${DATE}/${DB_NAME}_full.sql.gz

# 备份状态检查
if [ ${PIPESTATUS[0]} -eq 0 ]; then
    echo "[$(date)] 数据库全量备份成功: ${DATE}" >> /var/log/capp/backup.log
    # 计算校验和
    md5sum ${BACKUP_DIR}/${DATE}/${DB_NAME}_full.sql.gz > ${BACKUP_DIR}/${DATE}/checksum.md5
else
    echo "[$(date)] 数据库全量备份失败: ${DATE}" >> /var/log/capp/backup.log
    # 发送告警（调用告警脚本）
    /opt/scripts/alert.sh "数据库备份失败" "全量备份异常，请立即检查"
    exit 1
fi

# 清理过期备份
find ${BACKUP_DIR} -maxdepth 1 -type d -mtime +${RETENTION_DAYS} -exec rm -rf {} \;

# 同步至异地备份服务器
rsync -avz --delete ${BACKUP_DIR}/ backup-server:/backup/capp/db/
```

## 10. 故障处理

### 10.1 常见问题排查

**问题1：页面加载缓慢或超时**

排查步骤：
1. 检查服务器资源：CPU、内存、磁盘I/O是否达到瓶颈
2. 检查Nginx错误日志，定位是连接超时还是PHP处理超时
3. 检查MySQL慢查询日志，定位是否存在未优化SQL
4. 检查Redis连接状态，确认会话和缓存服务正常
5. 检查网络延迟：ping和traceroute测试网络连通性

常见原因与处理：
- PHP-FPM进程不足：调整pm.max_children参数，增加进程池容量
- 数据库锁等待：通过`SHOW PROCESSLIST`定位阻塞会话，必要时KILL阻塞进程
- 缓存失效导致数据库压力：检查Redis内存使用率和键驱逐情况
- 大文件上传阻塞：检查磁盘I/O和网络带宽，限制并发上传数

**问题2：数据库连接失败**

排查步骤：
1. 测试网络连通性：`telnet db_host 3306`
2. 检查MySQL服务状态：`systemctl status mysqld`
3. 检查MySQL错误日志：`/var/log/mysql/error.log`
4. 检查连接数是否耗尽：`SHOW STATUS LIKE 'Threads_connected'`
5. 检查防火墙规则是否变动

常见原因与处理：
- 连接数耗尽：临时调大max_connections，长期优化连接池配置和SQL性能
- 账号权限问题：检查用户来源IP是否匹配，密码是否过期
- 主从切换后应用未更新配置：检查应用配置中的数据库地址是否为VIP或当前主库

**问题3：文件上传失败**

排查步骤：
1. 检查PHP上传限制：`upload_max_filesize`和`post_max_size`
2. 检查磁盘空间：`df -h`确认上传目录所在分区空间充足
3. 检查目录权限：`ls -ld /var/www/capp/uploads`确认Web用户可写
4. 检查Nginx限制：`client_max_body_size`配置
5. 检查文件类型白名单：确认上传文件扩展名在允许列表中

**问题4：企业微信集成异常**

排查步骤：
1. 检查企业微信应用配置：CorpID、AgentID、Secret是否正确
2. 检查回调URL可访问性：确保企业微信服务器能访问CAPP回调地址
3. 检查IP白名单：企业微信后台是否配置了CAPP服务器出口IP
4. 检查HTTPS证书：企业微信要求回调地址必须为有效HTTPS
5. 查看企业微信API调用日志，定位具体错误码

### 10.2 应急响应预案

**预案A：数据库主库故障**

1. **检测**：监控告警发现主库不可连接或复制中断
2. **确认**：运维工程师通过独立通道确认主库状态（非网络分区假死）
3. **切换**：执行自动或手动故障转移，将从库提升为新主库
4. **通知**：通过企业微信通知技术负责人和业务负责人
5. **恢复**：修复原主库后作为新从库加入集群
6. **复盘**：故障恢复后24小时内完成故障复盘报告

**预案B：系统遭受网络攻击**

1. **检测**：WAF或日志分析发现异常流量（如大量登录尝试、SQL注入特征）
2. **阻断**：立即在防火墙层面阻断攻击源IP段，启用CDN防护
3. **分析**：保存攻击日志，分析攻击手法和影响范围
4. **加固**：根据攻击特征临时提升安全策略（如加强验证码、限制登录频率）
5. **恢复**：确认无入侵成功后逐步恢复正常访问策略
6. **上报**：如涉及数据泄露，按《网络安全事件应急预案》上报监管部门

**预案C：数据误删除或损坏**

1. **止损**：立即停止相关服务，防止数据覆盖
2. **评估**：确认数据损坏范围和影响业务
3. **恢复**：从最近全量备份+二进制日志恢复至故障前时间点
4. **验证**：在隔离环境验证恢复数据完整性
5. **上线**：经业务负责人确认后切换至恢复后的数据
6. **复盘**：分析误操作原因，完善权限控制和操作审计

## 11. 升级方案

### 11.1 版本升级流程

CAPP系统版本升级遵循蓝绿部署或滚动发布策略，确保升级过程业务中断时间最小化：

**升级前准备**

1. **版本评审**：开发团队提交升级包和《版本发布说明》，包含变更清单、影响范围、回滚方案
2. **测试验证**：升级包在测试环境完成功能测试、性能测试、兼容性测试
3. **备份确认**：升级前完成全量数据库备份和文件备份，验证备份可恢复
4. **窗口确认**：与业务部门确认升级时间窗口，通常选择周末或夜间低峰期
5. **通知发布**：提前24小时通过企业微信通知用户升级计划和预计影响

**升级执行步骤**

```bash
#!/bin/bash
# /opt/scripts/deploy_upgrade.sh

VERSION=$1
BACKUP_DIR="/var/www/capp/backup/releases"
APP_DIR="/var/www/capp/app"

# 1. 前置检查
echo "=== 升级前检查 ==="
php -v
nginx -t
mysql -u capp_user -p -e "SELECT 1" || exit 1

# 2. 备份当前版本
cp -r ${APP_DIR}/releases/current ${BACKUP_DIR}/rollback-$(date +%Y%m%d%H%M%S)

# 3. 解压新版本
mkdir -p ${APP_DIR}/releases/${VERSION}
tar -xzf /tmp/capp-${VERSION}.tar.gz -C ${APP_DIR}/releases/${VERSION}/

# 4. 迁移配置文件
cp ${APP_DIR}/releases/current/config/*.env ${APP_DIR}/releases/${VERSION}/config/

# 5. 执行数据库迁移
php ${APP_DIR}/releases/${VERSION}/scripts/db_migrate.php --env=production

# 6. 切换符号链接（原子操作）
ln -sfn ${APP_DIR}/releases/${VERSION} ${APP_DIR}/current

# 7. 清理OPcache（使新代码生效）
php -r "opcache_reset();"

# 8. 平滑重载PHP-FPM和Nginx
systemctl reload php-fpm
systemctl reload nginx

# 9. 健康检查
sleep 5
curl -sf https://capp.company.local/api/health || {
    echo "健康检查失败，执行回滚"
    # 自动回滚逻辑...
    exit 1
}

echo "=== 升级完成: ${VERSION} ==="
```

**升级后验证**

1. 执行核心业务流程验证（登录→工艺查询→编辑→保存→审批）
2. 检查错误日志，确认无新增异常
3. 监控关键性能指标，确认无性能退化
4. 收集用户反馈，确认无功能异常

### 11.2 数据库迁移策略

数据库结构变更通过版本化迁移脚本管理，确保升级和回滚的可控性：

**迁移脚本规范**

- 命名规则：`V{版本号}__{描述}.sql`，如 `V1.1.0__add_process_template_table.sql`
- 脚本内容：每个迁移脚本必须包含`UP`（升级）和`DOWN`（回滚）两部分
- 事务控制：每个迁移脚本在事务中执行，失败自动回滚
- 幂等性：迁移脚本需支持重复执行不报错（`IF NOT EXISTS`）

**迁移脚本示例**


### 11.3 回滚策略

当升级后出现严重问题且无法快速修复时，执行版本回滚：

**快速回滚（应用层）**

1. 恢复符号链接至上一稳定版本：`ln -sfn releases/v1.0.0 current`
2. 清理OPcache：`php -r "opcache_reset();"`
3. 重载PHP-FPM和Nginx
4. 验证健康检查接口

**完整回滚（含数据库）**

1. 停止应用服务，防止新数据写入
2. 评估数据变更范围：对比升级前后的数据差异
3. 执行数据库回滚脚本（DOWN部分）
4. 如数据库变更复杂，从升级前全量备份恢复，再应用二进制日志回滚至升级前时间点
5. 恢复应用代码至上一版本
6. 启动服务并验证

**回滚时间目标**

- 仅应用回滚：≤5分钟
- 含数据库回滚：≤30分钟（需提前准备回滚脚本和备份验证）

## 12. 安全加固

### 12.1 网络安全

**防火墙策略**

```bash
# 使用firewalld配置基础策略
# 1. 默认拒绝所有入站连接
firewall-cmd --set-default-zone=drop

# 2. 允许已建立的连接和回包
firewall-cmd --permanent --direct --add-rule ipv4 filter INPUT 0 -m state --state ESTABLISHED,RELATED -j ACCEPT

# 3. 允许回环接口
firewall-cmd --permanent --direct --add-rule ipv4 filter INPUT 0 -i lo -j ACCEPT

# 4. 允许SSH（仅管理区）
firewall-cmd --permanent --direct --add-rule ipv4 filter INPUT 0 -p tcp --dport 22 -s 203.0.113.10/24 -j ACCEPT

# 5. 允许HTTP/HTTPS（办公区+DMZ）
firewall-cmd --permanent --direct --add-rule ipv4 filter INPUT 0 -p tcp --dport 80 -s 203.0.113.10/24,203.0.113.10/24 -j ACCEPT
firewall-cmd --permanent --direct --add-rule ipv4 filter INPUT 0 -p tcp --dport 443 -s 203.0.113.10/24,203.0.113.10/24 -j ACCEPT

# 6. 拒绝其他所有入站
firewall-cmd --permanent --direct --add-rule ipv4 filter INPUT 999 -j LOG --log-prefix "FIREWALL_DROP: "
firewall-cmd --permanent --direct --add-rule ipv4 filter INPUT 999 -j DROP

firewall-cmd --reload
```

**网络隔离**

- 数据库服务器部署于独立网段，仅允许应用服务器访问3306端口
- Redis服务器启用AUTH认证，绑定内网IP，禁止公网暴露
- 管理端口（SSH）仅允许堡垒机IP访问，启用密钥认证+二次验证
- 服务器间通信优先使用私有网络，避免流量经过公网

### 12.2 传输安全

**SSL/TLS配置**

```nginx
# Nginx SSL强化配置
server {
    listen 443 ssl http2;
    
    # 证书配置
    ssl_certificate /etc/nginx/ssl/capp.crt;
    ssl_certificate_key /etc/nginx/ssl/capp.key;
    
    # 协议与算法
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384;
    ssl_prefer_server_ciphers on;
    
    # 会话缓存
    ssl_session_cache shared:SSL:50m;
    ssl_session_timeout 1d;
    ssl_session_tickets off;
    
    # HSTS（强制HTTPS）
    add_header Strict-Transport-Security "max-age=63072000; includeSubDomains; preload" always;
    
    # OCSP Stapling
    ssl_stapling on;
    ssl_stapling_verify on;
    ssl_trusted_certificate /etc/nginx/ssl/ca-chain.crt;
    resolver 8.8.8.8 114.114.114.114 valid=300s;
    resolver_timeout 5s;
}
```

**证书管理**

- 使用企业内CA或受信任商业CA签发的证书，禁止自签名证书用于生产环境
- 证书有效期监控，到期前30天自动告警
- 私钥文件权限设置为600，存储于加密分区或HSM硬件模块

### 12.3 访问控制

**身份认证强化**

- 密码策略：最小长度8位，必须包含大小写字母、数字和特殊字符，90天强制更换
- 登录保护：连续5次失败锁定账号15分钟，登录IP异常触发二次验证
- 会话管理：会话超时1小时，单用户同时在线设备数限制为3台
- 多因素认证：系统管理员和工艺总工程师强制启用企业微信扫码或短信验证码二次认证

**权限控制**

- 基于RBAC模型，角色权限最小化原则分配
- 数据权限按组织架构隔离，工艺员仅可见本部门工艺数据
- 敏感操作（删除工艺、修改审批状态、系统配置变更）需二次确认并记录审计日志
- 离职人员账号24小时内完成禁用或删除

**API安全**

- 所有API接口启用身份认证（Token或Session）
- 外部集成接口（CAD/ERP/MES）使用API Key + IP白名单双重认证
- 关键接口启用请求签名验证，防止重放攻击
- 接口限流：普通用户100次/分钟，外部系统1000次/分钟

### 12.4 漏洞修复

**漏洞管理流程**

1. **漏洞发现**：通过安全扫描工具（Nessus、OpenVAS）、厂商公告、CNVD/CNVD漏洞库获取漏洞信息
2. **风险评估**：评估漏洞对CAPP系统的影响程度（CVSS评分）和利用可能性
3. **修复计划**：高危漏洞24小时内修复，中危漏洞7天内修复，低危漏洞纳入下次版本更新
4. **测试验证**：补丁在测试环境验证功能兼容性和性能影响
5. **生产部署**：通过标准变更流程部署补丁，验证修复效果
6. **记录归档**：漏洞修复记录归档至安全台账，供审计查阅

## 1. 总体架构图

### 1.1 架构概述

CAPP系统采用经典的分层架构设计，整体架构自上而下分为五个层次：用户接入层、表现层、业务逻辑层、数据访问层、基础设施层。同时，在横向上划分为安全管控、系统监控、集成接口三大支撑体系，形成"五层三翼"的总体架构格局。

系统以PHP原生代码为核心开发语言，MySQL关系型数据库为数据持久化存储，通过Apache/Nginx Web服务器对外提供HTTP服务。系统不依赖任何PHP开发框架，完全基于原生PHP语言特性进行自主架构设计和代码实现，确保系统具有最高的可控性、最轻量的运行开销和最灵活的定制能力。

### 1.2 架构层次描述

**（1）用户接入层**

用户接入层是系统与外部用户或系统进行交互的入口，包括多种接入终端和渠道：

- **桌面浏览器**：工艺人员、管理人员通过PC端浏览器访问系统，进行工艺编制、审批、查询、统计等操作，是系统的主要使用场景；
- **移动浏览器**：车间现场人员、领导通过平板电脑或手机浏览器查看工艺文件、审批待办、浏览报表，支持移动办公和现场作业指导；
- **打印终端**：连接至系统的专用打印设备，用于输出纸质工艺卡片、工艺流程图、检验记录表等现场使用的纸质文件；
- **扫码终端**：车间工位配备的扫码枪或工业平板，工人通过扫描零件条码或工序条码快速定位到当前工序的工艺文件；
- **第三方系统**：CAD/PLM系统、ERP系统、MES系统、质量管理系统等通过标准接口与CAPP系统进行数据交互。

**（2）表现层**

表现层负责处理用户请求、渲染页面视图、提供API接口服务。表现层分为两个子层：

- **Web页面子层**：基于HTML5、CSS3、JavaScript技术构建的响应式Web应用，采用模块化前端架构，通过AJAX与后端进行异步数据交互。页面组件包括工艺卡片编辑器、流程图绘制器、报表展示器、树形结构导航器等；
- **API接口子层**：基于RESTful架构风格设计的HTTP API接口，为前端页面和第三方系统提供统一的数据服务接口。接口采用JSON数据格式，支持标准HTTP方法（GET/POST/PUT/DELETE），接口版本控制采用URL路径版本号方式（如/api/v1/process）。

**（3）业务逻辑层**

业务逻辑层是系统的核心，封装了所有业务领域的处理逻辑。该层按照业务领域划分为多个服务模块，每个服务模块内部采用面向对象的设计方式，通过Service类封装业务操作，通过Entity/Model类封装业务实体。业务逻辑层通过调用数据访问层完成数据的持久化操作，通过调用跨层组件（如工作流引擎、规则引擎）完成复杂的业务处理。

**（4）数据访问层**

数据访问层负责屏蔽底层数据存储的差异，为业务逻辑层提供统一的数据访问接口。该层封装了数据库连接管理、SQL语句构建、事务控制、结果集映射等底层数据操作细节。数据访问层支持MySQL关系型数据库的访问，同时封装了Redis缓存、文件存储、消息队列等其他数据介质的访问接口。

**（5）基础设施层**

基础设施层提供系统运行所需的底层技术设施，包括：

- **MySQL数据库集群**：主从复制架构的关系型数据库，存储系统的业务数据、配置数据、审计数据；
- **Redis缓存服务**：内存级键值存储，用于会话管理、热点数据缓存、分布式锁、消息队列等场景；
- **Nginx Web服务器**：高性能HTTP服务器和反向代理，负责静态资源服务、负载均衡、SSL终止、请求限流等；
- **文件存储服务**：网络附加存储（NAS）或分布式文件系统，存储工艺文件附件、图纸文件、报表文件等非结构化数据；
- **消息队列服务**（可选）：基于Redis列表或RabbitMQ实现的消息队列，用于异步任务处理、系统间解耦、流量削峰等场景。

### 1.3 数据流向说明

系统的主要数据流向包括以下几条链路：

**（1）工艺编制数据流**

用户通过浏览器访问工艺编制页面 → 表现层接收请求并调用工艺规程服务 → 业务逻辑层执行业务校验和工艺数据处理 → 数据访问层将工艺数据写入MySQL数据库，将工艺文件附件写入文件存储 → 返回处理结果至前端页面 → 前端页面更新工艺卡片视图。

**（2）审批流程数据流**

工艺员提交审批 → 业务逻辑层调用工作流引擎创建流程实例 → 工作流引擎根据流程定义计算下一节点和审批人 → 数据访问层将流程状态写入数据库，发送待办通知至Redis消息队列 → 审批人登录系统查询待办列表 → 审批人执行审批操作 → 工作流引擎推进流程至下一节点或结束 → 流程结束时触发工艺文件发布事件，更新工艺文件状态。

**（3）系统集成数据流**

CAD/PLM系统推送设计BOM变更 → 集成适配服务接收并解析数据 → 业务逻辑层校验数据完整性和一致性 → 数据访问层将设计BOM数据写入数据库 → 触发工艺BOM同步任务 → 工艺员在CAPP系统中查看更新后的设计数据并调整工艺。

CAPP系统发布工艺数据 → 集成适配服务将工艺路线、定额数据转换为ERP所需格式 → 通过API或中间表方式推送至ERP系统 → ERP系统接收数据并用于MRP运算和生产计划编制。

**（4）报表统计数据流**

用户发起统计查询请求 → 业务逻辑层解析查询条件 → 数据访问层执行聚合查询（优先从Redis缓存获取热点统计结果） → 业务逻辑层对查询结果进行业务计算和格式转换 → 表现层渲染统计图表和表格 → 用户查看或导出报表。

## 2. 技术架构

系统采用经典的三层架构模式（表现层、业务逻辑层、数据访问层），并在三层之上构建了跨层公共服务组件。技术架构的设计遵循"高内聚、低耦合"的原则，各层之间通过明确的接口契约进行交互，层与层之间禁止跨层直接调用。

### 2.1 表现层

表现层是系统与用户交互的界面层，负责接收用户输入、展示处理结果、控制页面流转。表现层的技术实现包括：

**（1）前端页面技术栈**

- **HTML5/CSS3**：构建语义化的页面结构和响应式布局，采用Flexbox和Grid布局技术实现复杂的工艺卡片排版和报表表格展示；
- **原生JavaScript（ES6+）**：不依赖大型前端框架（如Vue/React/Angular），采用模块化JavaScript开发模式，通过原生DOM操作和Fetch API实现页面交互和数据请求。对于工艺卡片编辑器、流程图绘制器等复杂交互组件，采用Canvas 2D或SVG技术实现；
- **前端组件库**：基于原生JavaScript封装企业级UI组件库，包括数据表格（支持分页、排序、筛选、冻结列）、树形控件（支持懒加载、拖拽排序）、表单控件（支持动态表单、字段校验、联动逻辑）、对话框、下拉菜单、日期选择器、文件上传器等；
- **图表库**：集成ECharts开源图表库，用于报表统计中的柱状图、折线图、饼图、雷达图、甘特图等数据可视化展示。

**（2）后端页面控制器**

- **Page Controller模式**：每个功能页面对应一个PHP控制器文件，控制器负责接收HTTP请求参数、调用业务逻辑层服务、准备页面数据、渲染视图模板；
- **视图模板引擎**：采用轻量级的PHP原生模板机制（通过include和输出缓冲实现），模板文件仅包含HTML结构和简单的PHP变量输出/循环逻辑，禁止在模板中编写业务逻辑代码；
- **API控制器**：独立的API控制器目录，所有对外接口统一以/api为前缀，API控制器负责参数校验、身份认证、调用业务服务、封装JSON响应。

**（3）前端工程化**

- 采用原生JavaScript模块（ES6 Module）进行代码组织，通过构建工具（如Vite或Rollup）进行代码打包、压缩、转译；
- CSS采用预处理器（Sass/LESS）编写，通过构建工具编译为标准CSS；
- 静态资源（JS/CSS/图片/字体）通过Nginx直接提供服务，并配置长期缓存策略。

### 2.2 业务逻辑层

业务逻辑层是系统的核心层，承载了所有业务领域的处理规则和流程控制逻辑。该层的设计采用领域驱动设计（DDD）的简化实践，将业务领域划分为多个限界上下文，每个上下文内部包含实体、值对象、领域服务、应用服务等组件。

**（1）服务层（Service Layer）**

服务层是业务逻辑层的对外接口，为表现层提供粗粒度的业务操作接口。每个业务领域对应一个或多个Service类：

- `ProcessResourceService`：工艺资源管理服务，提供设备、工装、刀具、材料、工种等基础资源的CRUD操作和关联查询；
- `ProcessRouteService`：工艺路线管理服务，提供工艺路线的创建、编辑、版本管理、审批发布等业务操作；
- `ProcessSpecificationService`：工艺规程编制服务，提供工艺卡片的结构化编辑、模板应用、参数推荐、文件生成等核心功能；
- `ProcessBOMService`：工艺BOM管理服务，提供工艺BOM构建、材料定额计算、工时定额计算、外协工艺管理等功能；
- `WorkflowService`：工作流服务，封装工作流引擎的调用，提供流程启动、任务查询、任务办理、流程监控等接口；
- `ChangeManagementService`：变更管理服务，提供变更申请、影响评估、变更审批、变更执行、变更通知等全流程管理；
- `KnowledgeBaseService`：知识库服务，提供知识的分类管理、全文检索、智能推荐、评价优化等功能；
- `ReportService`：报表统计服务，提供标准报表生成、自定义报表查询、统计分析计算、图表数据准备等功能；
- `IntegrationService`：集成适配服务，提供与CAD/PLM/ERP/MES系统的数据转换和接口适配功能。

**（2）领域模型层（Domain Model）**

领域模型层封装业务实体及其行为，采用贫血模型与充血模型相结合的方式：

- **实体类（Entity）**：对应数据库表的结构化数据对象，如`ProcessRouteEntity`、`OperationEntity`、`MaterialQuotaEntity`等。实体类包含属性定义、数据校验规则、简单的业务计算方法；
- **值对象（Value Object）**：无唯一标识的不可变对象，用于封装具有业务含义的属性组合，如`Money`（金额+币种）、`TimeRange`（起止时间）、`Dimension`（尺寸+公差）等；
- **领域服务（Domain Service）**：封装不属于任何单个实体的领域逻辑，如`QuotaCalculationService`（定额计算逻辑）、`ProcessValidationService`（工艺校验逻辑）、`VersionComparisonService`（版本对比逻辑）等。

**（3）业务规则引擎**

对于复杂且频繁变化的业务规则，采用规则引擎机制实现规则与代码的分离：

- 规则以配置数据的形式存储在数据库中，包括规则条件（如"当材料为不锈钢且壁厚大于20mm时"）和规则动作（如"必须执行焊后热处理"）；
- 规则引擎采用前向链推理方式，在工艺编制过程中自动匹配适用规则，给出提示或强制约束；
- 规则配置界面提供给工艺主管，支持规则的新增、修改、启用、停用，无需修改程序代码即可调整业务规则。

**（4）工作流引擎**

工作流引擎是支撑工艺审批流程的核心组件，采用自主实现的轻量级工作流引擎：

- 流程定义采用JSON格式描述，包括节点定义、转移条件、参与者设置、超时配置等；
- 引擎支持顺序流程、并行分支、条件分支、会签聚合、子流程嵌套等流程模式；
- 流程实例状态持久化至数据库，支持流程的暂停、恢复、回退、转办、加签等异常处理；
- 提供流程实例查询API，支持按发起人、流程类型、当前节点、办理状态等多维度查询。

### 2.3 数据访问层

数据访问层负责所有与数据持久化相关的操作，为业务逻辑层提供统一、简洁、安全的数据访问接口。该层的设计目标是屏蔽底层数据库的差异，集中管理数据库连接、SQL构建、事务控制和性能优化。

**（1）数据库连接管理**

- 采用PDO（PHP Data Objects）作为数据库访问抽象层，PDO提供了统一的API接口，支持多种数据库驱动，便于未来数据库迁移；
- 实现数据库连接池的模拟机制，通过单例模式管理PDO实例，避免频繁创建和销毁数据库连接带来的性能开销；
- 支持主从数据库的读写分离配置，查询操作自动路由至从库，写操作强制路由至主库，通过数据库代理或应用层路由实现；
- 数据库连接配置（主机、端口、用户名、密码、数据库名）存储在独立的配置文件中，配置文件通过PHP常量或环境变量加载，密码采用加密存储。

**（2）数据访问对象（DAO）**

- 每个业务实体对应一个DAO类，如`ProcessRouteDao`、`OperationDao`、`MaterialQuotaDao`等；
- DAO类封装了对单表的增删改查操作，提供`insert()`、`update()`、`delete()`、`selectById()`、`selectByCondition()`、`count()`等标准方法；
- DAO类禁止编写跨表关联查询，复杂的业务查询通过Service层组合多个DAO操作或调用专用的Query对象实现；
- DAO层自动处理SQL注入防护，所有外部输入的参数通过PDO预处理语句绑定，禁止字符串拼接SQL语句。

**（3）查询构建器（Query Builder）**

- 实现轻量级的SQL查询构建器，通过链式调用API动态构建SELECT语句，如`$query->table('process_route')->where('status', 'published')->orderBy('create_time', 'desc')->limit(20)->offset(0)->execute()`；
- 查询构建器自动处理字段转义、表名前缀、参数绑定，支持复杂的WHERE条件组合（AND/OR/IN/BETWEEN/LIKE）、JOIN关联、GROUP BY分组、HAVING过滤、ORDER BY排序、LIMIT分页；
- 查询构建器支持查询缓存注解，对于标注为可缓存的查询，自动将结果集序列化后存入Redis，下次相同查询直接从缓存返回。

**（4）事务管理**

- 在Service层通过声明式事务注解或编程式事务API控制事务边界；
- 事务管理器自动在方法开始时开启事务，在方法正常返回时提交事务，在发生异常时回滚事务；
- 支持嵌套事务（通过数据库SAVEPOINT实现），支持事务传播行为配置（REQUIRED、REQUIRES_NEW、NESTED等）；
- 事务超时和隔离级别可通过配置全局设置或在方法级别覆盖。

**（5）数据库迁移工具**

- 实现简单的数据库版本迁移机制，迁移脚本以SQL文件形式存储，按版本号顺序执行；
- 系统启动时自动检测当前数据库版本，执行待执行的迁移脚本，确保数据库结构与代码版本保持一致；
- 迁移脚本包括DDL（建表、改表、索引、约束）和DML（基础数据初始化、字典数据导入）两类，分别存放在不同目录。

### 2.4 跨层组件

跨层组件是为表现层、业务逻辑层、数据访问层提供公共服务的共享组件，独立于具体业务领域。

**（1）认证与授权组件**

- `AuthComponent`：负责用户身份认证，包括登录校验、会话管理、Token生成与校验、单点登录对接等；
- `AclComponent`：负责访问控制列表管理，根据当前用户角色和请求资源，判定是否允许访问；
- `PermissionChecker`：负责细粒度权限校验，在Service方法执行前进行权限拦截。

**（2）日志与审计组件**

- `Logger`：分级日志记录器（DEBUG/INFO/WARNING/ERROR/FATAL），支持文件日志、数据库日志、远程日志等多种输出目标；
- `AuditRecorder`：审计日志记录器，自动记录数据变更前后的完整快照，支持操作回溯；
- `PerformanceProfiler`：性能分析器，记录关键方法的执行耗时和数据库查询次数，用于性能瓶颈定位。

**（3）缓存组件**

- `CacheManager`：缓存管理器，支持多级缓存策略（本地文件缓存 → Redis缓存 → 数据库），自动处理缓存的读取、写入、失效、刷新；
- `CacheKeyBuilder`：缓存键构建器，根据查询参数自动生成规范的缓存键，支持缓存键的命名空间管理和版本控制。

**（4）异常处理组件**

- `ExceptionHandler`：全局异常处理器，捕获系统运行过程中的未处理异常，根据异常类型返回友好的错误页面或JSON错误响应；
- `BusinessException`：业务异常基类，用于封装可预期的业务错误（如"工艺文件已发布，不可修改"），异常信息可直接展示给用户；
- `SystemException`：系统异常基类，用于封装不可预期的系统错误（如数据库连接失败），异常信息记录日志后返回通用错误提示。

**（5）工具类库**

- `StringUtil`、`DateUtil`、`ArrayUtil`、`FileUtil`、`HttpUtil`、`EncryptUtil`、`ValidateUtil`等常用工具类；
- `ExcelExporter`、`PdfGenerator`、`QrCodeGenerator`等文档生成工具类；
- `IdGenerator`：分布式唯一ID生成器，基于雪花算法或数据库序列实现；
- `CodeGenerator`：业务编码生成器，根据编码规则自动生成项目编号、工艺文件编号等。

## 3. 部署架构

### 3.1 服务器规划

根据企业当前规模和未来发展预期，CAPP系统的服务器规划分为两个阶段：初期单节点部署阶段和中期集群部署阶段。

**（1）初期部署方案（当前至未来2年）**

初期采用两台物理服务器或虚拟机的部署模式，满足50-100并发用户的日常使用需求：

| 服务器角色 | 配置要求 | 部署组件 | 说明 |
|-----------|---------|---------|------|
| 应用服务器 | 8核CPU/32GB内存/500GB SSD | Nginx + PHP-FPM + 应用代码 | 运行Web服务和业务应用，PHP-FPM配置动态子进程池，最大并发进程数200 |
| 数据库服务器 | 8核CPU/32GB内存/1TB SSD RAID10 | MySQL主库 + Redis | 运行MySQL数据库和Redis缓存服务，SSD确保数据库I/O性能 |

- 应用服务器安装CentOS/RHEL 8.x或Ubuntu Server 22.04 LTS操作系统，PHP版本8.1+，Nginx版本1.20+；
- 数据库服务器安装相同操作系统，MySQL版本8.0+，Redis版本6.2+；
- 两台服务器通过千兆内网互联，数据库服务器仅开放3306和6379端口给应用服务器访问，不直接暴露至外网；
- 文件存储使用应用服务器的本地磁盘，通过NFS或Samba共享给内网用户进行大文件上传下载。

**（2）中期集群部署方案（未来2-5年）**

随着用户数量增长和业务数据积累，中期扩展为集群部署模式，支持200+并发用户：

| 服务器角色 | 数量 | 配置要求 | 部署组件 |
|-----------|------|---------|---------|
| 负载均衡服务器 | 2台 | 4核CPU/8GB内存/200GB SSD | Nginx（负载均衡+静态资源）+ Keepalived（高可用） |
| 应用服务器 | 2-4台 | 8核CPU/32GB内存/500GB SSD | Nginx（反向代理）+ PHP-FPM + 应用代码 |
| 数据库主服务器 | 1台 | 16核CPU/64GB内存/2TB SSD RAID10 | MySQL主库 |
| 数据库从服务器 | 1-2台 | 16核CPU/64GB内存/2TB SSD RAID10 | MySQL从库（只读） |
| 缓存服务器 | 2台 | 8核CPU/32GB内存/500GB SSD | Redis主从 + Sentinel高可用 |
| 文件存储服务器 | 1台 | 8核CPU/32GB内存/10TB HDD RAID6 | MinIO分布式对象存储或NAS |

- 负载均衡层采用Nginx的反向代理和负载均衡模块，将用户请求分发至多台应用服务器，采用加权轮询算法，支持会话保持（IP Hash或Sticky Session）；
- 两台负载均衡服务器通过Keepalived实现主备高可用，虚拟IP（VIP）对外提供服务，主节点故障时自动切换至备节点，切换时间小于5秒；
- 应用服务器为无状态节点，不保存用户会话数据，会话统一存储在Redis中，任何应用服务器均可处理任何用户的请求；
- 数据库采用一主两从架构，主库负责写操作，从库负责读操作，通过应用层或中间件实现读写分离。从库同时作为热备，主库故障时可快速切换；
- Redis采用一主一从+Sentinel哨兵架构，实现缓存服务的高可用，Sentinel自动监控主从状态并执行故障转移；
- 文件存储采用MinIO分布式对象存储或企业NAS，支持S3协议，应用通过统一接口上传下载文件，存储容量可横向扩展。

### 3.2 负载均衡

负载均衡是保障系统高可用和高性能的关键机制，本系统的负载均衡策略包括：

**（1）入口层负载均衡**

- 采用DNS轮询或硬件F5/软件Nginx实现入口流量分发；
- 支持基于权重的流量分配，新上线的应用服务器可设置较低权重进行灰度验证；
- 支持健康检查机制，定时探测应用服务器的HTTP接口，连续3次探测失败则自动将该节点移出负载池，恢复后自动加入。

**（2）应用层负载均衡**

- PHP-FPM进程池采用动态管理模式（pm = dynamic），根据当前请求量自动调整工作进程数量；
- 配置合理的进程池参数：pm.max_children = 200，pm.start_servers = 20，pm.min_spare_servers = 10，pm.max_spare_servers = 50，pm.max_requests = 1000（防止内存泄漏）；
- 对于耗时较长的报表生成请求，通过异步任务队列处理，避免占用PHP-FPM工作进程导致其他请求阻塞。

**（3）数据库层负载均衡**

- 读操作自动分发至MySQL从库，通过应用层DAO的路由逻辑或数据库中间件（如MySQL Proxy、MaxScale）实现；
- 写操作强制路由至MySQL主库，确保数据一致性；
- 从库延迟监控，当从库复制延迟超过10秒时，临时将读操作回退至主库，避免读取过期数据。

### 3.3 文件存储

CAPP系统涉及大量的非结构化数据存储，包括：

- **工艺文件附件**：工艺卡片中的工序简图、工艺附图、检验示意图等图片文件；
- **设计图纸文件**：从CAD/PLM系统同步的产品图纸、三维模型、PDF轻量化文件；
- **工艺规程文档**：生成的PDF工艺文件、Excel报表、Word说明文档；
- **知识库文档**：工艺标准扫描件、工艺案例文档、培训视频等知识资产。

文件存储架构设计如下：

**（1）存储分层策略**

- **热数据层**：最近3个月频繁访问的文件，存储在应用服务器本地SSD或高速NAS，通过Nginx直接提供HTTP访问，响应速度最快；
- **温数据层**：3个月至2年的文件，存储在企业NAS或MinIO对象存储，通过应用服务器代理访问，支持断点续传和压缩传输；
- **冷数据层**：超过2年的归档文件，迁移至低成本存储（如磁带库、蓝光库或云存储归档），保留元数据索引，需要时手动或自动解冻恢复。

**（2）文件管理策略**

- 文件上传时由系统自动生成全局唯一文件名（UUID），原始文件名作为元数据保存，避免文件名冲突和特殊字符问题；
- 文件按日期和类型分目录存储，如`/storage/2026/06/process_image/xxx.jpg`，便于管理和归档；
- 文件元数据（文件名、大小、类型、上传人、上传时间、关联业务ID、MD5校验值）记录在数据库中，支持按业务维度检索文件；
- 大文件（超过50MB）采用分片上传机制，前端将文件切分为多个分片依次上传，后端合并分片并校验完整性；
- 文件下载支持权限校验，用户只能下载其权限范围内的文件，敏感文件下载记录审计日志。

**（3）文件备份策略**

- 热数据和温数据每日增量备份至异地备份服务器，每周全量备份；
- 备份数据保留周期：每日增量备份保留30天，每周全量备份保留12周，每月归档备份保留3年；
- 定期执行备份恢复演练，验证备份数据的完整性和可恢复性。

### 3.4 缓存策略

缓存是提升系统性能、降低数据库压力的重要手段。本系统采用多级缓存架构，针对不同数据特性选择适宜的缓存策略。

**（1）缓存层级设计**

| 缓存层级 | 技术实现 | 存储内容 | 过期策略 |
|---------|---------|---------|---------|
| 一级缓存（应用本地） | PHP数组/OPcache | 系统配置、字典数据、权限规则 | 进程生命周期/手动刷新 |
| 二级缓存（分布式内存） | Redis | 用户会话、热点数据、查询结果、锁对象 | TTL过期/主动失效 |
| 三级缓存（文件静态化） | 本地文件 | 报表页面、PDF文件、频繁访问的列表页 | 定时刷新/事件触发刷新 |
| 浏览器缓存 | HTTP Cache-Control | 静态资源（JS/CSS/图片）、不常变的API响应 | 长期缓存/版本号控制 |

**（2）缓存应用场景**

- **用户会话缓存**：用户登录成功后，会话数据（用户ID、角色、权限列表）存储在Redis中，设置30分钟过期时间，每次用户操作刷新过期时间。应用服务器通过Session ID从Redis读取会话，实现无状态部署；
- **权限数据缓存**：用户权限列表、角色配置、数据范围规则等数据在Redis中缓存，过期时间设置为1小时。权限配置变更时，主动清除相关缓存；
- **工艺资源缓存**：设备台账、材料库、刀具库等基础数据访问频率高但变更频率低，查询结果在Redis中缓存24小时；
- **工艺文件缓存**：已发布的工艺文件生成静态HTML或PDF缓存，工艺员查看时直接返回缓存文件，避免重复查询数据库和渲染页面；
- **报表统计缓存**：复杂统计报表的计算结果缓存1小时，支持用户手动刷新获取最新数据；
- **查询结果缓存**：通用列表查询（如工艺文件列表、审批待办列表）的查询结果缓存5分钟，分页参数作为缓存键的一部分。

**（3）缓存一致性保障**

- 写操作（新增、修改、删除）成功后，立即删除相关缓存键，确保下次读取获取最新数据；
- 对于高并发场景下的缓存穿透问题，采用布隆过滤器或空值缓存策略，避免大量请求直接冲击数据库；
- 对于缓存雪崩问题，设置缓存过期时间的随机偏移量（如基础TTL ± 10%），避免大量缓存同时过期；
- 对于缓存击穿问题，采用分布式锁（Redis SETNX）机制，确保只有一个请求回源数据库，其他请求等待缓存重建。

## 4. 安全架构

### 4.1 认证授权

**（1）用户身份认证**

- **表单登录认证**：用户输入用户名、密码、图形验证码，系统校验通过后创建会话（Session），会话ID存储在HTTP Only、Secure、SameSite=Strict属性的Cookie中，防止XSS攻击和CSRF攻击；
- **密码安全策略**：用户密码采用bcrypt算法（cost factor = 12）进行加盐哈希存储，即使数据库泄露也无法逆向破解原始密码。密码复杂度要求：最小8位，包含大小写字母、数字、特殊字符，90天强制更换，不可复用最近5次历史密码；
- **登录安全控制**：连续5次登录失败自动锁定账号30分钟，锁定期间即使输入正确密码也拒绝登录。同一账号不允许在多个地点同时在线（可选配置）；
- **会话安全管理**：会话空闲30分钟自动失效，用户主动退出时立即销毁会话。会话数据存储在服务器端（Redis），客户端仅持有会话ID，防止会话数据篡改；
- **单点登录集成**（可选）：未来可扩展对接企业AD/LDAP或统一身份认证平台（如OAuth2/OIDC），实现与企业其他系统的单点登录和统一身份管理。

**（2）访问控制授权**

- **RBAC权限模型**：系统采用基于角色的访问控制模型，用户通过角色获得权限，角色通过权限配置获得功能操作和数据范围的授权。支持角色的继承和组合；
- **功能权限控制**：精确到菜单、按钮、API接口级别的功能权限控制。前端页面根据用户权限动态渲染可用按钮，后端API在入口处校验权限，防止通过直接调用API绕过前端限制；
- **数据权限控制**：在SQL查询层面自动附加数据范围过滤条件，确保用户只能查询其权限范围内的数据。数据权限维度包括：部门范围、项目范围、产品类型范围、个人范围、共享范围；
- **审批权限控制**：审批流程中的每个节点可配置办理人范围（指定人员、指定角色、部门负责人、上级领导等），系统根据流程定义自动计算当前任务的合法办理人列表，非合法办理人无法查看和处理该任务。

### 4.2 数据加密

**（1）传输层加密**

- 系统全站启用HTTPS协议，通过SSL/TLS证书加密客户端与服务器之间的所有数据传输，防止中间人攻击和数据窃听；
- HTTPS配置采用TLS 1.2及以上版本，禁用不安全的SSLv2/SSLv3/TLS 1.0/TLS 1.1协议，配置强加密套件（如ECDHE-RSA-AES256-GCM-SHA384）；
- 内部服务间通信（如应用服务器与数据库服务器）根据安全域划分，可选择启用SSL加密连接或依赖内网隔离保障安全。

**（2）存储层加密**

- **密码加密**：用户密码采用bcrypt哈希存储，不可逆；
- **敏感配置加密**：数据库连接密码、API密钥、邮件服务器密码等敏感配置信息，使用AES-256算法加密后存储在配置文件中，解密密钥通过环境变量或硬件安全模块（HSM）提供，避免密钥与密文存储在同一位置；
- **附件加密**（可选）：对于涉及核心工艺机密的高敏感文件，上传时采用AES-256加密存储，下载时解密传输。加密密钥由文件所有者保管或存储在密钥管理系统（KMS）中；
- **数据库透明加密**（可选）：对于极高安全要求的场景，可启用MySQL的TDE（Transparent Data Encryption）功能，对数据文件和日志文件进行自动加密，防止物理存储介质被盗导致的数据泄露。

**（3）应用层加密**

- 对于身份证号、手机号等个人隐私数据，在数据库中存储时进行脱敏或加密处理，业务查询时按需解密；
- 系统管理员和数据库管理员在未经业务授权的情况下，无法直接查看敏感业务数据的明文内容。

### 4.3 审计日志

审计日志是保障系统操作可追溯、满足质量管理体系和合规要求的重要手段。本系统建立全面的审计日志体系，覆盖用户操作、数据变更、系统事件、安全事件四大类。

**（1）操作审计日志**

- 记录所有用户的登录、登出行为，包括时间、IP地址、浏览器信息、登录结果（成功/失败/锁定）；
- 记录所有数据的新增、修改、删除操作，包括操作人、操作时间、操作对象、操作类型、操作前数据快照、操作后数据快照；
- 记录所有审批流程的操作，包括提交、审核、会签、批准、退回、转办、撤销等，记录每个环节的处理人、处理时间、处理意见；
- 记录所有文件的上传、下载、预览、打印操作，记录操作人、操作时间、文件名称、文件大小、关联业务；
- 记录所有系统配置变更，包括权限调整、流程定义修改、编码规则变更、参数设置调整等。

**（2）系统运行日志**

- 记录应用服务器的启动、停止、配置加载、模块初始化等生命周期事件；
- 记录数据库连接池的状态变化、SQL慢查询（执行时间超过1秒）、数据库死锁和超时事件；
- 记录缓存的命中率、失效事件、异常访问模式；
- 记录定时任务的执行时间、执行结果、异常堆栈。

**（3）安全事件日志**

- 记录所有安全相关事件，包括：异常登录尝试（暴力破解）、权限越界访问、SQL注入攻击尝试、XSS攻击尝试、CSRF攻击拦截、文件上传漏洞尝试等；
- 安全事件日志独立存储，保留期限不少于5年，定期导出至企业安全运营中心（SOC）进行分析。

**（4）日志存储与保护**

- 审计日志采用"数据库+文件"双轨存储模式：近期日志（6个月内）存储在数据库中，便于快速查询和报表统计；历史日志（6个月以上）归档为压缩文件，存储在独立的日志服务器或对象存储中；
- 审计日志表采用分区表设计，按月份自动分区，便于数据清理和查询优化；
- 审计日志禁止通过系统界面删除或修改，仅系统管理员可查询和导出。日志数据库账户与应用业务数据库账户分离，应用代码无法直接操作日志表（通过存储过程或消息队列间接写入）；
- 关键审计日志（如权限变更、数据删除）实时同步至异地日志中心，防止本地日志被篡改或销毁。

### 4.4 备份策略

数据备份是保障业务连续性和数据安全的最后一道防线。本系统建立多层次、多频率、异地化的备份体系。

**（1）数据库备份**

- **全量备份**：每周日凌晨2:00执行MySQL全量逻辑备份（mysqldump），导出完整的SQL脚本文件，压缩后存储至备份服务器。全量备份保留最近12个副本；
- **增量备份**：每日凌晨2:00执行基于二进制日志（binlog）的增量备份，备份自上次全量或增量备份以来的所有数据变更。增量备份保留最近30天；
- **实时备份**：MySQL主从复制本身构成实时热备份机制，从库数据与主库保持同步，主库故障时可快速切换至从库；
- **异地备份**：每周全量备份完成后，通过加密传输通道将备份文件复制至异地灾备中心，异地备份保留最近6个月；
- **备份验证**：每月随机抽取一份备份文件，在测试环境中执行恢复演练，验证备份数据的完整性和可恢复性，演练结果记录备案。

**（2）文件备份**

- 文件存储服务器每日执行增量备份（rsync），每周执行全量备份；
- 备份文件存储在独立的备份存储设备上，与生产存储物理隔离；
- 大文件备份采用分卷压缩和校验和（MD5/SHA256）验证，确保备份文件未损坏。

**（3）应用代码备份**

- 应用代码通过Git版本控制系统管理，代码仓库托管在企业内部Git服务器或私有云Git平台；
- 每次发布上线前打标签（Tag），记录发布版本对应的代码提交点，支持快速回滚至历史版本；
- Git仓库每日自动同步至异地备份节点，防止代码仓库单点故障。

**（4）灾难恢复预案**

- 制定详细的灾难恢复预案（DRP），明确不同灾难场景（数据库损坏、服务器宕机、机房火灾、勒索病毒等）下的恢复流程、恢复时间目标（RTO）和恢复点目标（RPO）；
- 数据库故障RTO目标：主库故障切换至从库，RTO ≤ 5分钟；全库恢复至最近备份点，RTO ≤ 4小时，RPO ≤ 24小时；
- 每年至少开展一次全面的灾难恢复演练，检验预案的可行性和团队的响应能力，演练后更新完善预案。

## 5. 模块划分与依赖关系

### 5.1 模块划分

CAPP系统按照业务领域和职责边界，划分为以下核心模块：

**（1）基础平台模块（Foundation）**

基础平台模块为其他所有模块提供公共服务和基础设施，是系统的技术底座。包括：

- 用户与组织架构管理（User & Org）
- 角色与权限管理（RBAC）
- 系统配置与参数管理（Config）
- 编码规则管理（Coding Rule）
- 操作日志与审计（Audit Log）
- 数据字典管理（Data Dictionary）
- 消息通知服务（Notification）
- 文件存储服务（File Storage）
- 定时任务调度（Job Scheduler）
- 系统监控与告警（Monitoring）

**（2）工艺资源模块（Process Resource）**

工艺资源模块管理工艺规划所需的各类基础资源数据。包括：

- 设备资源管理（Equipment）
- 工艺装备管理（Tooling）
- 刀具量具管理（Cutting & Measuring Tools）
- 材料库管理（Material Library）
- 工种与人员资质管理（Craft & Qualification）
- 工艺标准管理（Process Standard）

**（3）工艺设计模块（Process Design）**

工艺设计模块是系统的核心业务模块，实现工艺路线和工艺规程的编制管理。包括：

- 工艺路线管理（Process Route）
- 工艺规程编制（Process Specification）
- 工序内容管理（Operation Management）
- 工艺BOM管理（Process BOM）
- 材料定额计算（Material Quota）
- 工时定额计算（Time Quota）
- 外协工艺管理（Outsourcing Process）

**（4）流程控制模块（Workflow）**

流程控制模块提供通用的工作流引擎和审批流程管理功能。包括：

- 流程定义管理（Process Definition）
- 流程实例运行（Process Instance）
- 任务管理（Task Management）
- 流程监控与干预（Process Monitoring）
- 流程报表与统计（Workflow Report）

**（5）变更管理模块（Change Management）**

变更管理模块实现工艺文件和工艺数据的变更控制。包括：

- 变更申请（Change Request）
- 变更评估（Change Assessment）
- 变更审批（Change Approval）
- 变更执行（Change Execution）
- 变更通知（Change Notification）
- 变更历史追溯（Change History）

**（6）知识管理模块（Knowledge Base）**

知识管理模块实现工艺知识的积累、检索和推荐。包括：

- 知识分类体系（Knowledge Category）
- 知识采集录入（Knowledge Entry）
- 知识全文检索（Knowledge Search）
- 知识智能推荐（Knowledge Recommendation）
- 知识评价优化（Knowledge Evaluation）

**（7）报表统计模块（Reporting）**

报表统计模块提供工艺数据的多样化展示和分析。包括：

- 标准报表管理（Standard Report）
- 自定义报表设计（Custom Report）
- 统计图表生成（Chart Generation）
- 报表定时任务（Report Scheduler）

**（8）系统集成模块（Integration）**

系统集成模块实现CAPP系统与外部系统的数据交互。包括：

- CAD/PLM集成适配器（CAD/PLM Adapter）
- ERP集成适配器（ERP Adapter）
- MES集成适配器（MES Adapter）
- 质量管理集成适配器（QMS Adapter）
- 统一接口网关（API Gateway）
- 数据交换中间表（Data Exchange Table）
- 消息队列处理（Message Queue Handler）

### 5.2 模块依赖关系

模块之间的依赖关系遵循"上层依赖下层、业务依赖基础、横向弱耦合"的原则：

                    │         报表统计模块 (Reporting)       │

                                  │

        │                         │                         │

│(Process Design)│       │(Change Mgmt)    │       │(Knowledge Base) │
└───────┬───────┘       └─────────────────┘       └─────────────────┘
        │
        ▼
┌───────────────┐       ┌─────────────────┐       ┌─────────────────┐
│  工艺资源模块   │◄────►│   流程控制模块    │◄────►│   系统集成模块    │
│(Process Res.) │       │   (Workflow)    │       │  (Integration)  │
└───────────────┘       └─────────────────┘       └─────────────────┘
        │                         │                         │
        └─────────────────────────┼─────────────────────────┘
                                  │
                                  ▼

**依赖关系说明：**

- 所有业务模块均依赖基础平台模块，基础平台模块不依赖任何业务模块；
- 工艺设计模块依赖工艺资源模块，编制工艺时需要引用设备、材料、工装等资源数据；
- 变更管理模块依赖工艺设计模块和流程控制模块，工艺变更需要修改工艺数据并触发审批流程；
- 知识管理模块依赖工艺设计模块，从工艺文件中自动提取知识，同时工艺编制时可引用知识库内容；
- 报表统计模块依赖所有业务模块，从各模块获取数据进行汇总分析；
- 系统集成模块依赖工艺设计模块和流程控制模块，将工艺数据和流程状态同步至外部系统；
- 模块之间通过Service接口进行交互，禁止跨模块直接访问DAO或数据库表。

### 5.3 接口契约

模块之间的接口契约定义了模块交互的规范，确保模块可以独立开发、独立测试、独立部署。

**（1）内部Service接口**

- 模块对内部其他模块暴露的接口以Service类的方法形式定义，方法签名包含：方法名、参数类型、返回值类型、异常声明；
- 参数和返回值采用DTO（Data Transfer Object）对象传递，DTO对象仅包含数据属性，不包含业务逻辑；
- 接口方法遵循统一的命名规范：`动词+业务对象+操作`，如`createProcessRoute()`、`getMaterialQuotaById()`、`approveChangeRequest()`；
- 接口文档采用PHP注释（PHPDoc）格式编写，包含方法说明、参数说明、返回值说明、异常说明、调用示例。

**（2）外部API接口**

- 对外部系统暴露的RESTful API接口遵循统一的URL规范：`/api/{version}/{module}/{resource}/{action}`；
- 接口请求采用JSON格式，支持标准的HTTP方法语义：GET（查询）、POST（创建）、PUT（更新）、DELETE（删除）、PATCH（部分更新）；
- 接口响应采用统一的JSON结构：`{ "code": 0, "message": "success", "data": {}, "timestamp": 1234567890 }`，其中code为0表示成功，非0表示业务错误或系统错误；
- 接口认证采用API Key + 请求签名或OAuth2 Bearer Token机制，确保接口调用的身份可信和请求防篡改；
- 接口限流采用令牌桶算法，每个API Key限制每分钟的调用次数，防止恶意调用或意外流量冲击。

**（3）数据库表契约**

- 每个模块拥有独立的数据库表命名空间，表名前缀标识所属模块，如`pr_`（Process Resource）、`pd_`（Process Design）、`wf_`（Workflow）等；
- 模块之间的数据关联通过外键约束或逻辑关联实现，禁止跨模块直接操作其他模块的数据表；
- 数据库表结构变更通过版本化的迁移脚本管理，迁移脚本包含升级脚本和回滚脚本，确保变更可逆。

## 6. 技术选型说明

### 6.1 为什么选用PHP原生

在企业级信息系统开发中，PHP原生开发（不使用Laravel、Symfony、ThinkPHP等框架）是一种看似"非主流"但具有独特优势的技术选择。本系统选用PHP原生开发，基于以下深入的技术考量和业务匹配分析：

**（1）极致的可控性与透明度**

PHP原生开发意味着每一行代码、每一个执行流程都在开发团队的完全掌控之中。对于CAPP这类工艺规划系统，业务逻辑复杂、定制化程度高、与制造业业务深度耦合，使用框架虽然可以加速初期开发，但框架的"黑盒"特性会带来长期隐患：

- 框架的ORM自动生成的SQL语句往往不够优化，对于CAPP系统中复杂的多表关联查询（如工艺路线关联工序关联设备关联工装关联材料），手动编写优化SQL比依赖ORM自动生成的SQL性能更可控；
- 框架的依赖注入容器、事件分发机制、中间件管道等抽象层增加了代码的间接性，调试和性能分析时需要穿透多层框架代码，定位问题困难；
- 原生PHP代码的执行路径清晰，从HTTP请求入口到业务逻辑到数据库查询，每一层的调用栈都直观可见，便于性能剖析和故障排查。

**（2）轻量化的运行开销**

PHP原生代码的运行时开销远低于大型框架：

- 框架启动时需要加载大量类文件、解析配置文件、初始化服务容器，内存占用和启动时间显著增加。原生PHP应用启动时仅加载必要的类文件，内存占用可降低50%以上；
- 对于CAPP系统这类以数据查询和表单提交为主的业务系统，框架提供的许多高级特性（如路由解析、模板引擎、ORM关系映射、队列系统）并非必需，引入框架反而带来不必要的性能损耗；
- 在相同的硬件配置下，原生PHP应用可以支撑更高的并发请求量，这对于企业初期有限的IT预算尤为重要。

**（3）长期维护与演进优势**

企业级系统的生命周期通常长达10年以上，技术选型的长期可维护性比短期开发效率更重要：

- PHP框架的版本迭代速度快，Laravel等框架每年发布一个大版本，升级往往伴随破坏性变更，企业系统跟随框架升级的成本高昂，不升级则面临安全漏洞和兼容性问题；
- 原生PHP代码不依赖特定框架的版本生命周期，只要PHP语言本身保持兼容（PHP 8.x对7.x的兼容性良好），系统核心代码可以长期稳定运行；
- 开发团队对原生代码的理解和掌控是深度和持久的，核心开发人员离职后，新成员理解原生代码的门槛低于理解特定框架的深层机制；
- 原生代码的架构由团队自主设计，可以根据业务演进灵活调整，不受框架设计范式的约束。

**（4）与制造业IT环境的适配**

制造业企业的IT环境具有特殊性，PHP原生开发更适配这些场景：

- 制造业企业通常已有稳定的IT基础设施（Windows Server或Linux服务器），PHP作为跨平台语言，部署简单，与现有Apache/Nginx环境集成成熟；
- 企业内网环境对系统响应速度要求高（工艺员编制工艺时频繁保存和查询），原生PHP的低延迟特性更匹配这种交互密集型场景；
- 制造业企业的IT人员配置通常精简，系统需要"低运维成本"，原生PHP应用的部署和故障排查更简单，不需要掌握框架特有的运维命令和调试工具。

**（5）自主技术能力建设**

- 通过原生PHP开发，企业可以逐步积累自主的技术平台和组件库（如本系统构建的DAO层、查询构建器、工作流引擎、报表引擎），这些资产可以复用于未来的其他系统建设；
- 避免对特定商业框架或开源框架的过度依赖，降低技术供应链风险；
- 培养团队对Web应用底层机制（HTTP协议、会话管理、数据库连接、缓存原理）的深入理解，提升整体技术能力。

**（6）PHP语言自身的成熟度**

- PHP 8.x版本在性能（JIT编译）、类型系统（联合类型、属性注解）、错误处理（异常体系）、标准库等方面已非常成熟，完全具备支撑企业级系统开发的语言能力；
- PHP拥有丰富的官方扩展和PECL扩展（如PDO、Redis、GD、Zip、XML、JSON），满足CAPP系统的各类技术需求；
- PHP的FPM（FastCGI Process Manager）进程模型与Nginx配合，是业界经过大规模验证的高性能Web服务架构。

### 6.2 MySQL数据库选型

MySQL作为世界上最流行的开源关系型数据库，是本系统数据持久化的核心选择：

- **成熟稳定**：MySQL 8.0版本经过多年生产环境验证，在数据一致性、事务完整性、崩溃恢复等方面表现可靠，满足工艺数据对准确性的严格要求；
- **性能优异**：MySQL 8.0的InnoDB存储引擎支持行级锁、MVCC并发控制、自适应哈希索引，对于CAPP系统的高并发查询和写入场景性能优异；
- **生态丰富**：MySQL拥有完善的运维工具链（MySQL Workbench、Percona Toolkit、Prometheus Exporter等），便于DBA进行性能调优、备份恢复、监控告警；
- **成本优势**：MySQL社区版免费开源，无需支付商业数据库许可费用，适合制造业企业的成本控制要求；
- **人才储备**：MySQL是Web开发领域最广泛使用的数据库，招聘具有MySQL经验的开发和运维人员相对容易；
- **主从复制**：MySQL成熟的主从复制机制为系统的读写分离和高可用架构提供基础支撑。

### 6.3 前端技术选型

前端技术栈的选择遵循"轻量、标准、可控"的原则：

- **不采用重型前端框架**：不选用Vue、React、Angular等前端框架，避免引入复杂的构建工具链、状态管理库和组件生态依赖。CAPP系统以表单、表格、树形结构、流程图等传统企业界面为主，原生JavaScript配合模块化开发足以满足需求；
- **HTML5 + CSS3 + ES6+**：基于Web标准技术构建前端应用，确保浏览器兼容性和未来可维护性。CSS采用Sass预处理器提升样式代码的组织性，JavaScript采用ES6 Module进行模块化拆分；
- **ECharts图表库**：选用百度开源的ECharts作为数据可视化图表库，ECharts功能丰富、文档完善、性能优秀，满足报表统计中的各类图表需求；
- **Canvas/SVG工艺图**：工艺卡片中的工序简图、流程图等采用原生Canvas 2D或SVG技术绘制，避免引入重型图形库（如Fabric.js、D3.js）带来的学习成本和性能开销。

### 6.4 其他技术组件选型

| 技术组件 | 选型 | 选型理由 |
|---------|------|---------|
| Web服务器 | Nginx | 高性能、低内存占用、强大的反向代理和负载均衡能力、静态资源服务效率高 |

| 消息队列 | Redis List / RabbitMQ | 初期使用Redis List实现轻量级消息队列，满足异步任务需求；未来业务复杂时平滑迁移至RabbitMQ |

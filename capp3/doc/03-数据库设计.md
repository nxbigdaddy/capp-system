## 1. 数据库设计原则与规范

### 1.1 设计原则

本CAPP（计算机辅助工艺规划）系统数据库设计遵循以下核心原则：

**（1）第三范式（3NF）为主，适度反范式**

- 基础数据表严格遵循第三范式，消除数据冗余，保证数据一致性。
- 针对高频查询场景（如工艺卡片展示、BOM展开），允许适度冗余字段，通过触发器或应用层逻辑保证冗余数据同步，以空间换时间，提升查询性能。

**（2）数据完整性优先**

- 所有核心业务表必须定义主键，主键采用自增整数或雪花ID，禁止业务含义字段作为主键。
- 外键关系在数据库层面定义，确保参照完整性。对于高并发写入场景，外键约束配合应用层校验共同使用。
- 关键字段（如状态、金额、数量）必须设置NOT NULL约束及默认值，避免脏数据产生。

**（3）安全性设计**

- 敏感字段（如用户密码、企业微信Token、对接密钥）必须加密存储，密码采用bcrypt算法哈希，API密钥采用AES-256-GCM加密。
- 建立完善的操作日志体系，所有数据变更（增删改）记录操作人、操作时间、变更前后值，满足审计追溯要求。
- 数据库账号按最小权限原则分配，应用连接账号仅授予必要的数据库对象DML权限，禁止直接授予DROP、TRUNCATE权限。

**（4）可扩展性设计**

- 预留扩展字段（ext_json JSON类型），用于存储未来可能增加的非结构化属性，避免频繁DDL操作。
- 字典表驱动业务状态、类型等枚举值，避免硬编码，提升系统可配置性。
- 表结构设计考虑未来分表分库需求，主键设计具备全局唯一性。

**（5）性能前置**

- 所有高频查询条件字段必须建立索引，联合索引遵循最左前缀原则。
- 大文本、文件内容存储采用独立表或对象存储（OSS），主表仅保存引用标识。
- 历史数据与在线数据分离，通过归档策略控制在线库数据量，保障查询性能稳定。

### 1.2 字符集与排序规则

- 数据库默认字符集：`utf8mb4`，支持完整的Unicode字符（包括emoji、生僻字）。
- 默认排序规则：`utf8mb4_unicode_ci`，保证中文排序符合语言习惯。
- 所有表、字段统一使用utf8mb4字符集，禁止混用utf8（MySQL早期伪实现）。

### 1.3 存储引擎

- 所有业务表统一使用`InnoDB`存储引擎，支持事务、行级锁、外键、MVCC等特性。
- 系统配置类读多写少表可酌情使用`MyISAM`（如静态字典表），但统一使用InnoDB以简化运维。

## 2. 命名规范

### 2.1 数据库对象命名

| 对象类型 | 命名规则 | 示例 |
|---------|---------|------|
| 数据库 | `db_` + 系统简称 + `_` + 环境标识 | `db_capp_prod` |
| 表 | `t_` + 模块简称 + `_` + 业务实体名 | `t_sys_user` |
| 视图 | `v_` + 业务含义 | `v_process_card_full` |
| 索引 | `idx_` + 表名（不含t_前缀）+ `_` + 字段名 | `idx_sys_user_dept_id` |
| 唯一索引 | `uk_` + 表名 + `_` + 字段名 | `uk_sys_user_phone` |
| 主键 | `pk_` + 表名 + `_` + 字段名 | `pk_sys_user_id` |
| 外键 | `fk_` + 从表名 + `_` + 主表名 + `_` + 字段 | `fk_process_route_product_id` |
| 存储过程 | `sp_` + 业务操作 | `sp_bom_expand` |
| 触发器 | `trg_` + 表名 + `_` + 操作类型 | `trg_process_card_audit` |

### 2.2 字段命名规范

- 采用小写蛇形命名法（snake_case），如 `create_time`、`update_by`。
- 主键统一命名为 `id`，类型 `BIGINT UNSIGNED AUTO_INCREMENT`。
- 逻辑删除字段统一命名为 `deleted`，类型 `TINYINT(1)`，默认值 `0`（0未删除，1已删除）。
- 时间戳字段统一使用 `create_time`、`update_time`，类型 `DATETIME(3)`，精确到毫秒。
- 创建人/更新人字段统一使用 `create_by`、`update_by`，类型 `BIGINT UNSIGNED`，关联用户表ID。
- 状态字段统一命名为 `status`，类型 `TINYINT` 或 `VARCHAR(20)`，具体含义由字典表定义。
- 布尔类型统一使用 `TINYINT(1)`，0表示假，1表示真，禁止使用BOOL（MySQL中BOOL是TINYINT别名，但语义不明确）。
- 金额字段使用 `DECIMAL(18,4)`，数量字段使用 `DECIMAL(18,6)`，避免浮点数精度问题。

### 2.3 注释规范

- 每张表必须有表注释（COMMENT），说明表的用途、业务场景。
- 每个字段必须有字段注释（COMMENT），说明字段含义、取值范围、业务规则。
- 枚举类型字段注释中必须列出所有枚举值及含义，如：`状态：0-草稿，1-已发布，2-已归档`。

## 3. 数据库ER图

### 3.1 实体关系概述

本系统核心实体关系围绕"产品-工艺-资源"三大主线展开：

- **产品主线**：产品分类 → 产品 → 零件 → BOM → BOM明细
- **工艺主线**：工艺路线 → 工序 → 工艺卡片 → 工序资源/工艺参数/工艺文件
- **资源主线**：设备/工装夹具 → 设备工序关联；材料 → 材料定额
- **支撑主线**：用户/角色/权限/部门；流程定义/流程实例/流程任务；变更申请/审批/历史
- **智能主线**：AI对话/决策记录/知识库
- **集成主线**：对接配置/数据同步记录

### 3.2 实体关系矩阵

| 实体A | 关系 | 实体B | 基数 | 说明 |
|------|------|------|------|------|
| 产品分类 | 包含 | 产品 | 1:N | 一个分类下可有多个产品 |
| 产品 | 组成 | 零件 | 1:N | 一个产品由多个零件组成 |

## 5. 数据库性能优化策略

### 5.1 索引优化

**（1）主键与唯一索引**

所有表必须定义主键，主键采用自增BIGINT UNSIGNED，保证数据物理存储有序，减少页分裂。业务唯一性约束通过唯一索引实现，避免业务字段直接作为主键导致的主键频繁变更问题。

**（2）联合索引设计**

联合索引严格遵循最左前缀原则，将区分度高的字段放在前面。例如：
- `t_pdm_bom_item`的`bom_id + seq_no`联合索引，支持BOM明细按序号快速查询。
- `t_process_operation`的`route_id + op_seq`联合索引，支持工艺路线工序顺序查询。
- `t_sys_log`的`log_type + create_time`联合索引，支持按类型分时段查询。

**（3）覆盖索引**

对于高频列表查询，设计覆盖索引减少回表。例如：
- `t_pdm_part`的`status + part_type + part_code + part_name`联合索引，支持零件列表页仅通过索引即可返回所需字段。

**（4）前缀索引**

对大字段（如`tags`、`user_agent`）建立前缀索引，控制索引大小。例如：
- `t_ai_knowledge`的`tags`字段建立前100字符前缀索引。

**（5）避免索引失效场景**

- 禁止在索引字段上使用函数或隐式类型转换。
- 避免使用`LIKE '%xxx%'`前缀模糊查询，对全文检索需求使用MySQL全文索引或引入Elasticsearch。
- `IN`子句元素数量控制在1000以内，超量分批查询或使用临时表关联。

### 5.2 查询优化

**（1）慢查询治理**

- 开启MySQL慢查询日志（`long_query_time = 1`），每日分析慢查询日志。
- 对执行时间超过1秒的SQL强制要求EXPLAIN分析，确保使用索引、避免全表扫描。
- 禁止使用`SELECT *`，必须明确指定所需字段，减少网络传输和内存消耗。

**（2）分页优化**

- 传统`LIMIT offset, rows`在offset超过10万时性能急剧下降，采用"游标分页"或"延迟关联"优化：
  - 游标分页：基于有序主键或唯一索引，使用`WHERE id > last_id LIMIT rows`。
  - 延迟关联：先通过覆盖索引查询主键，再JOIN主表获取完整数据。

**（3）复杂查询拆分**

- 避免多表JOIN超过5张表，复杂报表查询通过应用层多次简单查询+内存组装实现。
- 统计类查询（如BOM成本汇总、工时汇总）使用汇总表或物化视图（MySQL 8.0支持），定时任务刷新。

### 5.3 写入优化

**（1）批量插入**

- 批量导入场景（如BOM导入、标准工时库导入）使用`INSERT INTO ... VALUES (...), (...), (...)`批量插入，单批次控制在1000~5000条。
- 大数据量导入时临时关闭唯一索引检查（`SET unique_checks=0`）和自动提交，导入完成后恢复。

**（2）事务控制**

- 事务粒度尽量小，避免长事务持有锁资源。工艺路线发布等复杂业务采用"乐观锁+状态机"，减少行锁持有时间。
- 高并发写入场景（如操作日志、AI对话记录）允许适当降低隔离级别至READ COMMITTED，减少锁竞争。

**（3）主键设计**

- 核心表使用自增ID保证顺序写入，避免UUID随机写入导致的页分裂和磁盘碎片。
- 需要全局唯一且对外暴露的场景（如流程实例号、变更申请单号），采用独立发号器表或雪花算法生成，与自增主键分离。

### 5.4 架构层优化

**（1）读写分离**

- 系统部署一主多从架构，主库负责写入，从库承担查询、报表、AI训练数据抽取等读负载。
- 应用层通过数据库中间件（如MyCat、ShardingSphere-Proxy）或代码层数据源路由实现读写分离。

**（2）缓存策略**

- 字典表、产品分类、设备列表等读多写少数据，应用层使用Redis缓存，TTL设置为10~30分钟。
- 工艺卡片内容、工艺文件元数据等热点数据，使用Redis缓存，更新时主动失效。
- 缓存与数据库一致性采用"Cache Aside"模式：先更新数据库，再删除缓存。

**（3）连接池优化**

- PHP使用PDO连接MySQL，配置持久连接（`PDO::ATTR_PERSISTENT => true`），减少连接建立开销。
- 连接池大小根据并发量配置，公式：`连接数 = (核心数 * 2) + 有效磁盘数`，初始值建议20~50。

## 6. 数据备份与恢复策略

### 6.1 备份策略

**（1）全量备份**

- 每周日凌晨2:00执行全量物理备份（使用Percona XtraBackup或MySQL Enterprise Backup），备份文件压缩后上传至异地对象存储（MinIO/阿里云OSS）。
- 全量备份保留周期：生产环境保留最近8周，测试环境保留最近4周。
- 备份完成后自动执行校验（`xtrabackup --prepare`），确保备份文件可恢复。

**（2）增量备份**

- 每日凌晨2:30执行增量备份（基于Percona XtraBackup的增量模式），仅备份自上次备份以来的变化数据。
- 增量备份保留周期：保留最近14天，与全量备份形成完整恢复链。

**（3）逻辑备份**

- 每日凌晨3:00执行逻辑备份（`mysqldump`），导出核心表（用户、权限、流程定义、字典）的SQL文件，用于单表恢复和跨环境数据迁移。
- 逻辑备份同时导出为CSV格式，便于数据分析和AI训练数据抽取。

**（4）Binlog归档**

- 开启MySQL Binlog（`binlog_format=ROW`），所有数据变更记录到Binlog。
- Binlog实时同步至异地日志服务器，保留周期30天，支持任意时间点恢复（Point-in-Time Recovery）。

**（5）备份监控与告警**

- 备份任务通过Cron+Shell脚本执行，执行结果写入监控表。
- 备份失败立即通过企业微信机器人推送告警消息至运维群。
- 每月执行一次备份恢复演练，验证备份有效性。

### 6.2 恢复策略

**（1）全库恢复**

- 灾难恢复场景：使用最近全量备份+后续增量备份+Binlog，恢复至故障前最近时间点。
- 恢复流程：准备全量备份 → 应用增量备份 → 回放Binlog至目标时间点 → 验证数据一致性 → 切换业务流量。
- RTO（恢复时间目标）：< 4小时；RPO（恢复点目标）：< 15分钟。

**（2）单表恢复**

- 误操作场景（如误删表、误删数据）：从逻辑备份SQL中提取目标表结构及数据，导入临时库后选择性恢复。
- 对于逻辑删除（`deleted=1`）的误删，可直接通过UPDATE恢复，无需动用备份。

**（3）数据闪回**

- 利用Binlog解析工具（如`binlog2sql`、`MyFlash`），将DELETE/UPDATE操作生成反向SQL，实现行级数据闪回。
- 闪回操作必须在只读从库或临时库验证无误后，方可在生产库执行。

## 7. 分表分库策略

### 7.1 当前阶段策略

系统上线初期（数据量<1000万条），采用单库单表架构，通过索引优化、读写分离、缓存策略满足性能需求。以下表预留分表能力，主键采用BIGINT自增，未来可平滑迁移至分布式ID：

- `t_sys_log`（操作日志）
- `t_ai_chat`（AI对话记录）
- `t_intf_sync_log`（数据同步记录）
- `t_change_history`（变更历史）

### 7.2 未来分表策略

当上述表数据量超过5000万条或单表体积超过10GB时，启动分表：

**（1）按时间分表（日志类、历史类）**

- `t_sys_log`按月份分表，表名格式：`t_sys_log_YYYYMM`，如`t_sys_log_202601`。
- `t_ai_chat`按季度分表，表名格式：`t_ai_chat_YYYYQ`，如`t_ai_chat_2026Q1`。
- `t_change_history`按年份分表，表名格式：`t_change_history_YYYY`。
- 应用层通过分表路由组件（PHP实现）根据`create_time`自动路由至目标表。
- 历史表设为只读或归档至冷存储（如ClickHouse、对象存储），在线库仅保留最近2年数据。

**（2）按业务ID取模分表（高并发写入类）**

- 若未来`t_flow_task`（流程任务）数据量激增，按`instance_id % 16`分16张表：`t_flow_task_00` ~ `t_flow_task_15`。
- 应用层通过一致性Hash算法路由，保证同一流程实例的任务落在同一张表，便于聚合查询。

### 7.3 分库策略

当单库数据量超过1亿条或QPS超过5000时，考虑垂直分库+水平分库：

**（1）垂直分库**

- 将AI相关表（`t_ai_chat`、`t_ai_decision`、`t_ai_knowledge`）独立至AI库，避免AI高频写入影响核心业务。
- 将日志、监控、对接同步类表独立至日志库，采用低成本的存储介质（如SATA盘）。

**（2）水平分库**

- 按业务维度分库：产品/零件/BOM数据按产品线分库（工业压缩机库、压力容器库）。
- 分库后跨库JOIN通过应用层聚合或数据冗余（宽表）解决，复杂报表通过数据中台（ETL至ClickHouse）实现。

### 7.4 分表分库实施原则

- 分表分库对应用层透明，通过数据库中间件（ShardingSphere-Proxy）或PHP DAO层封装实现路由逻辑。
- 分表后全局唯一ID采用雪花算法（Snowflake），替代数据库自增ID，避免分表间ID冲突。
- 分表后分页查询改为"分表并行查询+内存归并排序"，或限制为仅支持游标分页。
- 分库分表方案必须在测试环境充分验证（数据迁移、双写一致性、故障切换）后，方可上线生产。
